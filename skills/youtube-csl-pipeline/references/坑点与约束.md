# CSL 与 YouTube Studio 自动化的坑点与硬约束

> 本文档原为独立 skill 的正文，作为本流水线的**坑点参考**随包分发。
> 讲的是「为什么这么做」和「踩过什么」，具体装法与操作看 SKILL.md。

# Google Play 自定义商店页（CSL）

这份文件记录 CSL 的硬约束和自动化边界。内容经过 2026 年 9 月的官方文档与行业资料查证，不是推测。

## 什么时候用

用户提到这些场景时读取本文件：

- 想按国家、语言、搜索词、用户状态给不同人群展示不同商店页
- 想做商店页 A/B 测试（比如「有视频」对「没视频」）
- 想把 CSL 创建流程自动化，操作 Play Console
- 要把本地 MP4 变成 Play 商店页上的预览视频
- 要规划 CSL 配额怎么分配

## 第零件事：选型 —— 用 UserScript，别用 Playwright

**2026-09-15 定论。** 操作 Play Console 应该用 Tampermonkey 脚本，不是 Playwright。

理由有两条，任一条都足以定案：

1. **登录。** 脚本跑在用户已登录的页面里，登录这个问题根本不存在。
   Playwright 要另起浏览器会话，实测四条路全部失败（见下文「登录方案」一节）。
2. **读本地素材目录。** `window.showDirectoryPicker()` 只有页面上下文能调用；
   Playwright 调它会弹出操作系统原生对话框，程序点不了。
   而批量上传素材必须先拿到本地文件。

> ⚠️ **本文件后面凡是提到 Playwright 的地方 —— 登录四条路、选标签页判据、
> 反自动化检测 —— 现在都是背景资料，记录的是「为什么那条路走不通」。**
> 不要照着那些内容去搭新方案。
>
> 具体实现见项目里的 `userscript/csl-helper.user.js`，
> 通用方法论见 `ops-userscript` 技能。

**UserScript 路线下依然绕不开的**（Playwright 做不到，UserScript 也做不到）：

- 官方 API 没有 CSL 资源，只能操作页面
- Play Console 的 class 名是构建产物，改版就变，选择器要实测不能猜
- 上传素材会进 Asset Library，那是 app 级共享资产库，影响面大于单个 CSL

## 第一件事：确认没有官方 API

**Google Play Developer API（androidpublisher v3）不包含 CSL 资源。**

- `edits.listings` 只有语言维度，管的是默认商店页
- fastlane 官方在 2026 年 6 月明确答复：Developer API 不暴露 CSL 和商店页实验，`supply` 只能更新默认页
- 2026 年 7 月的 API 变更没有 CSL 相关方法

所以「用接口批量传 CSL」这件事做不到。任何声称能全自动的服务商，实际都绕不开 Console 后台。

**能做的是**：内容层全自动（脚本批量生成文案和素材规格）+ 后台素材组批量同步 + 人工创建页面。

### 补充：YouTube 侧的 API —— **能传，但传上去发不出去**

这条 2026-09-21 核实（Google 官方文档原文），比 Play 侧那条更值得记住：

> *"All videos uploaded using the `videos.insert` endpoint from **unverified**
> API projects created after 28 July 2020 will be restricted to **private**
> viewing mode. To lift this restriction, each API project must undergo an
> **audit**."*

**翻译成业务语言：用 API 传的视频会强制变成"私享"，而且改不了 ——
API 改不了、Studio 里也改不了；要解除，只能让整个 API 项目过审。**

★ 这直接判了死刑：CSL 要的是**能公开访问的预览视频**，
一条私享视频放进去等于没传 —— 而整条流水线的产出就是"一堆能用的链接"。

★★ 而且审核是**两道独立**的，都要过：
  · **OAuth 验证** —— `youtube.upload` 是 Restricted scope，必须过
  · **YouTube API Compliance Audit** —— 决定上传的视频能不能不是私享
  ★ 官方**没公布周期**，按"以周计"准备。

★★★ **"配额不够"已经不是理由了**（别拿旧资料说事）：

| 时间 | 变化 |
|---|---|
| 2025-12-04 | `videos.insert` 从约 1600 单位 → 约 **100** 单位 |
| 2026-06-01 | 上传进**独立 bucket：每天 100 次** |

→ 一次传 68 个完全够。真正的障碍是上面那条"强制私享"。

**还有两个能力缺口（即使过了审也补不上）：**

| 要做的事 | 脚本（操作页面） | API |
|---|---|---|
| 缩略图**从 YouTube 自动生成的截图里挑一张** | ✅ | ❌ `thumbnails.set` 只能上传**自定义图**，没有"从自动生成的三张里选"的方法 |
| 判断这条会不会被判成 **Short** | ✅ 看对话框里链接的形态 | ❌ 平台自动判定，上传前拿不到 |

★★★ **一句话概括整个选型：**

> **API 自动化** = 以"**第三方应用**"的身份操作 → 要过平台的开发者审核。
> **脚本自动化** = 替"**用户本人**"操作 → 就是用户自己在点，**没有第三方**。

后者天然不在那些规则的范围里 —— 用户本来就有权在自己已登录的页面上做这些事，
脚本只是替他做得更快、更准。

★ 完整方法论（含流程与设计决策）见项目里的
  `docs/方法论-YouTube上传与CSL自动化.md`。


## 六条硬约束

### 1. 同一个国家同一时间只能挂一个 CSL

这是最容易踩的坑。两个 CSL 都选国家定位，第二个直接建不出来。

**做 A/B 测试时必须以「不同的 Ads 流量」为主要分配机制，而不是国家。**

```
Variant A  →  Ads Traffic A
Variant B  →  Ads Traffic B
```

⚠️ **但不要把 Google Ads ↔ CSL 的具体绑定方式写死。**
资料里流传的说法是「Ad Group 级关联」，但 Console 侧的实际入口粒度和操作路径**尚未在本机走查确认**。
可能的形式有三种：

1. Play Console 里输入 AdGroupID
2. Google Ads 里选择 CSL
3. 两侧共同配置

在 Play Console 界面走查完成前，**代码里不得硬编码任何绑定方式**，方案文档里也不要写成既定结论。
走查确认后再定架构。

### 2. YouTube API 上传的视频会被锁成 private

2020-07-28 之后创建的、未经审核的 API 项目，上传的视频被**强制锁定为 private**，且无法通过 API 或 YouTube Studio 改回。

而 Play 的预览视频要求 **public 或 unlisted**，private 播不了。产出的 URL 填进 CSL 就是死链。

解锁要过 **YouTube API Compliance Audit**，这是独立于 OAuth 验证的另一个审核，周期按周计。

**当前应采取的策略**：**不把 YouTube API 自动上传作为生产必需能力**。

#### 但「页面自动化上传」是另一条路，而且不受这个限制

上面说的是 **YouTube Data API**。走 `studio.youtube.com` 的页面自动化（UserScript 模拟点上传）
走的是网页自己的上传通道，和 API 项目的审核状态无关，**可以设成 unlisted 并发布**。

这条路 2026-09 已确认可行，代价是三件事：

| 代价 | 说明 |
|---|---|
| **配额按频道算，不按 API 项目算** | 未验证频道每天约 15 个视频，验证后约 100 个。还有每日总时长上限 |
| **删除不返还配额** | 配额按当天消耗算，传错了删掉也回不来。所以试运行要格外保守 |
| **刚发布的视频处于处理中** | Play 校验这个链接时**可能不认**。上传和建 CSL 之间要留等待，或人工确认 |

所以完整链条是：

```
本地 MP4 → 页面自动化批量上传 YouTube（设 unlisted，发布）→ 拿到链接
        → 批量建 CSL，只填 Preview Video，图文随模板继承
```

**注意「发布」这个词在两个后台的分量完全不同**，红线也不一样：

- **Play Console 的发布** = 商店页真的对外可见、Google Ads 那边可能就开始跑了。**绝对不做。**
- **YouTube 的发布** = 视频按你选的可见性出现。不发布拿不到可用链接，这一步是必需的。

写脚本时不要用一句「禁止发布」把两件事一起禁掉 —— 那会把功能一整个堵死。

### 3. 预览视频的四个播放条件

缺一不可：

- 链接指向**单个 YouTube 视频**，不能是播放列表或频道
- 视频为 **public 或 unlisted**，private 不行
- **关闭创收**，且无年龄限制
- **允许嵌入**

内容上 Google 建议至少 80% 展示真实应用体验，时长 30 秒到 2 分钟。首 5 秒最关键，因为自动播放是静音的。

### 4. CSL 名称创建后不可修改

永久锁定。批量创建前先定好命名规范，否则删掉重建会浪费配额。

### 5. 上限 50 个，A/B 双倍消耗

A/B 测试一次吃两个。10 个实验就占 20 个。规划时按「实验数 × 2」算。

### 6. Play Console 没有沙盒

没有测试环境。选中定位条件就可能真的生效。测试建议用小市场，且只保存草稿不发布。

## 图形素材规格（含最容易翻车的一条）

| 素材 | 尺寸 | 格式 | 上限 |
|---|---|---|---|
| App icon | 512×512 | PNG 32-bit，**必须带 alpha** | 1 MB |
| Feature graphic | 1024×500 | PNG **24-bit 不带 alpha** 或 JPEG | 15 MB |
| 手机截图 | 2–8 张，最小边 ≥320px，最大边 ≤3840px，长边 ≤ 短边×2 | PNG / JPEG | — |
| 7" 平板截图 | 可选；给了就 2–8 张，最小边 ≥320px | PNG / JPEG | — |
| 10" 平板截图 | 可选；给了就 2–8 张，最小边 ≥1080px | PNG / JPEG | — |

> 数字以官方文档为准，改版可能调整。关键是**这些校验要放本地做**。

**最容易翻车的一条：feature graphic 不能带 alpha 通道。**

设计师导出的 PNG 十有八九是 RGBA（colorType 6），直接传会被拒，
而且 Play 给的报错很含糊，来回试浪费的是运营的时间。

本地判断靠 PNG 头的 color type，不用解码整张图：
读前 26 字节，`offset 25` 就是 colorType。
`2`（RGB）和 `0`（灰度）才算无 alpha；`4` / `6` / `3` 都带。

**素材预检查不通过，就不应该允许创建 CSL**，而不是弹个警告继续跑。
批量操作里带着不合规素材跑一遍的代价，远高于停下来让人修图。

**另一个容易忘的**：Asset Library 是 **app 级共享资产库**。
往上传图 = 整个 app 的资产库都多一份，其他 listing / CSL 也能看到并选用。
传错图的影响面比「改一个 CSL」大得多，走查时要确认这一点。

### 但更省事的做法是：图片根本不上传

**2026-09-15 的需求变更。** 图片改成**按模板走** ——
CSL 通过「复制基准 listing」创建，图片跟着过来，脚本一个字节都不碰。

变体之间的差异改成**不同的 YouTube 链接**（而不是原来的「有视频 vs 无视频」）。
于是整个工具退化成「批量建 CSL + 每个填不同的 Preview Video」，
上面那一整节素材规格和预检查都用不上了。

**代价是风险点搬家了：**

| | 图片自己传 | 图片走模板 |
|---|---|---|
| 风险 | 传错图（看得见，能换） | **模板没带过来**（要人工逐个看才发现） |
| 最坏情况 | 一个 CSL 图不对 | **批量建出 10 个没图的页面** |

所以走查项 **D6（Duplicate 到底复不复制图片）从「想知道」升级成头号风险**。
原来图片自己传，Duplicate 复不复制都无所谓；现在整套方案压在它上面。

**改造后必须补一道运行时校验**：复制完 listing 立刻检查图片区有没有内容，
没有就中断，不要继续往下建。配一个 `templateAssetMarker`（「有图时才存在」的元素选择器）
就能做到，不配等于默认相信 D6 成立。

> 通用教训：**需求变更时，先问「最坏情况变了没有」，再动代码。**
> 风险点搬家了，但「执行前必须能拦住」这个原则没变。

### 再往后一步：文案和图片**都**别碰

2026-09-15 第二轮变更，把「图片走模板」推到极致：

> 选一个已有的 CSL 当模板 → 复制它 → **只决定要不要填视频链接，文案和图片一个字都不动**。

也就是说 Play 侧只剩 7 个步骤（原来是 11 个）：

```
创建 CSL → 选模板 → 确认素材就位 → 填名称 → 处理 Preview Video → 保存草稿 → 验证
```

删掉的是「填 Title / Short Description / Full Description」三步。
**少填一个字段就少一个填错的机会** —— 这个收益比省下来的那点代码量值钱。

> 设计上的一条原则：**需要填的字段越少，出错的面越小。**
> 一份需求里写着「模板里已经有了」的东西，就不要在脚本里再填一遍，
> 哪怕那个字段看着很简单。

## 让「同一个视频被建了两次」不可能发生

批量建 CSL 时**最隐蔽的错误不是填错，是重复**：

| | 填错一个链接 | 两个 CSL 填了同一个视频 |
|---|---|---|
| 报错吗 | 会（格式不对时） | **不会，静默通过** |
| 浪费 | 一个 CSL | 两个 CSL 配额 + 几天的实验时间 |
| 什么时候发现 | 当场 | **几天后看数据，发现两边一模一样** |

所以去重必须放在**生成任务之前**，不通过就不让生成。

### 去重要按「视频 id」判，不能按字符串判

这是最容易写错的一处。下面两条指向**同一个视频**：

```
https://youtu.be/dQw4w9WgXcQ
https://www.youtube.com/watch?v=dQw4w9WgXcQ
```

字符串比对说它们不同，视频 id 比对说它们相同。写脚本时先抽出 11 位 id 再比：

```js
const ID = '([A-Za-z0-9_-]{11})(?![A-Za-z0-9_-])';
// 认这几种写法：watch?v= / youtu.be/ / shorts/ / embed/ / live/ / studio 的 /video/<id>/edit
```

> 顺带一提，最后那个 `/video/<id>/edit` 是 `studio.youtube.com` 上传完成后的地址栏形态 ——
> 这也意味着**取视频链接那一步不用配选择器，从地址栏抠就行**。

### Play 侧的「防重复执行」键里也必须带视频 id

```js
taskKey(task) → `${task.name}|${task.useVideo ? task.videoId : 'no-video'}`
```

不带的话，「Jackpot A」这个任务换了视频也会被当成「已经跑过」而跳过 ——
表现是**改了配置重新跑，什么都没发生**。

## 可修改的字段

标题、简短描述（80 字符）、完整描述（4000 字符）、图标（512×512）、特色图片（1024×500）、截图、预览视频。

改不了的：应用包、价格、订阅、实际功能集。

另外 **CSL 不会自动本地化**。建一个定位多国的 CSL 只填一种语言，那些国家的用户就都看到这一种语言。要手动逐个加翻译。

## 降低工作量的一个手段

**素材组（Store listing groups）** 是 Google 官方给的批量手段。组级设置的素材和文本自动同步到组内所有页面。

做 A/B 时把两个变体放进同一个组，一致性由 Google 保证，不用靠脚本事后校验。

**但有个待确认点**：素材组同步的字段范围是否包括预览视频。如果包括，视频单独设置即可，正好它就是实验变量；如果不包括，那视频必须手动逐个设。用之前先在 Console 里验证。

## 配额规划建议

上限 50，按这个顺序分：

1. 主力市场一个国家一个（US / JP / DE / BR / IN / ID 等）
2. 区域合并成组（东南亚、拉美、欧洲），共用素材组省配额
3. 高流量搜索词各一个（Console 会推荐带来流量的词）
4. 买量活动一个活动一个专属链接页，保证广告素材和商店页口径一致
5. 非活跃用户做一版召回页

留余量给节日活动和版本节点。

## YouTube Studio 上传对话框：真机跑四遍才知道的十三件事

2026-09 两次真机试跑（共 3 次失败，全部停在中途）逼出来的。
**每一条都是"看代码看不出来"的**，而且**每停一次都在烧配额**
（配额按当天消耗算，删了不返还）—— 所以下面这些坑要在写代码时一次性避开，不要靠试。

> **第二次试跑（3.1.1）修的三条有一个共同点：全是「猜错」。**
> 手上没有真实 DOM 就只能猜（完成按钮叫什么、受众声明是什么文案、
> 滚动到底有没有真的发生），而**猜错一次付一次配额**。
> 所以第 8 条（结构快照）比它修的任何单个 bug 都更重要 ——
> 它让"下一轮失败"自带答案，不用再猜第三次。

### 1. 标题不要用文件名，用模板

运营的原话是「拿视频名字太low了」。文件名（`prod-b260326_buffalo_duojitai_KT_720gqw`）
当标题既不可读，也不好做 A/B。正确做法是 CONFIG 里放**固定模板**：

```js
title_template: 'Welcome to SLOT-02 — ... 🎰🔥',
description_template: [ '…', '', '⚡ 100+ SLOTS', '🎁 MORE WAYS TO PLAY', … ].join('\n'),
```

支持 `{name}` 占位（想带文件名时用），不填模板才退回文件名。
**描述也可以整段模板化** —— 长文案手填更容易填错。

### 2. ★★ 标题截断必须按 code point，不能按 `.length`

**这条会直接烧掉配额。** 营销标题都带 emoji，
而 emoji 在 JS 里占 **2 个 UTF-16 code unit**：

```
用户给的标题：99 个字符
JS 的 .length：101        ← 🎰 🔥 各多算 1
```

`slice(0, 100)` 会把 🔥 切成**孤立高位代理** `\ud83d` →
标题回读核对对不上 → 脚本抛错停下 → **而这一次上传的配额已经扣了**。

```js
function truncateChars(s, max) {
    const chars = Array.from(String(s || ''));   // 按 code point 拆
    return chars.length <= max ? chars.join('') : chars.slice(0, max).join('');
}
```

> 凡是要按「字符数」截断的字段（标题 100、简短描述 80），
> 先问一句「这里面会不会有 emoji / 中文 / 生僻字」。会，就不能用 `.length`。

### 3. ★★ `input[type=file]` 有不止一个，取第一个会抓到缩略图框

详情那一步本来就有个传缩略图的框，实测抓到的是：

```
input：multiple=false  accept=image/jpeg,image/png     ← 缩略图框
```

更阴的是：**把 MP4 塞进这个框，`input.files` 居然也"设置成功"**，
页面上还弹了上传对话框 —— 于是脚本报「YouTube 已接受」，
**看起来一切正常，实际传了个不是视频的东西**。

所以不能「取第一个」，要**打分**：

```js
function scoreFileInput(node) {
    const accept = String(node.accept || '').toLowerCase();
    let s = 0;
    if (/video/.test(accept)) s += 100;
    else if (accept) s -= 100;   // 明确限定了别的类型 → 基本可以判死
    else s += 1;
    if (node.multiple) s += 10;
    // 再按祖先加分：在 ytcp-uploads-file-picker 里 +50、在 ytcp-uploads-dialog 里 +30
    return s;
}
```

**没有 video 的就不选，报错停下** —— 不要退回 `all[0]`。
「找不到」和「抓错了还继续跑」是两个成本差一个数量级的结果。

### 4. 受众声明在对话框的滚动区下半部分，不滚不渲染

运营的原话：「面向儿童的这个选项需要下滑才能看见，你现在看不见」。

「不是给小朋友看的」这一对 radio **在滚动到底之前根本不在 DOM 里** ——
不是"在 DOM 里但不可见"，是**没渲染**。所以单纯的 `waitFor` 等多久都没用，
必须主动拨滚动条：

```js
async function withScrollSweep(find, label) {
    let hit = find();
    if (hit) return hit;
    const box = findScrollContainer();      // 必须是 overflowY:auto|scroll
    if (!box) return null;                  // 且 scrollHeight > clientHeight + 8
    const start = box.scrollTop;
    const span = Math.max(1, box.scrollHeight - box.clientHeight);
    for (let i = 1; i <= CONFIG.scroll_passes; i += 1) {   // 拨 4 档，每档停 250ms
        box.scrollTop = start + (span * i) / CONFIG.scroll_passes;
        await sleep(CONFIG.scroll_pause);
        hit = find();
        if (hit) { log(`  ${label}：滚动区往下拨了 ${i} 档才出现`); return hit; }
    }
    box.scrollTop = start;
    return null;
}
```

⚠️ 找滚动容器时**两件事都要判**：`overflowY` 是 `auto`/`scroll`
**并且** `scrollHeight > clientHeight`。只判前者会挑中一个滚不动的普通容器。

### 5. ★★ 受众声明不要靠「文案表」找 —— 用谓词

第一版是这么写的：把见过的文案一条条抄进配置：

```js
not_made_for_kids_texts: ['not made for kids', '不是给小朋友看的', '并非面向儿童'],
```

**真机第二次试跑证明这条路是死的。** 中文界面下这一对的真实文案是：

```
是的，为儿童打造
不，并非为儿童打造
```

表里那两条**都不是它的子串** → 稳定匹配不到 → 白烧一份配额。
而它追不上是结构性的：**语种多、简繁不同、文案还会改**。

改成**谓词**（两个特征同时具备），就跟具体文案脱钩了：

```js
const KIDS_WORDS = /kids|children|child|儿童|兒童|小朋友|孩童/;
const NOT_WORDS  = /\bnot\b|\bno\b|n't|并非|並非|不是|不，|不,/;
const isNotForKidsLabel = s => KIDS_WORDS.test(s) && NOT_WORDS.test(s);
```

`「不，并非为儿童打造」`（儿童✓ + 并非✓）命中；
`「是的，为儿童打造」`（无否定）不命中。

**三条必须照抄的细节，每条都是踩出来的：**

1. **否定词里故意不收单个「否」字。** 题干是「此视频是否为儿童打造？」——
   收了「否」字，**题干自己就会被当成答案**。而题干和选项在 DOM 里挨得很近，
   点错就是"标成给儿童看的"，属于必填项填错的最高代价那一类。
2. **「不」必须跟一个逗号才算**（`不，` / `不,`）。放宽成单个「不」的话，
   同一个对话框里可见性的**「不公开列出」**就会命中 ——
   "选受众"这一步直接点到可见性上。这是变异测试逼出来的反例。
3. **简繁都要收。** 只写「儿童」的话，繁体界面的「兒童」命中不了 ——
   而"漏一个写法"的表现和"这个功能没做"完全一样，都是找不到。

文案表**不是删掉，是降级成兜底**（谓词万一失手的极端情况），
而且**一开始就要保留"表 + 谓词"两条路**：先只用表跑一遍会发现找不到，
加上谓词就找到了 —— 这两条断言一起才说明"谓词是那个修复"。

**还有两个副作用要一起处理：**

- **YouTube 会记住上次的受众选择。** 已选中的再点一次 = **取消选中** →
  点之前先 `isControlChecked(...)`，选了就跳过
- **找控件要认 `aria-label`，而且多个命中要取最深的那个。**
  从根往下找时，外层容器的 `textContent` 会把所有子孙的文字拼在一起，
  先撞上的往往是**整个滚动区**，点它等于没点。
  同时要限制文本长度（`maxLen ≈ 80`），否则对话框里含关键字的
  **大段 help text** 也会被当成控件

★ **「找不到」和「选错了」必须分开报。** 找不到时先看一眼**实际选中状态**
（遍历 radio，用同一个谓词判断哪个 checked），如果本来就选着对的，
就只说"状态是对的，继续"——不要喊狼来了。

### 6. ★★ 最后一步的按钮不叫「发布」—— 它随可见性改名

视频设成 **unlisted（不公开列出）** 时，YouTube 把主按钮从
**「发布 / Publish」** 换成 **「保存 / Save」**。

理由不难懂：unlisted 不是"公开发布"，是"保存成不公开列出"。
**但点它同样会让视频可用**（拿得到链接，Play 那边能校验）——
所以这不算"没发布成功"，只是按钮换了个名字。

只配 `['Publish','发布']` 的后果：**空等 15 秒，然后谎报"等不到发布按钮"，
而按钮一直就在那里。**

```js
finish_texts: [
    'Publish', '发布',
    'Save', '保存',
    'Schedule', '排期',
    '继续', 'Continue',      // 兜底：真机上可能就叫「继续」
],
```

**顺序有意义**（精确匹配优先、再子串匹配），所以兜底的「继续」必须排最后
—— 它太通用，放前面会点错东西。

**两条附带规矩：**

- **只在对话框里找。** 页面别处也有「保存」（设置、偏好），
  不限定范围会点到一个跟这次上传毫无关系的按钮上 ——
  后果不是报错，是"**视频到底发到哪去了不知道**"
- **对话框根找不到时，绝不能退到整页去找。** `finish_texts` 里有
  「继续 / Continue」这种到处都有的词，退到整页等于把"点错无关按钮"
  从"不可能"变成"可能"。这一步本来就是对话框的第 9 步，
  根本身不存在说明流程已经不对了 —— 停下来报错比乱点强

### 7. ★★ 说「滚过了」之前得真的滚过 —— 日志说谎比不报错更糟

第一版的 `withScrollSweep`：

```js
const box = findScrollContainer();      // 只试一个标签名 ytcp-uploads-dialog
if (!box) return null;                  // ← 一次都没滚
```

而调用方打完一句「**滚动也找过了**」才放弃。
于是真因（**对话框标签名对不上 / 结构变了**）被永久盖住，
排查方向从一开始就是错的 —— 人会一直去查"为什么滚了还是没有"。

**四条修正：**

1. **日志必须说真话。** 滚了几个、拨到第几档、还是一下都没滚，全写出来。
   一个都没找到时明说「**这次没有滚动过**（别以为滚过了）」
2. **对话框根试多个标签名**：
   `ytcp-uploads-dialog` / `ytcp-upload-dialog` / `tp-yt-paper-dialog` /
   `ytcp-video-metadata-editor` / `ytcp-uploads-file-picker`
3. **返回所有真能滚的容器，不是第一个。** 对话框内部不止一层可滚结构
   （外层 dialog、里面某个 `#scrollable`、再里面某段列表），
   **受众声明在哪一层是不确定的** —— 挑错了，表现和"没滚"一模一样。
   与其猜哪一层，不如全拨一遍（拨多了没副作用，最后还原位置）
4. **"真的能滚"要判两件事**：`overflowY` 是 `auto|scroll`
   **且** `scrollHeight > clientHeight + 8`。只看样式会挑中滚不动的容器

### 8. ★★ 失败必须自带答案：结构快照

**前两次真机试跑，三次失败都是同一个模式：手上没有真实 DOM，只能猜，
猜错一次烧一份配额。** 而当时的日志只给一句「没找到」——
看不出是"真没有"、"没滚到"，还是"结构变了"。

加一个 `dumpDialog()`，在**出错的那一步**自动打印并复制一段结构快照：

- 对话框根节点的**标签名**（对不上就明说"一个候选标签名都没匹配到"）
- **所有按钮**：可见文字 + `#id` + `aria-label` + 能不能看见
  （`#id` 尤其值钱：拿到就能配成稳定选择器，从此不用按文字猜）
- **所有单/多选项**：文案 + `[✓]` 标出哪个已选中
- **含关键字的所有元素** + 一句判断（"一个都没有 → 这块压根没渲染，不是文案问题"）
- **可滚容器清单**：几个、在哪个标签上、`scrollHeight`/`clientHeight` 各多少
  （这回答的是"到底滚没滚得动"）

**★ 零配额验证法**：`dumpDialog` 在**整页**里找，不要求上传对话框在场。
打开任意**已有视频**的编辑页
（`studio.youtube.com/video/<已有id>/edit`）—— 同一套元数据编辑器，
受众声明那对 radio、可见性选项、按钮全在，**点一下诊断按钮，一个配额都不花**
就能把真实文案和 `#id` 倒出来。

先把零成本能确认的确认掉，再去烧配额。
（唯一验不了的是"unlisted 时完成按钮叫什么"—— 那只能在真机上传时看。）

### 9. ★ 「下一步」沉默前进会掩盖真因 —— 谎报军情

受众没选上 → YouTube 拒绝前进 → 脚本照点「下一步」→
报出来的错是「**等不到可见性选项 unlisted**」。

**真实原因是受众声明没选**，但报错把人指向可见性。
排查会从错误信息出发去找可见性选项的问题，方向从一开始就是错的。

规矩：**分步对话框里，「点下一步」和「下一步成功了」必须分开判。**
点完要确认真的翻页了（步骤标记变了），没变就报「上一步大概率没填成：<上一步的名字>」。

#### ★★★ 同一件事的另一半：「下一步」**一次都没点**，然后宣布成功

上面那条说的是"点了没翻页"。真机上后来出的是更阴的一种：
**「下一步」的文案表里没写中文那个词，于是它一次都没点**，
对话框停在第一步不动 —— 而脚本**照旧把后面所有步骤做完了**（在错的步骤上），
最后兜底点到了一个**翻页按钮**，然后写日志「✓ 完成：https://…」。

- 中文界面下，分步对话框的主按钮叫 **「继续」**（实测 id `#next-button`）
- 完成按钮是 **`#done-button`**（视频设成 unlisted 时它叫「保存」）
- 当时 `next_texts` 写的是 `['Next', '下一步']` —— **一个都不命中**

**三条规矩，每条都从这一次里长出来：**

1. **"往前走一页"和"这就完了"必须是两组毫不重叠的词。**
   当时「继续」被放在 `finish_texts` **最后当兜底**。它一旦被兜到，
   点下去只是翻页 —— 而"翻页"和"完成"在日志里长得一模一样。
   ★ 问自己一句就能发现：**这个词会不会出现在中间某个步骤上？** 会，它就不是完成词。

2. **点"完成"之前要有一道守卫**，确认命中的词不是翻页词。
   命中的词只要出现在 `next_texts` 里，就**不许点**，直接抛错停下。
   —— **报告成功比停下更糟**：停下不亏（东西已经交上去了、在草稿里，
   不扣新配额也不用重做），而"谎报成功"会让人以为跑通了、拿着它继续往下做。

3. **怎么一眼看出"一次都没点"：看那句"点了 N 次"有没有出现。**
   凡是"循环点击"的动作，都要在循环结束时打一句带次数的日志 ——
   **次数为 0 时也要打**（或至少让"没点过"和"点了但没动"区分得开）。
   真机上就是靠"日志里没有那句『点了 N 次』"才在十秒内定位到根因的。
   ★ 反过来：如果那句日志写成 `if (hops) log(...)`，
   hops=0 时**静默**，读日志的人只会以为"点过了但没反应"。

> 这三条合起来的元教训：**"步骤没走对"和"结果不对"要能分开看见。**
> 一个分步流程里，如果只有"最后成功/失败"的日志，
> 中间任何一步没做，表现都和"做了但没生效"一样。
> 把"我做了几次 / 步骤标记变成了什么"打出来，是唯一能把两者分开的办法。

### 9.5 ★★★ 动作做完了、日志写了，事情**没成** —— 必须回读

这是 9 节那条的**第三种**形态，也是最贵的一种。前两种是"点了没翻页"和"一次都没点"，
这一种是：**点了、日志写了、YouTube 没认**。

真机上的样子（点了可见性，然后点保存）：

```
已点「保存」，可见性 unlisted          ← 日志说成功了
✓ 完成：https://www.youtube.com/watch?v=…
```

34 秒后用户截的图：

```
当前步骤：公开范围        · 「保存」 #done-button      ← 对话框还在这儿
单/多选项（4）：[ ] 「私享」 [ ] 「不公开列出」 [ ] 「公开」   ← 一个都没勾
```

**可见性那一下根本没生效**。YouTube 因为这一项必填拒绝了保存，对话框停在原地 ——
脚本已经宣布完成。紧接着的一条因果链更值钱：
**可见性没选上 → YouTube 不渲染排期区 → "设排期"那一步也找不到东西 → 排期也没设**。
一个静默失败把后面所有步骤一起带偏。

#### 怎么回读：三个必须做对的地方

**① 读"选中状态"要从节点往**上**读，不能只看给它那一个。**

Studio 把 `aria-checked` 挂在**外层**的 `tp-yt-paper-radio-button` 上，
而按文字找控件时拿到的是**文字所在的最深节点**。
只看最深那个 → 永远读到 `null` → **"到底选上没有"这个问题在代码里根本问不出来**。

> ★★★★★ **但"往上读"的下一句是：不能把外层那个当成最新的。**（2026-09-19 实测）
>
> 真机第 4 步「评价」：脚本点了「不为资源添加标签」，**连读 5 秒每次都是 `false`**，
> 于是报「点了但没勾上」停下；而 **4 秒后**用户手动打的快照里
> **同一个选项是 `[✓] 已选中`**。
>
> 两边判据不同：
> - 诊断快照读的是**原生 input**（那一节列的就是 `input.mdc-radio__native-control`）
> - 回读读的是"手里这个节点"，从**外层**开始读 ——
>   外层那个 `aria-checked` **框架没跟着更新**，真值被一个陈旧的外层属性挡在外面
>
> **规则：`aria-*` 说 `false` 时先别急着信 ——
> 只要这个节点（或它里面）有【恰好一个】原生 `radio`/`checkbox`，
> `input.checked` 就是真值。**
>
> - 只覆盖 `false` 这个方向（`true` 依然直接返回）→ 不会把"确实选中了"读成没选中
> - **"恰好一个"是硬条件**：两个以上是"整组"，取第一个读到的是**别的选项**的状态。
>   方向很危险 —— 会**漏勾**，最后建出一个选项不对的 CSL 而配额照扣。

> ⚠️ **但"恰好一个"千万别当万能类比往外搬**（2026-09-20 实测，代价是一份报告撒谎）。
>
> 同样是"附近有输入框"，**认出"这个数字是字数计数"**要问的问题**完全相反**：
>
> | 场景 | 该问的问题 | "恰好一个" |
> |---|---|---|
> | 读某一项的状态 | **这一项**选中没有 | ✅ 对 —— 组里取一个会读到**别的选项** |
> | 认出"这个数字是字数计数" | **有没有哪个框**跟这个数对得上 | ❌ 错 —— 框多只会让判断更可信 |
>
> 实测：给字数计数那道守卫加了"恰好一个框"，而真机第 2 步名称框旁边
> **还有两个单选** → 守卫恒假 → 快照报出 `配额线索 —— CSL 的：38/50`，
> 而 38 是名称的字数（`…_duojitai_KT_1080_gqw` 正好 38 个字符）。
> 我据此在报告里写了"配额只剩 12、别建到一半撞墙"——
> **用户一句「我明明只建了 18 个」就把它戳穿了。**
>
> ★ **能搬的是原则（判据要看语义），不能搬的是具体阈值。**
> ★ 附带一条：判成"别处"的数字**也必须印出来** ——
> "我看了，它不是我说的那个"本身就是信息；不印，读的人就会把唯一能看到的数字
> 当成他要找的那个。（这次两份记录一起导致的误读：判错 + 不印。）

**② "读不到"和"没选中"必须分开。**

```
true  → 已选中
false → 确实没选中   → 这才可以报错/重试
null  → 读不到状态   → 只能警告，**不能**报错
```
拿 `null` 当 `false` 去抛，会在任何没写 aria 的版本上每次误停 —— 比静默更糟。

**③ 没生效就把点击目标往外挪一层再试。**

- **找**的时候取最深 —— 为了别误点整块容器（这条不能丢）
- **点**的时候从深到浅试 —— 因为点击处理常挂在**外层容器**上，
  点里面的 `<span>` 不生效

两条规则不冲突，但很容易只记住前一条。

#### ★★★ 最好的回读信号：**目标按钮禁不禁用**

回读"选中状态"有个前提：那个控件得**写了** aria 状态。
实测里**同样是单选，两组可读性不一样**：

- 受众那一组（`是/否，内容是面向儿童的`）**有** `aria-checked` —— 快照里能看到 `[✓]`
- 「公开范围」那一组（`私享 / 不公开列出 / 公开`）**很可能没有** ——
  于是回读只能打一句 `⚠ 读不到选中状态`，等于白回读

**而"最下面那个保存/发布按钮禁不禁用"这个信号不需要读任何单选状态**，
而且它就是 **YouTube 自己算出来的"必填项齐没齐"** —— 官方替你判断完了。

> 运营原话：「在『保存并发布』下面还需要点击**安排时间**，默认就行，
> 但是不点好像就**点不了预定这个按钮**」

也就是说：**这一组必须选中一个**，否则主按钮是禁用的 ——
点了毫无反应、对话框一动不动，而你**看不出来**是"点了没生效"还是"按钮本来就是灰的"。

所以要**在点之前**问一句：

```
isDisabled(node)  ← aria-disabled="true" / disabled 属性 / node.disabled
                    ★ 往上找几层：Studio 的禁用标常标在**外层容器**上
finishDisabledProblem(info) → 是禁用就返回一句"哪一步没选完"，然后**不要去点**
```

★ 顺带一条给诊断输出的：**结构快照里要把禁用按钮标出来**。
真机上快照写的是 `· 「保存」 #done-button` —— `·` 只表示"可见"，
而它其实是灰的。**可见 ≠ 能用**；不标出来，读快照的人会以为按钮是好的。

#### 凡是"点一下就该有变化"的动作，都要能回答"变了没有"

| 动作 | 回读什么 |
|---|---|
| 选可见性 / 受众 / 排期 | `aria-checked` 是不是 true |
| 点「下一步」 | 步骤标记变没变（见第 9 节） |
| 点「保存 / 发布」 | 完成按钮还在不在、步骤标记变没变。★ **但这还不够** —— 见下面第 7 条：「保存」是**唯一一个点完就退出整套流程**的动作，它的判据必须能**自证** |
| 填标题 / 描述 | 回读一遍字符串比对（这条一直都有） |

**没有回读的那一处，就是下次"谎报成功"的地方。** 而它们的共同点是：
**动作做了、日志写了、事情没成** —— 这三件事在日志里长得完全一样。

> ★★★★★ **回读失败时，报错必须把"现场"拆开打**（2026-09-19 实测）。
>
> 「点了但没勾上」这一句话底下藏着**至少四种修法完全不同**的情况：
> ① 点击没生效 ② 状态挂在**我们读不到的地方**（外层 aria 陈旧）
> ③ 页面**重新渲染把节点换掉了** —— 我们一直盯着一个**已经不在页面上**的旧节点
> ④ 手里这个元素**从一开始就挑错了**（比如挑到了字段标签）
>
> 所以那句报错里至少要有四样东西：
> ```
> · 手里这个是谁（标签/class/文字）+ 在不在文档里（isConnected）
> · 它自己怎么说（aria-checked / checked 属性）
> · 它里面的原生框怎么说
> · 按【同一个选择器】现在重新找一个 —— 它又是谁、又怎么说
> ```
> 最后那条是分水岭：**"手里的"和"现在能找到的"不是同一个元素**
> → 是 ③，而 ③ 的修法**不是"多点几次"**，是"每次读之前重新找一次"。
>
> ★ 一条同样便宜的伙伴：**动手之前先 `log('元素：' + describeNode(node))`**。
> 真机就是靠这行（`label` vs `div.button`）把"点错元素"从"事件序列"里摘出来的，
> 又靠它确认了修好之后点到的是**真下拉**。
> **没有这行身份信息，两份日志在纸面上长得一模一样，没法比。**

> ★ 还有一条更小的：**静默的 `return` 也是谎报**。
> 「排期」那个函数原来在"没找到"和"已经是了"两种情况下都直接 `return`，
> 日志里只剩上一行的"没找到任何能滚的容器"加一片空白 ——
> 读的人会以为"滚过了、大概设好了"。
> **每一条分支都要留话**，尤其是"我没做成"那条。

#### ★★★★★ 点完之后要**等它真的发生**：固定 sleep 不是判据，是掷骰子

**2026-09-19 定论，同一个形状在一个项目里出现了三次：**

| 次 | 动作 | 当时的写法 | 报出来的（错的）结论 |
|---|---|---|---|
| ① | 点「下一步」 | `sleep(step_pause*2)` 读一次 | "点了下一步还停在第 1 步"（页面 1 秒后其实翻了） |
| ② | 选「100%」 | 选完直接回读 | "点了 100% 没选上"（其实是弹了「是/否」没点） |
| ③ | 点开「选择受众群体」 | `sleep(step_pause*2)` 读一次 | "下拉可能没真的展开"（其实是**没等够**） |

★ ③ 的证据最干净，值得当范例记：
**同一份日志、同一段代码、同一个等待时长** —— 同一批里发布比例那个下拉
在 1000ms 内展开了（✓），受众这个没有（✗）。**两个结果**。
这恰好证明那个时长**不是判据** —— 它决定的只是"这次运气好不好"。

**判据：动作之后"有没有发生"要用轮询去等，不能用一个固定时长去赌。**
落地成三条：

1. **一直等**，轮询到目标出现为止；预算按 CONFIG 缩放（如 `max(3000, step_pause*6)`）。
2. **判"没发生"时要把"等了多久"写进报错** ——
   "等了 8 秒还是没有"和"一找就没有"对判断原因的价值完全不同
   （一个偏向页面没到，一个偏向选择器配错了）。
3. **出口要分家** —— 这是最容易被漏掉、也最值钱的一条：
   "等不到"和"等到了、但里面没有"必须走**两条不同的出口**报出来，
   因为修法**相反**：
   - 等不到 → 去查时序 / 触发按钮点错了
   - 等到了但没有 → 去改配置里的文案（页面改词了）

   ★ 而且"等到了但没有"要**立刻停**，不许把预算耗完：
   再等它也不会自己冒出来，多等的那几秒**买不到任何信息**，
   只会让报错来得更晚、还把人误导向"没等够"。

   ★ 混成一句报错的代价是实测过的：真机报"（列表里一个可选项都没读到 ——
   下拉可能没真的展开）"，正好把人往"页面不对"上引；而（如果）真相是文案变了，
   就白折腾一轮、还得再烧一次向导和配额。

4. **失败要自带答案**：只报"读到 0 个"是没用的，因为"读到 0 个"至少有**三种**原因
   （菜单没开 / 页面用的不是下拉菜单 / 触发按钮点错了）。
   做法：失败路径上再用**一套更宽的选择器**兜底读一遍
   （`[role=checkbox]`、`mat-checkbox`、`[role=dialog]`、`.cdk-overlay-pane` …），
   把"像选项的东西"列进报错。目标若出现在这份清单里 →
   当场就能说"**页面用的不是下拉菜单**，等多久都没用"。
   > ★ 这份宽名单**只进报错文本，不参与判定** ——
   > **诊断可以吵，判据必须准。** 拿它当判据会把无关元素当成选项。

5. ★★★★★ **"点不开"和"没得读"必须用浮层探测分开**（2026-09-19 实测，最值钱的一条）。

   上面那份兜底清单兑现过一次：真机报错里列出 61 项导航、且目标文字整页不存在 →
   当场判定"**菜单从来没开过**"。但"没开"还有两种，**修法相反**：

   - ① 菜单**压根没被创建** → 换**点击打法**
   - ② 菜单**创建了**（动画期间不可见 / 标记不认）→ 改**读法**

   → 做法：查**浮层类容器**（`.cdk-overlay-container` / `.cdk-overlay-pane` /
   `.mdc-menu-surface` / `mat-select-panel` / `[role=listbox]` / `[role=dialog]` …），
   **连不可见的都报**（每条带上 `可见=是/否`）。
   有 = ②（去改读法）；一个都没有 = ①（去换打法）。
   ★ **"连不可见的也报"是这个判据的全部价值** —— 加上 `isVisible` 过滤就退回
     "两种原因长得一模一样"。**这里的"噪声"正是信号。**

6. ★★★★ **一个动作点不开时，要换的是"事件序列"，不是"再点一次"。**

   铁证：同一屏上「发布比例」和「受众」是**一模一样的 class**
   （`button _ngcontent-lmx-49 border`），**一个开一个不开**。
   长得一样 → 差别只可能在事件序列上。

   把点击序列做成**三种打法**，按顺序试，并**记下哪一级生效**：

   | 打法 | 序列 | 针对的组件 |
   |---|---|---|
   | `full` | pointerover…pointerdown,mousedown,**focus**,pointerup,mouseup,**click** | 在 `click` 上打开 |
   | `downOnly` | 只到 `mousedown`，**不补 up / click** | 在 `pointerdown/mousedown` 上打开、**又被后面那记 click 关掉** |
   | `clickOnly` | 只一枪 `click` | 只认 `click` |

   ★ 嫌疑机制：整条链最后那记 `click`（`bubbles`+`composed`，会冒到 document）
     被 CDK 的"点到外面就关"收到 → **打开和关掉发生在同一串里** →
     轮询永远看不到它。这正好解释"读到的永远是 0 个"，而不是"开着但没有那一项"。
   ★ **哪一级生效本身就是证据**：第 2 级才开 → 页面把整条链当成了"点到别处"。
     **不记的话，下一轮还是只能猜。**
   ★ 实现上：把序列抽成一张数据表（`MOUSE_SEQ`），`clickHard` / `clickDownOnly` /
     `clickOnce` 只是三张表的薄壳 —— 这样"改打法"是改表，不是复制一段代码。
     （注意：`clickHard` 从此只是一层壳，**切它必须连 `fireMouseSeq` 和 `MOUSE_SEQ`
     一起切**，否则测试里就是 `fireMouseSeq is not defined`。）

   > 另一个便宜的必须项：**点之前先把"点的是哪个元素"记进日志**
   > （`describeNode`：标签 / class / 尺寸 / 文字）。
   > 没有它，两份日志在纸面上**长得一模一样，没法比** ——
   > 而"两个下拉长得一样"正是这次要判的事。

7. ★★★★★ **"保存成功"不能用"页面上有那个东西"来判 —— 必须扫基线自证**（2026-09-20 真机）。

   真机实测：整条四步向导**第一次一路走到第 4 步「保存」**（入口 / 翻页 / 100% 确认框 /
   受众下拉 / 勾选全部通过，全是历史故障点），最后却报 `UNKNOWN`：
   `没配 savedSignal —— **存没存上不知道**` → **不记录 `PLAY_DONE`、这一批停在这里**。

   ★ 注意这个**结论是对的**：那时候确实不知道。
   错的是"走到这一步还得靠人手工配一个信号"，配不上就整批卡住。

   **判据按证据强度分三档**，按顺序试：

   | 档 | 判据 | 强度 |
   |---|---|---|
   | ① | 配了 `savedSignal`（保存成功提示的选择器） | 最强 —— 页面自己说的 |
   | ② | `save_hints` 里**保存前没有、保存后才出现**的按钮 | 中 —— ★ 必须**自证**，见下 |
   | ③ | **正面**证据：读到一个**不是向导**的页面形状 | 兜底 |

   **② 的全部机关在"自证"**：保存**之前**先扫一遍页面、把现有的记下来；
   保存后只有"**保存前没有、保存后有**"的才算信号 ——
   否则"页面上有这个按钮"会被当成"保存造成的"，而它可能一直在那儿。

   ★ 真机上 `save_hints` 里那两个词（「转到概览页面」「以后再说」）
     在**保存前的页面上就已经存在**，所以**一个都没用上**。
     日志必须把这件事**说出来**（"它们在保存前就在，所以证不了保存成功"），
     不能沉默 —— 沉默的话，读日志的人会以为判据成立了。

   ★ **"没检查" ≠ "成功"**。这种情况返回 `false`、不许返回 `true`：
   错记成 `PLAY_DONE` 会让这一条**永远补不上**（既不在待办里、也没真成）。
   UNKNOWN 的报错文案要落在"**没有任何一条能自证的判据**"，
   **不要**写死某个具体成因 —— 成因会随判据档位变化，写死了下次就不对。

   ★★ **保存之后必须收尾，否则这一条的账会记在下一条头上**。
   真机用户原话：「这一步完你还要**点击以后再说**，然后循环上传视频」。
   不点掉那个提示框 → 下一条撞上"已经在向导里了"那道闸 →
   报出来的错**长得像"选择器配错了"**，而去查选择器是白查。

   落地：`playDismissSavedScreen()` —— 判成功之后
   ① 点 `save_dismiss`（**只放「以后再说」**，不放「转到概览页面」：
      那个会跳去概览页，而下一条要回的是 **CSL 列表页**）
   ② `waitFor` 等一屏"非向导形状"

   两步失败都**只 warn、不抛错** —— 保存已经确认过了，
   收尾失败不该把一次成功改判成失败。

   ★ 回到"未知"那条老账：这里正好是它的正面用法 ——
   **`UNKNOWN` 的结果是"停下来问"，不是"当成没成继续往下跑"。**
   继续往下跑的代价是**整批都建在一条没存上的记录上**。

### 9.6 ★★★★★ 按文字找控件：候选排序的第一原则是"**点了会不会有反应**"

Play 上控件的 id 是渲染时生成的 GUID，所以**按文字定位**是主力手段。
但只要"按文字"，就一定会遇到**多个候选**（字段标签、真控件、外层容器都含这段字）。
排序规则写错一次，代价可以是**两轮真机**。

**2026-09-19 实测（最贵的一次误诊）：**

| 那一步 | 实际点到的元素 | 对不对 |
|---|---|---|
| 选择商品详情 | `div.button` 「选择商品详情 arrow_drop_down」 | ✓ |
| 发布比例 | `div.button` 「50% arrow_drop_down」 | ✓ |
| **受众** | `label` 「**选择受众群体 \***」 | ✗ **字段标签** |

三个下拉是**一模一样的 class**，只有受众点不开。而点标签**什么都不会发生**：
它没有 `for=` 指得到的元素、里面也没包控件。

根因是排序规则："子串命中时取**最短**的"（本意是排掉外层容器）。
- 字段标签「选择受众群体 \*」= **8 字** → 命中
- 真下拉「选择受众群体 arrow_drop_down」= 27 字 → 也命中，但更长
- → **最短的标签赢**。

另外两个下拉没事，纯属侥幸：它们的字段标签是「发布比例 \*」/「选择商品详情」，
**不含**目标词，没有竞争者。

**规律（可直接抄）：**

1. **两级排序，顺序不能反**
   ① **能反应的压过不能反应的**；② **同档里**才取最短。
   "最短"是**同档内的**次级判据，不是第一判据。
2. **"点了等于没点"怎么判**：`clickTargetOf` 解出来还是它自己
   （没有 `for=` 能指到真元素、里面也没包控件）**且**它本身是个 `<label>`。
   > ★ `label` **不能一刀切掉**：MDC 的单选/多选选项就是靠 `<label>` + `for=`
   > 触发的，那种 `clickTargetOf` 会解到真 `input` —— 属于"能反应"的那一档。
3. **只剩一个"点不动"的候选时**：照样返回它，但**必须 warn 出声**。
   「只找到个点不动的标签」和「什么都没找到」是两种**修法不同**的情况
   （前者改选择器 / 查控件有没有渲染；后者是文案变了或不在这一屏）。

> ★★ 更值钱的是**怎么发现的**：在点之前加一行
> `log('触发按钮：' + describeNode(node))`（标签/class/尺寸/文字）。
> 就是这一行把"两个下拉长得一样、一个开一个不开"变成了可直接比对的身份信息。
> **前两轮都白花在猜"事件序列"上 —— 其实根本没点到那个下拉。**
> **一个错误的判据比一个错误的假设更值钱，因为它每次都错。**

### 10. ★★ 缩略图：一个"绝不能点到的格子"和一条"选填必须降级成无事发生"

上传完 YouTube 会给几条自动截的视频帧，可以从里面挑一张当缩略图。
它在**和标题 / 描述同一个对话框步骤**里，所以顺手就能做。但有三条规矩：

**① 那排格子里有一个是「上传缩略图」入口 —— 点了会弹系统文件选择器。**

这是**浏览器原生弹窗**：脚本关不掉、读不到，而且**异步等待会一直挂着**，
整条流程吊死在那儿。最坏的是它**不报错** ——
日志停在"正在传第 N 个"这种看起来完全正常的地方，极难排查。

所以候选里必须排掉它。怎么排：

- 先靠 id / class 里提到 `thumbnail` / 缩略图 定位到"这一块"
  （用 DOM 自己的命名，不用界面上给人看的文案 —— 文案会随语种和改版变）
- 再靠**格子自己的文字**里有没有「上传 / Upload」来判
- ★ **"格子"这一层必须定义清楚**：从 `<img>` 往上走，
  **直到再多走一步就会装进第二张图为止**。
  往外多走一层就会把兄弟节点的「上传缩略图」几个字一起读进来
  （容器的 `textContent` = 自己 + **所有子孙**），
  于是**三张真截图一起被排掉**，表现成"这个功能没做"——
  和受众声明那次"文案表不是子串"是同一类静默失效。
- ★ 搭测试数据时**要给上传格子也放一张图**（真实页面上它是个带图标的格子）。
  不放的话，"必须有 `<img>`"这一条就把它排掉了，文字判据根本没被测到。

**② 自动截图是视频处理完之后才生成的。**

刚把文件投进去时，那一排**常常还是空的**。所以找不到要**等一会儿**
（一个有上限的等待，比如 20 秒），等不到才放弃。
走查时顺手记一下"刚投完文件时那一排到底有没有图"—— 这个数决定等待给多长。

**③ 选填项的正确写法是"降级成无事发生"，不是"抛错停下"。**

YouTube 本来就会自己挑一张。所以这一步**最坏的结果必须等于"没做这个功能"**：

- 找不到 → 打一条日志说清"跳过了、这是选填项、最坏会怎样"，然后 `return`
- 越界（配的第 5 张但其实只有 3 张）→ 同一条路，**跳过**，
  不能退化成"随便点一张"，更不能退到上传入口上去
- 已经是选中的那张 → **不要点**。跟受众那对 radio 是同一个坑：
  "再点一次"到底是重新选中还是取消，**没有真实 DOM 证明得了，那就别点**。
  最坏结果是保持原样，比点掉强。
- 什么时候**才**该抛：只有当"不做这件事会让后续步骤全部跑错"的时候。
  缩略图不属于这一类 —— 抛出去只是让一份**已经扣掉的配额**白费在"没选到一张图"上。

> 一条更通用的判据：**给一个功能做"选填 / 必填"分类时，
> 问的是"失败了会不会让后面的东西跑错"，不是"重不重要"。**
> 缩略图很重要（运营明确要），但它失败了后面的步骤照样对。

#### 附带：一张截图的「同一性」判据，连着被两份快照纠了两次

Studio 把**一张**自动截图渲染成两个节点：

```html
<div class="select">  … <img src="…AOn4CLC5BN…X7A">
<div class="preview"> … <img src="…n4CLBNhJt…&retry=2">
```

- 第一份快照：两个节点**地址一样** → 于是"按图片地址去重"就够了
- 第二份快照：两个节点**地址不一样**（preview 那个带 `&retry=2`）→ 按地址去重**失效**，
  一张图算成两个候选，`index=1` 实际点到的还是第一张，而日志会写"选了第 2 张"

**教训（可迁移）：判断"这两个节点是不是同一个东西"，别用它们的内容
（地址、文字）—— 内容会变（换一条渲染路径就变了）。
用它们在 DOM 里的位置关系，或者那个稳定的结构标记（这里是 `select` 格子）。**

兜底方向也要选对：认不出 `select` 就退回"按格子 + 按地址"去重 ——
那个方向错了只是"多数一张"，`index=0` 照样对；
反过来（少数一张）会让"配了第 2 张"静默地选成第 1 张。

### 11. ★★ 拿到一份真机快照之后：先找"哪种判据被现实打脸了"

`dumpDialog` 的价值不在"它证实了我的猜想"，而在**它一次就能把猜错的地方全打出来**。
2026-09 第二份真机快照（零配额，在已有视频编辑页上取的）当场暴露了四件事，
**四件没有一件是"猜对了"**：

| 快照上看到的 | 被判据怎么骗的 |
|---|---|
| `[缩略图区] …s176-…-no-rj 格子=ytcp-navigation-drawer` | **判据是"从 `<img>` 往上找，谁的名字里带 thumbnail 就算缩略图区"**。而 Studio 给**频道头像**包的类名里就带 `thumbnail`。它是页面上第一张图 → `index=0` 就会去点它 → **把导航抽屉点开、上传流程当场断掉** |
| `[上传入口!] …no_content_illustration_v4.svg`、`[上传入口!] …error_illustration_v2.svg` | 同一个判据的另一个方向：图少的时候"往上走"会一路涨到**整页容器**，而它的 `textContent` 里当然有「上传」 |
| `可滚容器（0）` | `<html>` 的 `overflow-y` 默认是 **visible**（按规范它把滚动交给视口），可它**照样能滚**。只认 `auto\|scroll` 就把整页滚动整个漏掉 —— 页面上明明能滚，日志说"没有可滚容器 / 没有滚动过" |
| `按钮（36…）` 但只列了 30 条，且其中 6 条是**我们自己面板**的按钮 | 快照没排掉自家元素，而**被截掉的那 6 条里就有「下一步」** |

**四条规矩，每条都能省下一整天：**

1. **"从节点往上找，谁的名字像就算"是个危险判据。**
   它会同时产生**两个方向**的错误：把无关的东西拉进来（频道头像），
   把该有的东西推出去（走太远之后整个区都被判成"上传入口"）。
   ★ 换成**"先认容器，再在容器里认成员"**，而且要有一条**结构性的准入条件**：
   缩略图**选择器**天然是"一排若干个"，所以"**至少两张图**"就是个又便宜又准的
   门槛 —— 单个头像、单张插图、缩略图预览全被它挡掉。
   （预览那张图很阴：它名字带 thumbnail、里面也确实有图，
   不挡它的话它会排到候选**第一位**，脚本就去点预览图 ——
   点预览什么都不会选中，纯白点。）

2. **`<html>` / `<body>` 的"能不能滚"不能只判 `overflow-y`。**
   视口滚动就是这么实现的：`overflow: visible` 的根元素照样滚。

3. **诊断输出必须排掉"自己的东西"。** 面板自己的按钮、自己写的日志行 ——
   一个把真正的按钮挤出了截断上限，一个把"这一块到底渲没渲染"彻底搅浑
   （日志里那句「受众：不是给小朋友看的」被当成了**页面上的证据**）。
   **诊断日志里最忌讳的，就是自己的输出跑到证据栏里** ——
   这比"没有证据"更容易把人带偏。

4. **截断要说出来。** 只列前 30 条却只写"按钮（36）"，
   读的人会以为下面就是全部 —— 而真机上正好截在答案前面。
   写成"…… 还有 N 个没列出来"。

> ★★ 还有一条更值钱的元教训：**这三处误判，代码看起来都没有毛病**。
> 它们全都是"在没有真实 DOM 的前提下，把话说得太满"——
> 判据写得像模像样、注释还解释了为什么这么写。
> 所以真机快照拿到手时，**不要先去找"哪里报错了"，
> 先去找"哪条判据的假设被现实推翻了"**：
> 看那些"看起来对但没人验证过"的分类、标签、计数。

### 12. ★★★ 视频链接在页面上是「文字」，不是 href

**拿到视频 id 是整条流水线最后、也最关键的一步**（Play 那边靠这个 id 校验），
而 Studio 把链接**当文字显示**：一个按钮样的元素，文字就是那条 URL，**没有 href**。

```html
<ytcp-button id="video-link">https://youtube.com/shorts/2Tm6_KCvdrI</ytcp-button>
```

所以只读 `n.href || n.value` 的扫描**三路全部空手而归**，
然后报「视频已经传上去了，但页面上找不到视频 id」——
**而链接就明摆在页面上，同一份快照里还有一行写着它。**

**规矩：找这种"页面自己生成的链接"时，属性和文字两条路都要读。**

```js
// ① 属性：<a href> / <input value>（"复制链接"那种只读框）
// ② 文字：整段文字本身就是一条 URL 的节点
if (!/^https?:\/\/\S*youtu/i.test(text)) continue;   // ★ 见下第 2 条
```

**四条必须一起做的边界，每条都是踩出来的：**

1. **选择器清单要覆盖那个元素的每一种外壳。**
   `#video-link` 在快照里被归在**按钮那一类** ——
   清单写成 `a[href], input, span, div` 就会漏掉
   `ytcp-button` / `paper-button` / `tp-yt-paper-button` / `[role=button]`。
   ★ 少写一个标签，就是"链接在页面上、代码看不见它"的翻版。
2. ★★ **文字那一路的判据必须卡死：整段文字本身就得是 URL**
   （`^https?://` 开头 + 含 youtu），**不能是"包含"。**
   因为**内容列表就在上传对话框后面**，每条视频都有自己的地址 ——
   放宽成 contains，随便一层容器 div 都能命中，抓到的是**别的视频**的 id，
   然后**一路顺利地把 CSL 建到错的视频上，全程不报错**。
   > **"找到但错了"比"找不到"危险得多。**
   > 找不到会停下、会进日志；找到错的会静默地做错事。
3. **顺序：先对话框，再整页。** 反了就会捡到内容列表里那条旧视频的地址。
4. **读 `textContent`，不要读 `innerText`。**
   `innerText` 每次读都触发布局计算，在几百上千个节点的循环里会明显卡页面。
   代价是 `textContent` 会把隐藏文字算进来 —— 第 2 条的判据正好挡住这个。

> ★★★ 更该记的一条：**这一段在此之前一个测试都没有。**
> 整条流水线最关键的一步零覆盖，所以它带着 bug 出了厂，只有真机才暴露。
> 补测试时**必须带一条对照断言**：用老写法在同一个 DOM 上跑一遍，
> 断言它**一个都读不到** —— 没有对照，"现在能读到"证明不了
> "以前读不到、而真机就是以前那种结构"。
>
> **判断"哪一段最该有测试"的方法：问"它错了会不会让结果悄悄错掉"。**
> 取视频 id 完全符合 —— 而且它错了的下场是"把 CSL 建到别的视频上"。

### 附带：两处「是时序不是选择器」和一处静默降级

- **找不到标题框 ≠ 选择器错。** 实测同样一份代码，11:04:02 找不到、
  11:04:18 找到了，**两次唯一的差别是时间**。
  所以「找不到就报选择器错」这个结论本身就是错的 ——
  先 `waitFor(...)` 到超时再说
- **模板没传到队列里会静默退回文件名当标题。** 面板 → 队列传参这一步
  抽成一个纯函数（`buildYtForm()`）才测得到；不抽就只能靠肉眼盯
- **`max_per_run` 在单条闭环跑通前保持 1。** 每停一次都在烧配额，
  批量试错的代价是线性的

## 接管浏览器：Chrome 136+ 的坑

想把自动化接到「用户自己已经登录好的浏览器」上，有两条路，但都有门槛。

### 坑一：默认 profile 上开不了调试端口

**Chrome 和 Edge 从 136 版本起，在默认 profile 上 `--remote-debugging-port` 会被静默忽略。** 参数给了不报错，端口就是不开。这是 Google 为防 cookie 窃取做的安全改动，绕不过去。

所以**没法直接接管用户日常在用的那个浏览器和它的登录态**。必须用 `--user-data-dir` 指向非标准目录，而一旦指定独立目录，拿到的就是全新 profile。

好消息是这样拿到的 profile 是**持久的**，登录一次可以长期复用，不用每次重登。

### 坑二：接手别人的浏览器时别乱导航

如果做了「用户自己开浏览器登录，程序只附加」的模式，**千万不要在用户没登录时导航到目标站点**。

导航到 `play.google.com/console` 会被重定向到 `accounts.google.com` 的登录页。这不是「程序在打开后台」，这是「程序弹了个登录页出来」，体验很差，也违背了「让用户自己登录」的初衷。

正确做法是**不导航，只查 Cookie**：

- Google 账号级鉴权 Cookie 是 `SID` 和 `__Secure-1PSID`（HttpOnly，页面 JS 读不到，但 Playwright 在浏览器进程里能读到）
- 用 `context.cookies(['https://accounts.google.com'])` 检查
- 有这些 Cookie 才导航，没有就原地等着，提示用户去登录
- 多账号时 `SAPISID0` / `SAPISID1` 这类编号副本可以反推账号数

这样全程不触发任何登录页，用户在自己的窗口里爱怎么登怎么登。

### 「复用日常浏览器登录态」四条路，2026-09 实测全部不通

这是个很自然会想到的省事思路（「我浏览器里已经登录了 Google，直接拿来用不行吗」）。
把四条可能的路全试过一遍，**结论是没有一条走得通**，不要再重复折腾：

| # | 方案 | 实测结果 |
|---|---|---|
| 1 | 附加到**正在运行**的日常浏览器 | ✕ 它没有调试端口，连不上 |
| 2 | 用默认 profile 手动开 `--remote-debugging-port` 启动 | ✕ 等 14 秒端口没开，参数被静默忽略 |
| 3 | Playwright 直接挂默认 userDataDir（Windows 走 **pipe** 不是 port） | ✕ `Timeout 30000ms exceeded` |
| 4 | 复制 profile 里的 `Local State` + `Cookies` 过来 | ✕ Cookie 被浏览器整个清空 |

第 3 条特别值得记：**「Playwright 用 pipe 所以能绕过 port 限制」是错误猜想，pipe 同样被限制。**

第 4 条失败的根因是 **ABE（App-Bound Encryption，应用绑定加密）**：

- `Local State` 的 `os_crypt` 里会有 `encrypted_key` 和 `app_bound_encrypted_key` 两个键，
  后者把解密密钥绑定到**具体 profile 路径**
- 文件复制到新目录后密钥对不上，浏览器无法解密这些 Cookie，于是**直接丢弃**
- 症状很有辨识度：**Cookies 文件大小不变（如 640 KB），但 `cookies` 表 0 行**

另外 Google 侧还有 **DBSC（Device Bound Sessions）**，`Network/Device Bound Sessions` 文件
把登录会话绑定到设备，即便 Cookie 侥幸解密成功，跨 profile 也未必被 Google 认账。

**结论：这次登录躲不掉，必须在自动化专用 profile 里人工登一次，之后长期有效。**
不要试图用第三方工具解 ABE 密钥 —— 那属于绕过浏览器安全机制。

### 两个容易误判的点

1. **不能用浏览器账号信息判断 Google 登录态。**
   `profile.info_cache.Default.account_info` 为空只说明**浏览器账号**（Microsoft 账号）没登，
   跟 **Google 网站账号**是两回事。实测遇到过：`account_info` 为空，但 Cookies 里
   SID / SAPISID / HSID / SSID / LSID / APISID / ACCOUNT_CHOOSER 全套都在。
   **判断 Google 登录态只能扫 cookie 表。**

2. **读 cookie 值要看对列。**
   现代 Chrome / Edge 把值存在 `encrypted_value` 列，`value` 列是空的。
   按 `name` 列扫名字是对的，判断加密形态要看 `encrypted_value` 的前缀（`v10` / `v11` / `v20`）。

### 给非技术用户配「双击启动」时的 Windows 编码坑

这类项目常要给运营同学配一个双击就开的 `.bat`。两个坑：

**坑一：中文输出必然乱码。**
Node 输出 UTF-8，cmd 默认代码页是 GBK(936)。解法是在 `.bat` 开头加：

```bat
chcp 65001 >nul 2>nul
```

同时 **`.bat` 文件内容保持全 ASCII** —— 中文提示放在 Node 脚本里输出，
不要让 `.bat` 自己去 `echo` 中文，免得脚本自身编码出问题。

**坑二：验证编码的方式本身会骗你。**
- 在 **PowerShell** 里跑 `cmd /c xxx.bat` 看输出 → 显示乱码，
  但那是 **PowerShell 用 GBK 解码 UTF-8 字节**造成的显示问题，不是 `.bat` 的毛病
- 在 **Git Bash** 里跑 `cmd //c "xxx.bat"` → 会进交互模式不执行脚本，中文文件名更难传参

**正确做法**：用 Node 起子进程，`encoding: 'buffer'` 拿原始字节，
再判断是不是合法 UTF-8（解码后不含 `\uFFFD` 即为合法）。

### 选标签页：Playwright 环境下没有可靠判据，必须显式指定

自动化要操作浏览器时，往往得从用户开的一堆标签页里挑一个。
**这件事不能自动猜**，三个看起来可行的判据 2026-09 实测**全部不可靠**：

| 判据 | 实测结果 |
|---|---|
| `context.pages()[0]` | ✕ 返回**创建顺序**，不跟随激活状态 |
| `document.visibilityState` | ✕ 有头无头**都**恒为 `'visible'`，不区分前后台 |
| CDP `Target.getTargets` 顺序 | ✕ 乱序（实测返回 3,2,1,4） |

第一条最容易中招：用户开了 5 个标签页、切到第 5 个，`pages()[0]` 还是第 1 个。
在「记录页面结构」这类场景下选错页，会把 A 页的数据记到 B 页头上，**且不易察觉**。

**正确做法**：挑选顺序显式化 ——

1. `--tab=<序号>`（用户指定，最可靠）
2. `--url=<片段>`（按 URL 匹配）
3. **唯一的**目标页（只有一个时无歧义）
4. 兜底第一个，但必须**标记「这是我猜的」并列出所有候选**告知用户

**绝对不能靠 `bringToFront()` 来「主动激活」目标标签页** ——
那是抢用户前台焦点的禁用操作，测试里也不该出现。

### 关闭浏览器时的坑

`taskkill /IM xxx.exe`（优雅关闭，不带 `/F`）之后，Edge 会用
`msedge.exe --no-startup-window` **自动拉起后台预加载进程**。
它没有窗口，但仍然锁着 Cookies 数据库（表现为 `WinError 32`、`unable to open database file`），
连 SQLite 的 `backup()` 在线备份接口也读不出来。**必须再强杀一次。**

判断方法：命令行含 `--no-startup-window` 且不含 `--type=` 的就是后台进程，强杀对用户无副作用。

### 别用万能选择器做占位符

登录态 DOM 判定的占位选择器**留空**，不要填 `'body'`。

踩过的坑：占位符写成 `'body'`，结果空白的 `chrome://new-tab-page/` 也命中，未登录被误判成已登录。加两道防线——不在目标域名下的页面直接判 false，空选择器直接短路成 false。**宁可判不出来，也不要误报已登录。**

## 登录状态必须分层判断（最容易犯的错）

### 「Google Cookie 存在」≠「Play Console 能操作」

这是本领域**最危险的简化**。有 Google 登录 Cookie 只说明浏览器里有账号 Session，
完全不代表这个账号进得了 Play Console、更不代表它有权改目标应用。

必须分成四层独立判断，任何一层都不能由上一层推出：

```
Browser  →  Google Session  →  Play Console  →  Developer Account  →  Target App
```

| 层 | 判据 | 未通过时 |
|---|---|---|
| Google Session | `SID` / `__Secure-1PSID` 存在 | 提示用户自行登录 |
| Play Console | **必须单独打开 Console 页面判断** | 换有权限的账号 |
| Developer Account | 当前开发者账号与预期是否一致 | 停止，防止改错账号 |
| Target App | 包名与预期是否一致 | 停止，防止改错应用 |

命名上也要守住：Cookie 检查函数叫 `checkGoogleSession()`，
**不要**叫 `isLoggedIntoPlayConsole()`；返回值用 `GOOGLE_SESSION_OK`，
**不要**用 `signed_in` 这种暗示「可以干活了」的措辞。

### 三态，不要布尔

所有页面元素判断返回 `found` / `not_found` / `unknown`，不要 true/false。

**空 selector 必须立即返回 `unknown`，禁止 fallback 到 `body`。**

selector 没配好时判成 `ACCESS_DENIED` 是灾难性的 —— 会让人以为账号没权限，
跑去申请开通，而真实原因只是走查还没做完。

写操作安全闸要**把 UNKNOWN 也算作不通过**：

```
Google Session ✓  +  Play Console ?  →  禁止写操作
```

判不出来就不许写，没有例外。

### ★ 「未知」不许被汇总成「失效」（2026-09-20 真踩）

体检 YouTube 链接死活的工具（`tools/check-video-links.py`），判据是拉
`img.youtube.com/vi/<id>/default.jpg`：200 = 活着，404 = 已删。

那天这台机器**访问不了 `img.youtube.com`**，20 个链接全部返回"问不到"。
而汇总行打印的是 ——

```
记录 20 条，活着 0 条，已失效 20 条
★ 需要处理的（这些文件建不出可用的 CSL）：
  - prod-b260326_EMPRESS WU_IF_KT_1080_gqw.mp4 （? 问不到（网络问题？URLError））
  …（20 行）
```

**这是把"没看"算成了"没有"。** 读的人会当场以为整批视频都被删了，
而下一步动作是"重传一遍"——**而这个动作本身是错的，还可能触发重复投稿**。

| 场景 | 正确措辞 | 错误措辞 |
|---|---|---|
| 网络不通 | 「没问到」「本次判不了死活」「结论本次不成立」 | 「已失效」「没有记录」 |
| 空 selector | `unknown` | `not_found` |
| 脚本没跑 | 「没跑过」 | 「检查通过」 |

三条硬要求：

1. **汇总行必须把"没问到"单列**，不许并进"已失效"——
   前者什么都不用做，后者要处理，混在一起等于把噪声当信号。
2. **整批都没问到时，整体声明"本节结论不成立"，并停止打印"需要处理的"清单** ——
   那份清单的依据是零。
3. 同名多项取"最新那条"时，判据要用**那一条自己的状态**
   （`group[-1]['http']`），不要用 `alive[-1] is not group[-1]` ——
   后者在最后一条"没问到"时会报出「最新那条死了、旧的反而活着」，依据同样是零。

这条对所有"探测"型判据都成立：**链接活不活、视频传没传、页面在不在。**
和本 skill 的「三态，不要布尔」是同一条规矩的两个面。

### 状态面板要分层显示，不要合并成一句「OK」

```
Browser            Edge 153
Mode               Attach
Google Session     ✓ OK
Play Console       ✓ Accessible
Developer Account  - Not checked
Target App        - Not checked
```

合并成一句「登录状态：OK」会让人误以为后面可以直接写数据。
被上游阻塞的层要报 `UNKNOWN(blocked_by_xxx)`，比「Not checked」更准确 ——
「被上游挡住」和「压根没查」是两件事。

## Playwright 自动化的注意事项

- 用 `launchPersistentContext` + 独立 profile 目录，**绝不碰用户日常浏览器 profile**
- 用系统安装的浏览器（Chrome `channel: 'chrome'` 或 Edge `channel: 'msedge'`），**不要用内置 Chromium**。内置版没有正常浏览器指纹，Google 风控更严
- **绝对不能开 headless**。实测无头模式 UA 会变成 `HeadlessChrome/153.0.0.0`，等于直接告诉 Google 这是爬虫，登录必挂。必须 `headless: false`
- profile 按浏览器通道分目录，两通道登录态可并存，代价是各自首次都要人工登录一次
- Edge 需要额外关掉一批噪声功能，否则弹窗和侧边栏会干扰自动化：`--disable-features=msEdgeSidebarV2,msEdgeShoppingAssistant,msEdgeCollections,msEdgeCopilot,msEdgeIdentityFeature,msFeedSSO,msEdgeSync`。注意 `--disable-features` 只能出现一次，重复出现后面的会覆盖前面的
- URL 加 `?hl=en` 固定英文界面，否则 selector 随账号语言变
- Play Console 是 Angular SPA，class 名是构建产物，定位只能用 role / label / testid / text
- Playwright 走 CDP 合成事件，**不移动真实光标**，不抢系统鼠标。只要不调 `bringToFront` 就不影响用户
- 上传文件用 `setInputFiles`，不要触发系统文件选择框
- 保存只到草稿，发布留人工
- 附加模式下关闭会话时**只断开 CDP 连接，绝不关闭浏览器**——浏览器是用户的，不是程序的

**本机实测的基础检测项**（有头模式下 Chrome 与 Edge 均未发现明显异常）：UA 不含 Headless、`navigator.webdriver === false`、`window.chrome` 存在、插件数正常。

⚠️ 措辞要守住：这**只说明常见基础特征没有明显暴露，不代表浏览器无法被识别为自动化环境**。
不要在方案文档里写成「没有自动化特征泄露」这类绝对结论。

加 `--disable-blink-features=AutomationControlled` 可让 webdriver 标志归位。

**风险提示**：自动化操作 Play Console 违反平台 ToS。用「持久化 profile + 人工登录」比全自动登录风险低，但建议用专门的运营账号，不要用主账号。日常用 Chrome 的话，可以专用 Edge 跑自动化，两个浏览器互不干扰，顺带隔离账号。

## 测试这类脚本时必须守的隔离规则

自动化测试**绝不能碰 `browser-profile/`** —— 那是用户的真实登录态，一次污染就要人工重登。

- 所有起浏览器的测试都在 `os.tmpdir()` 下建临时 profile
- 用**假 Cookie** 注入 + `route` 拦截伪造页面来测状态判断，不要真去登 Google
- 临时目录用 `TEMP_DIRS` 集合 + `process.on('exit')` 兜底清理，
  不然输出被 `head` 之类截断触发 EPIPE 时 `finally` 跑不完，目录就残留了
- Windows 上删临时目录要重试 3 次，文件句柄释放比 Linux 慢

### 硬编码端口是个真陷阱

测 CDP 附加时**不要硬编码端口**（比如 9222 / 9333）。

踩过的坑：硬编码 9333，结果撞上用户残留的 Edge 实例，`probe()` 返回了**别人的浏览器**，
测试结果全是假的。更糟的是它可能连上用户正在用的浏览器。

正确做法是用 `net.createServer().listen(0)` 让系统动态分配空闲端口，
再加一道通道一致性校验（确认连上的是自己起的那个浏览器）。

## 选择器配置：手抄，别做拾取器

这类脚本的 selector 是**一次性配置** —— 配完就不再动。为它养一套运行时系统
（生成候选 → 数命中数 → 唯一性校验 → 覆盖层落盘 → 导出回源码）不划算：
实测这样一套东西能长到一千多行，而它解决的问题每次只花十几分钟。
2026-09 做减法重构时整块删掉了，脚本从 5495 行降到 1816 行。

**手抄四步**：F12 点元素 → 看有没有 `id` / `data-*` / `aria-label`
（优先级按这个顺序，构建产物 id 如 `ng-tns-c123-4` / `css-1x2y3z` 不能用）
→ **粘到 Console 里数命中数** → 是 1 才写进 CONFIG。

```js
document.querySelectorAll('你抄的选择器').length   // 不是 1 就别填
```

数命中数是唯一不能省的一步。命中 3 个的选择器不会报错，
它会**点第一个碰巧匹配的元素** —— 表现成「步骤过了但结果不对」，比直接失败难查得多。
数出来不是 1 就往祖先方向换容器，找到有稳定 `role` / `aria-label` 的那层为止。

**选择器只有一种来源**：源码里的 CONFIG。不要做 `override` / `CONFIG` / `auto detect` 三级 ——
三级就是三种「这个值从哪来」的可能，排查时要同时想三件事。
也不要做「点页面元素自动生成 selector」的拾取器，那是把一次性工作做成常驻系统。

**只留「缺一个就停下」的选择器。** 「可选但推荐」的那种（错误提示、进度条、
素材校验标记）问题是"配了没配都能跑"，排查时要同时想两条路径。
实测 Play 侧只需要 8 个：创建入口 / 复制模板入口 / 模板搜索 / 名称框 /
预览视频框 / 清空预览视频 / 保存 / 保存成功提示。
YouTube 侧 5 个：文件 input / 标题框 / **描述框** / 受众声明 / 关闭对话框。

> 数命中数是唯一不能省的一步 —— 但**有些选择器可以先不配**：
> YouTube 侧这 5 个都写了自动兜底（按 `contenteditable`、按 `aria-label` 文字找），
> 所以留空也能跑，配了是为了"别再猜"。**配的时候一定要看它是不是唯一**：
> 标题框的 `aria-label` 实测是 `Add a title that describes your video`，
> 里面的 `describes` 含 `desc` —— 拿 `desc` 找描述框会**先命中标题框**。
> 找描述框必须先排除标题框，再找标题框后面紧挨着的那个 `contenteditable`。

按钮类（下一步 / 发布 / 可见性）**按可见文字找**，文字串明写在 CONFIG 里，
找不到就报错停下。这不是"猜"，也不会退化成「随便点一个按钮」。

> `保存` 这个选择器填错成发布按钮后果最严重。要有一道兜底：
> 点之前读按钮文案，命中 `publish` / `发布` / `send for review` 直接拒绝点击。
> 但兜底只是底线，正确定位仍然靠走查时看准。

### 工具坑：CRLF 行尾会静默打断按行匹配的脚本

维护这类脚本的工具（变异测试、源码切片器、批量替换）大多靠**多行精确匹配**。
源码一旦被 Windows 编辑器或 Python 文本模式写入存成 CRLF，所有多行 `find` 全部失效。
表现不是「某条规则失效」，而是**一次性报一大堆**，很容易误判成工具坏了，
进而把检查放宽 —— 那比不检查更糟。

两条防线：

1. 工具读源码时统一把 `\r\n` 归一化成 `\n`。
   JS 语义不受行尾影响，归一化是等价的，但顺手把「被人存成 CRLF」这件事喊出来
2. **匹配不上就报错退出，不是跳过。** 跳过会变成「什么都没改，当然全绿」

### 同一类工具坑：假警报比不检查更糟

维护这类脚本的另一个工具是 `tm-has-marker.py` —— 它回答
「我这次改的那段代码，到底有没有进到浏览器里装的那份」。

它里面有一组**反向特征串**：精简重构**应该删掉**的名字，出现就说明装的是旧版。
2026-09 往这组里加了 `isClickable`（3.1.0 删掉的假判断），
结果每次跑都报「本地源码里还留着 isClickable」——
因为它**还留在 `findControl` 的注释里**（那段注释在解释为什么删它）。

**杀伤力被低估了**：看到的人第一反应不是"检查错了"，而是**去翻那个函数**；
翻半天发现没毛病，最后只能得出「这个工具不准」，然后把它关掉。
**一个假警报换来的是一个被弃用的检查工具。**

所以：

- 挑反向特征串的硬规矩 —— **把名字从代码里删掉之后，`grep` 一遍还有没有结果。**
  注释、文档、日志文案里还提过一次，就不适合当特征串
- 这条规矩要**写进工具里**：把「只出现在注释行」的命中单独归类并打印
  「这些只在注释里出现过，不算」，不能只写在文档里等人记住
- 判断用**行级**的（这一行 strip 后是否以 `//` / `*` / `/*` 开头）就够，
  这样 `const u = 'http://127.0.0.1:8798/';` 不会被误判，
  也不需要去处理引号里的 `//`

### 发版必须升 `@version` —— 版本号相同 = 分不出装的是哪一份

**同一天里，同一个版本号可能发过两次。** 2026-09-18 实测：
浏览器里装的那份和盘上最新那份**都写着 `3.2.28`**，而**内容差 139 行**
（9459 vs 9598）。第一处不同正好是当天改的关键项
（`createCsl: null,` ↔ 已填上真值）。

后果**不是"提醒一句就能发现"，而是两类判断同时失效**：

- 油猴按**同版本**处理 → 点了「更新」也不一定会真的重装；
- 就算装上了，事后**分不出装的是哪一份** ——
  查版本号的工具两边都读到 `3.2.28`，会理直气壮地说「已是最新，不用更新」。

→ **只要改了脚本，就把 `// @version` 一起升。** 这不是仪式：
省一个版本号的功夫，赔掉的是「更新到底生效了没」这个**当场唯一能验**的东西。

配套三条：

- **`@version` 不能当判据的全部。** 版本号是脚本自己声明的 ——
  回退、贴错文件它都不会告诉你。要确认"盘上这一版真的装上去了"，
  得把浏览器里那份正文**解出来跟本地逐行比对**（`tm-has-marker.py`）。
- **每次发版，特征串清单跟着加一条。** 加的不是"这版改了什么"，
  而是"这版**新写了哪个名字 / 哪个字面量**"。
  ★ 改了既有函数、**一个新标识符都没有**的版本（3.2.28 就是这样），
  特征串只能用**字符串字面量** —— 别因为"别的组都是函数名"就硬去找个名字。
  ★ 判据是"这条串在**装的那一版**里是 0 次"，不是"本地源码里有"。
- **升完版本号要再跑一次变异预检。** 变异的 `find` 串是**源码的一份拷贝**；
  改源码（哪怕只是插一段 changelog 注释）就可能撞上它，让变异**静默失效** ——
  失效的变异照样算进总数、照样"全绿"，因为它压根没改任何东西。

> ★★★★★ **还有第四件，2026-09-19 用一轮白干换来的：
> 让脚本在日志里自己报出版本号。**
>
> 那一轮：用户又跑了一次，输出和上一轮**一字不差** —— 而真相是
> **他根本没装上新版**。判断这件事靠的是**对比代码特征**
> （"新版会多打一行 XX；这次没有，所以是旧版"）——
> 这属于**旁证**，而旁证会错：新版要是恰好没走到那一行，特征就看不出来。
> 代价是用户白跑一轮、我白分析一轮，还可能得出**方向相反**的结论
> （"新版没修好" vs "根本没装上新版"）。
>
> → 在**批次开头**（用户必然会看的那一行）打出脚本自己的版本：
> ```
> 这一批要建 1 条：　（脚本 v3.2.42）
> ```
> 实现：读 `GM_info.script.version`（`typeof` 守卫），
> **读不到就如实说"读不到"**，绝不编一个版本号 ——
> 编了，读的人会拿着那个号去对代码，**比不写更糟**。
>
> **"发版升版本号"解决的是"两份不一样"；
> "用户手里是哪一份"要放到用户看得见的地方才算解决。**

### 从油猴存储里认"自己的脚本"：按 `@namespace` 过滤，别按版本号最高挑

Tampermonkey 的存储里可能同时躺着**好几个脚本** ——
2026-09-18 实测这台机器上有**两个油猴实例**，各装各的：

| 存储（扩展 id） | 里面装的是什么 |
|---|---|
| Chrome 商店版 | 另一款脚本（`@version 6.0`，265 行） |
| Edge 商店版 | 本项目的 `CSL Helper`（3.2.28 + 2.0.0 两份） |

如果"挑出我们的脚本"这一步写成 **`max(所有脚本, key=版本号)`**，
`6.0 > 3.2.28` → **挑走了别人的脚本**。于是本项目的每一份正文都被归进
"旧版本残留"，**每一项特征串都报 ✗** —— 一句"修复没装进去"的假警报，
而人多半会把一个**正在正常工作**的版本重装一遍。

★ **最危险的形状**：判据本身没错，错的是**喂给它的文本**；
判据越"干净"，给出的假结论越整齐 ——
当时一份临时脚本里**每一个**候选串都被判成"新版独有"，
唯一露馅的是**已知答案的对照组**（`ICON_WORDS` 明明在装的那一版里）。

三条硬规矩：

1. 认自己的脚本用 **`@namespace`**，不用 `@name` ——
   名字会被改（本项目就改过），namespace 是钉子
2. 这个判据**只有一个定义处**（放在共享解码器里，如 `OUR_NAMESPACE`）。
   各调用方各抄一份，抄错一个字就会**一声不响地去认别人的脚本**
3. 跑任何"从存储里找我们的东西"的判据时，**同屏必须有一个已知答案的对照组**
   —— 它是唯一能揭穿"文本读错了"的东西

## 改完行为就跑测试 → 全绿 ≠ 新代码被验过

**症状**：往流程里加了新的守卫（形状门 / 必填项抛错 / 返回值判断），
跑测试**全部通过**。于是以为改对了。

**真相**：那个"全绿"只说明**新代码没被测到** ——
加进去的行为和"没加"的行为，在原有用例眼里**长得一模一样**。
而这类守卫要防的正是"脚本默默干了错事"，默默干错事**不会被旧断言发现**。

**规矩（两步，缺一步"绿"就只是数字）**：
1. 先给新行为补用例，每条新行为至少两个角度：
   **① 该拦的拦住 ② 该放行的放行**。
   只写 ① 的话，把守卫改成"无条件抛错"照样全绿 ——
   而真机上的表现是"这个工具再也跑不起来了"。
   （本项目原话：**一个恒真的判据比没有判据更糟**，它让人以为自己知道。）
2. **再**在变异器里把行为拆掉（照着"修之前的那个行为"复刻，不是随便改个比较符），
   跑一次确认用例真的变红。红的条数 ≥ 1 才算这组用例有区分能力。

**这条规矩的代价是诚实的**：补用例 → 补变异 → 跑变异，比"加完代码看到 772 全绿"慢得多。

## 变异器按功能组跑：`--group`，别用 `--only` 手敲名字

改完某一摊功能（比如向导第 1 步），要跑的守卫有二十条。
`--only a,b,c,…` 手敲的坏处是**敲漏一个看不出来**（输出里只少一行），跑完照样一屏 ✓。

**做法**：分组规则写**一处**、按**名字**派生，**不给每个变异加 `group:` 字段**。
理由：那要改 179 处，而且以后新增变异忘填就会**静默地不属于任何组** ——
`--group play` 少跑一条，而"少跑了一条"和"跑了且绿了"在输出里长得一样。

配套三件：
1. `--groups` 列出所有组，并**当场核对"各组条数之和 = 变异总数"**。
   对不上就说明有条变异两次没被算上（派生坏了），必须变成响亮的报错。
2. 跨几个组的"一摊"用**逗号并组**（`--group play-url,play-dedupe,play-groups`）。
   不要为它拍一个语义含糊的伞组 —— 边界是谁定的、后来的人怎么知道？
   组名写错当场报错，比一个含糊的伞组可靠。
3. `--group` 与 `--only` 同时给 → **直接报错**。
   否则输出里"跑了 N 个"到底是谁筛的，读的人得回去翻命令行。

**伞组（`play` / `core` / `all`）绿了只说"这几摊都没坏"**，说不到某一处 ——
输出里要明说这句，不然会被当成"我那处没问题"。

## 测试里打桩：`makeEnv` 的规矩会让"桩"变成死代码

这类测试套件通常用「从源码按函数名切出函数、再求值」的方式跑**真代码**。
切的时候有个规矩，它会导致一个**极难自查**的错误：

> **凡是被点名切进来的名字，用源码真身；只有没被点名的，才生成
> `var x = deps.x` 这种"桩"。**

于是当你**同时**做了这两件事：

1. 把某个函数加进了要切的名单（比如因为用例要直接调它）；
2. 又在 `deps` 上给它放了一个桩（比如因为"这一步的题目不是它，想跳过"）；

……那个桩就**永远不会被调用**。跑的是真实现，而真实现会在夹具上做真事
（等待、真的去查 DOM），于是用例以一种**看起来像别的问题**的方式红掉。

**2026-09-18 实测三次，三次都红在错的地方**：

| 症状 | 真因 |
|---|---|
| 一组 8 条全红，报"没进向导"，像"模板门坏了" | 被点名的函数用了真身，桩是死代码；真身拿"列表页"夹具等向导，等满 15 秒 |
| 报 `safeDeepAll is not defined` | 手写了一份 `fnNames` 清单，漏了一个依赖；它既不在清单、也不在 `deps` → 名字根本不在作用域里 |
| 压短等待的 `CONFIG.wait_timeout = 400` 不起作用 | 把 `CONFIG` 也点名切了进来 → 切的是**源码那份字面量**，测试改的是另一个对象 |

**三条规矩**：

1. **不要手写 `fnNames` 清单**。用已有的那份（比如四屏流程用的 `STEP_FNS`），
   需要桩就把名字**从里面减掉**：
   `STEP_FNS.filter(n => n !== 'deepQueryOne')`。
   手写清单的下场是"漏一个 → 那个名字不在作用域里 → 报一个和被测行为
   毫无关系的错"。
2. **不要点名切 `CONFIG`**。让它从 `deps.CONFIG` 走，才和别的组改的是同一个对象；
   点名切进来等于换了一份配置，所有"临时压短等待"的操作全部落空 ——
   而症状是"用例假绿"或"跑得特别慢"。
3. **给每个环境加一条自检断言**，在跑任何行为断言之前：
   ```
   eq(['A','B','C'].filter(n => typeof env[n] !== 'function'), [],
      '环境自检：这几个必须切进来');
   ```
   它的价值是**把"环境搭错了"和"被测行为坏了"分开** ——
   2026-09-18 那次是它一句 `实际 undefined` 直接点出真因，
   省掉了一轮误诊（否则会去查"等待为什么没生效"）。
4. **桩要在 `makeEnv` 之前放好。**（2026-09-19 实测踩到）
   `makeEnv` 只给"`deps` 里**已经有的键**"生成 `var x = deps.x` ——
   写成"先 `makeEnv`、再 `deps.clickHard = …`"，那一行**根本不会生成**，
   而函数体里引用 `clickHard` 就成了 **`clickHard is not defined`**
   （注意：不是"不是函数"，是**没这个名字**，看着像别的问题）。
   → 要当桩的东西，`deps.X = …` 必须出现在 `makeEnv(...)` **上面**。
   ★★★★ 反过来也有一个坑（2026-09-22 实测）：**环境建好之后再换 `deps.X`
   是没用的** —— 那行 `var x = deps.x` 已经把**当时的那个值**抄走了。
   症状是"桩换了，行为一点没变"，比前一种更难查（前一种至少有报错）。
   → 当**同一个环境里要换几次桩**的时候，`deps.X` 放一层**间接**：
     ```
     let impl = fnA;
     deps.X = function () { return impl.apply(null, arguments); };
     // 之后只换 impl，不用重建环境
     ```
     本项目 3.2.59 就是这么换假 `Image` 的（三种行为：alive / 404 / 永不回调）。
5. **自检名单要包含"传递依赖"**，不能只列自己直接调的那几个。
   2026-09-19 实测：`findOneByText` 内部要调 `clickTargetOf`
   （把"按文字找到的候选"换算成"真正该点的元素"）——
   漏了它，新写的 7 条断言**全红在 `clickTargetOf is not defined` 上**，
   而红的位置离真因（环境）隔着一整段被测代码。
   这类依赖的共同点是：**"没走到那一行就不会报错"**，所以藏得住。
6. **假 DOM 的"选择器语法"必须一项一项补齐** ——
   这是本类脚手架最阴的坑：**不支持的写法 = 静默返回空数组**，
   症状永远是"页面上没有这个东西"，而真因在假 DOM。

   已经补过六种，每次都是被一个具体的假象逼出来的：

   | 写法 | 没补时的假象 |
   |---|---|
   | `*` | `collectRoots` 找不到 shadow root，穿透层**静默失效** |
   | `#id` | 按 id 找按钮的分支**一条都跑不到** |
   | `,`（逗号列表） | 诊断快照"页面上什么都没有" |
   | 裸 `[attr]`（不带标签名） | `[role="radio"]` 那一档等于不存在 |
   | `[class*="…"]` | 步骤条永远找不到 |
   | **`.class`** | 2026-09-19：造"浮层"夹具时，源码 `.cdk-overlay-pane` 读到 0 个 → 报错说"浮层压根没被创建"，**而夹具里明明摆着一个** |

   ★ 最后那条最危险：**差一点把夹具的缺陷当成源码的行为去改源码。**
   → 规矩：**夹具里读到 0 个时，先怀疑假 DOM 认不认这个写法**，
     再怀疑源码。（和"读到 0 个先查环境缺不缺函数"是同一条。）

7. ★★★★ **断言里的阈值要卡在"两种行为各自的值之间"，不能"大概差不多"。**

   2026-09-19 两个实测例子，方向相反、都很难看：

   - **太紧 → 抖动**：`spent2 >= 2500`，实测跑出 **2494ms**，差 6ms 翻脸，
     套件连跑两次得到 919/1 和 920/0。而这 2500 是我**算错**的：
     三级探测各 700ms ≈ 2100ms，**不是** 3000ms 的预算。
   - **太松 → 抓不住**：`spent1 < 1000`（想钉"菜单开着就要立刻早退"），
     而两种行为分别是 **~0ms** 和 **~700ms** —— 1000ms 把两者都放进来了，
     去掉早退那个变异**照样全绿**（921/0，变异报告"没抓住"）。
     收紧到 400ms 才红。

   ★ 两条落地办法：
   ① **能用确定性判据就别用墙钟** —— 上面第一例最后改成"数试了几种打法"
      （`tried.length === 3`），跟机器快慢无关。
   ② 非要用时间，就先**把两种行为各自的值量出来**，阈值取中间，
      并把这两个值写进断言的说明里（下一个人改代码时才知道边界在哪）。

### ★★★ 同一个机制的反向坑：`log` 也被空桩吞掉，于是**插桩插了个寂寞**

上面那条规矩（"点名的用真身、没点名的给 `var x = deps.x` 空桩"）有两个方向：

- **正向**（上面记的）：你把桩放给了**被点名**的函数 → 桩是死代码，"跳过这步"没生效。
- **反向**（2026-09-19 实测）：你在**只切了白名单的组**里插一行调试日志 ——
  比如某组是 `makeEnv(['waitFor','StepError','sleep'])`，
  而你为了看现场在等待循环里插了 `log('limit=…')` ——
  那个 `log` 正是 `var log = deps.log`（**空桩**）→ **一个字都打不出来**。

后果比"没看到"更糟：你会得出**方向相反**的结论 ——
"这段代码根本没跑到"，于是去查调用链，而实际它正在原地死循环。

**规矩：插桩要用"确定切进来了"的东西。`throw` > `log`。**

```js
// 别这样（在只切白名单的组里，log 可能是空桩）
log('[debug] limit=' + limit);

// 这样：抛出去一定能被用例的 catch 接住，还能进失败列表、带上真实值
throw StepError('[debug] 走到这里说明期限永远退不出去：'
    + JSON.stringify(limit) + '（类型 ' + (typeof limit) + '）');
```

2026-09-19 实测效果：换成 `throw` 之后，那个原本**挂死黑屏**的套件
**跑完了**（900/1），并且自己把在死循环的坏值喊了出来 ——
`NaN` / `Infinity` / `'abc'` / `{}`（`-1`、`[]` 因为是"立刻返回"，不在其中）。
**一次插桩同时拿到了"确实在死循环"和"是哪些值"两个答案。**

> 顺带一条工作方法：变异器报「这条是以**挂死**形式被抓住的」时，
> 它自己也会提示"看一眼是不是被**别的**等待带崩的"。
> 这个提示**必须执行** —— 否则你只是知道"流程不返回"，
> 并不知道起作用的到底是哪处守卫。上面那套插桩就是为了回答这个问题。

## 一个会挂死的测试，比一条红用例贵得多

**这是本项目踩过最贵的失败形态**，值得单开一节。

2026-09-18 实测：`npm run test:core` **跑了 8 分钟不结束、一个字的输出都没有**。
前台超时被自动转后台，看进程列表才发现它还活着 ——
**没有报错、没有退出码、没有现场。**

根因：等待函数的期限读成了 `undefined`，而写法是
```js
const limit = timeout || CONFIG.wait_timeout;   // ← undefined
if (Date.now() - t0 >= limit) return null;      // ← 恒为假
```
`for(;;)` 里那个退出条件**永远不成立** → 永不返回。

**三条落地规矩**：

1. **等待类函数里，期限不是非负有限数就当场抛错。**
   不要"给个默认值兜住"—— 那只是把配置错误藏起来，
   而且会让"到底等了多久"变成一个谁都不知道的数字。
   报错里要写清：读到的是什么、为什么这会导致永不退出、去哪查。
2. **`||` 和 `??` 会吞值 —— 用精确判断。**
   `timeout || CONFIG.wait_timeout` 会把 `0` / `NaN` / `''` 全部换成默认值。
   实测发现传 `0`（语义明确："只探一次、不等"）会被静默变成 15 秒等待。
   正确写法：`(timeout === undefined || timeout === null) ? 默认 : timeout`。
   ★ 这类"值被静默替换"和"一找不到就抛"是同一个毛病：
   **调用方表达的意图没有到达执行处。**
3. **配置副本的漂移守卫要比"整个顶层"，不要"挑几棵子树"。**
   原来只 walk 了 `yt` / `selectors` / `play` 三棵子树，于是
   "副本漏抄了一整段顶层标量"它**看不见** —— 而这次挂死就是这么来的。
   判据换成**顶层键集合必须完全相等**（多一个也红：
   那等于测试在验一个真机不存在的东西）。
   顺带：判断"这个值合不合法"时也要覆盖标注的价值 ——
   `JSON.stringify(NaN)` 返回的就是 `"null"`，
   于是失败列表会把 `NaN` 那条写成 `null → …`，
   读的人去查 `null` 那条路，**而真凶是 NaN**。
   **报出来的标签撒谎，比不报还贵。**

4. **判「挂死」不能用"跑多久"，要用"多久没动静"。**
   变异器第一版给的是"整轮超过 90 秒 = 挂死"。而有一条变异
   （把"命中就立刻返回"改回"先无条件等满一轮"）会让套件从
   **30.0s 涨到 91.7s** —— 每次 `findOne` 都白等 8 秒，**是真 bug**。
   90 秒那条线正好卡在中间，于是它被当成挂死杀掉，
   而它本来要报的那条红（869/1，红的正是那条零延迟断言）
   **完全没机会说出来**。

   ★ 根子上：**「卡死」和「只是变慢」在"总时长"这一层长得一模一样。**
     总时长是二值判据（到点就杀），分不出"永不返回"和"一直在做、只是慢"。
     换成**「连续多久没有任何输出」**之后两者天然分开：慢的在动，卡死的不动。
     实测：基线最长安静 4.1s、那条慢变异 24.0s → 门槛定 45s。

   ★ 门槛**用基线校准**（基线最长安静 ×6，下限 45s），不写死：
     一台慢机器上正常的安静时间本来就更长，写死就每条都被误判成挂死。

   > **判据：选的那个量，必须能区分你要区分的东西。**
   > 拿一个回答不了这个问题的量去判，得到的不是"弱一点的答案"，
   > 是一个**错的答案** —— 而且它会把真正的答案**盖掉**。

   ★ 顺带两条：① 每次运行都把「用时 / 最长安静 / 门槛」报出来，
     让"离误判线还有多远"是看得见的；② 换用法定的新判据后，
     `execFileSync` 得换成 `spawn`（前者只能等结束，拿不到中间过程，
     所以没法知道是"卡住了"还是"在慢慢做"），函数随之变 async。

5. **有一种挂死是"正常"的：那条守卫**自己**的用例就是会挂死的那个。**
   2026-09-19 实测：把「期限必须是数」那道守卫拆掉时，
   守卫自己的用例（喂 `NaN` / `Infinity` / `'abc'` / `{}`）进入永不返回的循环，
   **整个套件黑屏** —— 它**没法自己报出"NaN 没抛"**，
   只能靠变异器的安静判据兜住。
   → 这种变异记成"以挂死形式被抓住"是**对的**，不算缺断言；
     但必须按上面那条插桩办法**确认一次**，把"是这处守卫"和"是别的等待"
     分开。分不开的话，你手里的只是一句"流程不返回"，不是一个结论。

## 模仿用户要模仿全：人点得开 ≠ 脚本点得动

2026-09-18 真机：脚本点了顶部「创建自定义商品详情」，**等满 15 秒页面一帧没变**，
向导没打开；而**用户手工点同一个按钮能打开**。

★ 这一步的价值：**手工点得开，就把"没权限 / 这个入口是死的"排掉了** ——
剩下的差别只有事件序列。原来的 `clickHard` 只派
`mousedown / mouseup / click`，而真实鼠标走的是完整一条链：

```
滚进视野 → pointerover / pointerenter → mouseover / mouseenter
→ pointermove / mousemove → pointerdown → mousedown → focus
→ pointerup → mouseup → click
```

Angular Material（新版 `mdc-button`）有一部分交互挂在 **`pointerdown`** 上，
缺了前面几枪，处理函数一次都没被叫起来。

> **判据：装到一半的动作，在页面看来不是"弱一点的点击"，是"根本没点"。**

**三条落地规矩**：

1. **合成点击要补齐整条链**，并且**点之前先 `scrollIntoView`** ——
   虚拟滚动 / 懒渲染的列表里，没进视野的元素压根没挂监听。
2. **这类回归不报错、不红**，只表现为"真机上点不动"。
   所以必须写断言 + 配变异（缺 pointer / 缺 focus / 不滚进视野三条），
   否则下次被人删掉一行没人知道。
3. **排错顺序：先让人手工做一次。** 手工能做通，就把外部原因（权限、
   入口失效、页面真的没这个功能）一次性排掉，剩下的才是代码的锅。
   ★ 反过来一开始就改代码，会在三个假原因之间来回浪费好几轮。

★ 附带一条诊断法（用于"用户到底有没有更新脚本"）：
别问"你更新了吗"，去**数新版必然打印的东西**——
本期有四处签名（等向导那行、`findOne` 那句"还没出现"、报错末尾的"当时在哪一屏"、
等待时长），用户日志里一条都没有，就是旧版；一条都有，就是新版工作正常。

### ★★★★★ 测试脚手架那一族坑：**环境错，报错长得像被测代码错**

2026-09-20 一天之内第三次踩到同一个形状，值得单独列一节：

| 次 | 缺的 / 放晚的 | 断言报出来的 |
|---|---|---|
| 早期 | `logSink` 没进名单 | 「期望 false，实际 null」——**看着像逻辑错** |
| 24f | `overlayRootCheck` 桩放晚了 | 读到的是另一个分支的话，**看着像改错了逻辑** |
| 组 25 | `deps.confirm` 放晚了 | 「期望 1，实际 0」——**看着像源码没问确认** |

**机制**（`makeEnv` 的实现决定的）：

```js
const setup = Object.keys(deps).filter(k => !cut[k])
    .map(k => 'var ' + k + ' = deps[' + JSON.stringify(k) + '];').join('\n');
return new Function('deps', setup + '\n' + src)(deps);
```

→ `deps` 里**当时存在**的键，会在**构造那一刻**被抄成局部 `var`。
   之后再改 `deps.xxx = …` **一点用都没有**。

**两条规矩**：

1. **桩必须在 `makeEnv` 之前**放好。
2. 桩要长成"**读一个闭包变量**"的样子，测试里改那个变量 —— 不要事后改 `deps`：

   ```js
   let rootState = { count: 1, visible: 1 };
   deps.overlayRootCheck = function () { return rootState; };   // ← makeEnv 之前
   ...
   const env = makeEnv([...]);
   rootState = { count: 0, visible: 0 };                        // ← 测试里改这个
   ```

★ 顺带：凡是"切进来"的名字**不要**再在 `deps` 里放同名桩 ——
   `cut` 会跳过它（`var` 不生成），源码版生效，桩等于没写。
   反过来，**要当桩用的就别切它**（组 24f 就是这么做的：
   切 `overlayRootSay` 真身、留 `overlayRootCheck` 当可配置输入）。

### ★★★★★ 测试里**不许写死运营给的文案**

2026-09-20 实测的代价：换一个产品的标题/描述，**连测试一起红了 5 条**：

|---|---|

   把"不许残留旧产品名"写成断言，等于给换产品这件事装了个哨兵。

★ 通理：**测试写死运营文案 = 给"换产品"这件事加一道税。**

### ★★★ 归档类功能：**只留一份的"备份"迟早会把上一份冲掉**

2026-09-20 踩到的形状。背景：运营要「之前的记录不显示」——
他要的是**换一批**（旧的搁一边、新的从零开始、以后能取回），不是删除。

第一版（3.2.47）的实现是"清理前先备份一份"（覆盖式）：

```
归档第 1 批 → 备份 = 第 1 批
传完第 2 批 → 归档第 2 批 → 备份 = 第 2 批，第 1 批没了
```

★★ **它不报错**：第二次归档照样成功、日志照样说"已归档"，
   只有某天想找第一批的时候才发现它早没了。
   ★ 而运营手上三个产品轮着来 → **每换一次产品就是一次归档** → 这个坑一定会踩到。

**规矩：凡是"先存再清"的退路机制，退路本身要能堆多份。**

落地三条：

1. **改成栈**（新的在前，上限 5 份）。★ 上限要显式写出来并有用例钉住 ——
   但判据必须是"**截断之后不为空**"，只断言"没超过上限"的话
   `slice(0, 0)` 那种手滑照样能溜过去（0 也符合"没超上限"）。
2. **兼容老格式**。键的**结构**变了（对象 → 数组）时，
   读的地方必须认旧的 —— 否则老用户一点"取回"就是"没有归档"，
   而那一份**是真实存在过的**。
3. **取回不弹出**。归档是历史，取回是复制回来。
   弹出的话，用户"只是想看看"就会永久损失一批，
   而他在点「取回」的时候**完全不会意识到那是在删除**。

★ 还有一条措辞上的：**名字要跟语义一致**。
   "清理"听起来像删掉 → 让人不敢点；点完又以为彻底没了 → 不去看外部存档。
   → 叫「归档（不再显示）」，并且在日志里**两个都说**：
     看不见了、但还在。

★★ 最后：**归档只在浏览器里**（清缓存/换电脑就没了）。
   这类数据要长期留，必须有**落到文件系统**的导出
   （本项目是 `tools/export-video-records.py`，写成 md 放进素材服务器）。
   ★ 归档按钮的日志里要提示这一句 —— 不说的话用户会以为"归档了 = 安全了"。

### ★★★★★ 删注释是**静默**的 —— 用「代码指纹」给自己搭安全网

2026-09-20 做「注释外移到 docs」时意识到的：

| 改动类型 | 安全网 |
|---|---|
| 改代码 | 1023 条用例 + 248 个变异 —— 改错会红 |
| **删/挪注释** | **什么都没有** —— 删完不会红、不会提 |

★ 也就是说，这类重构里**最容易出事的那部分恰恰没有保护**。
  「挪错了（把代码一起删了）」「顺手改了个变量名」都不会有任何提示。

**做法：先存一份"剥掉注释之后的代码"的指纹，改完对一次，必须逐字节一致。**

    node tools/code-fingerprint.js --save     # 改之前
    （…挪注释…）
    node tools/code-fingerprint.js --check    # 改之后：绿了才算成功

★ 实现上的两个要点（都在 `tools/code-fingerprint.js` 里）：
  · **必须识别引号**。源码里有 `'https://www.youtube.com/…'`，
    粗暴地找 `//` 会把 URL 切成两半，指纹全错。
  · **同时记行号**，不一致时直接指出是第几行变的 ——
    只说"变了"等于让人自己去找。

★★ 配套的还有一条：**代码有没有变，别拿 `git diff` 判断**。
  那个会把"注释动了"也报出来，几百行噪声里分不出代码是否也动了。
  指纹只回答一个问题：**代码本身变没变**。

### ★★★ 被切片的结构（CONFIG 这类）要**留余量**，别贴着上限写

2026-09-20 撞了两次，同一个形状。

测试的 `slice()` 对每个声明有**行数上限**（CONFIG 是 800），
本意是抓"掩码炸了 → 括号不配对 → 切片一路吃到文件末尾"。这没问题。

问题在于**贴着上限写注释**：

- 第一次：CONFIG 涨到 **824** → 组 0 崩
- 第二次：压过之后又涨到 **801**（就超 1 行）→ 组 0 又崩

★ 而**越界的表现极具误导性**：

```

通过 479 / 失败 6      ← 越界时
```

  组 0 一崩，**后面几十组全不跑**，通过数腰斩。

  把人往"查掩码"上引，而真因只是**注释多写了一行**。

  而"这个报错在猜什么"也该被审视 —— 至少要把**判据**摆出来
  （切片尾巴停在文件末尾 = 掩码炸了；停在正确的收尾括号 = 就是太长）。

### ★★★★★ 「已传过没有」这条判据要往**宽**的那边站

2026-09-20 做「上传过的视频标注 + 跳过已上传」时的设计决定。

判据有两种写法，而它们的**代价不对称**：

| 写法 | 判错了会怎样 |
|---|---|
| 判**窄**（比如要求 `videoId` 非空才算传过） | → **重传**：频道上多一份、上传额度不回收、还得专门去删 |
| 判**宽**（只要有记录就算传过） | → **漏传**：人工看一眼就能补，再跑一次就行 |

★ 所以判据必须往**宽**的那边站：**宁可漏传，不可重传。**

★★ 而"判窄"这个错特别容易犯，因为它**看起来更严谨**：
  "没拿到链接 = 没成功 = 应该重传" —— 这个推理听起来很顺，
  而它漏掉的是：**`videoId` 为空只说明"没落成链接"，
  视频很可能已经传上去了**（停在草稿、或者脚本在取链接那一步崩了）。

**通理：凡是"这条以前做过没有"的判据，都要先问一句
"判错的两个方向，代价是不是一样大"。不一样大的时候，往代价小的那边站。**

### ★★★ "顺序承重"的代码：两个都对，只有先后错了

同一件事里踩到的另一类。`runYtQueue` 里有两段：

```
① 跳过以前传过的   ← 必须在前面
② 超过上限就报错   ← 必须在后面
```

★ 顺序反了的后果：这一批 189 个、上限 20 ——
  "勾了 189 个、其中 20 个传过了"会**先**被 ② 拦下、整批一条都不传，
  而真正要传的只有 169 个。**报出来的数字是错的。**

★★ 而这类错在 diff 里**完全看不出来**：两段代码都在、都写得对，
  只是先后换了位置。**所以判据必须钉"相对位置"**：

```js
const pSkip = qSrc.indexOf('uploadedInEntries(');
const pLimit = qSrc.indexOf('CONFIG.yt.max_per_run');
ok(pSkip >= 0 && pSkip < pLimit, '跳过必须在超上限检查之前 —— 顺序是承重的');
```

★ 同类需要"钉相对位置"的还有（本项目里已经出现过的）：
  · "基线要在点击之前扫"（保存自证）
  · "先确认再回读"（下拉选择）
  · "先备份再清空"（归档）
  ★ 共同点：**都是"动作 A 必须先于 B"**，而两段代码本身都没错。

### ★★ 长列表的实时判定要**带缓存**

`matchYtFilter` 会被**每一个条目**调一次。189 个条目 ×
每次重建一次"已上传索引"（= 189 次 `GM_getValue` + JSON.parse）

做法：索引函数内部带 300ms 缓存（跟 `cachedRoots` 一个量级），

★ 不主动失效的话，刚传完的那条要等 300ms 才会显示成"已上传"，

### ★★★★★ "查源码里有没有这段字符串"只是**半个断言**

2026-09-20 做变异测试时抓到的：一条变异**没被抓住**，而它的破坏力很大。

被守的代码：

```js
if (failedList.length) {
    log('—— 这一趟有 ' + failedList.length + ' 条失败 ——', 'warn');
    failedList.forEach(n => log('  · ' + n, 'warn'));
    ...
}
```

断言：

```js
ok(/这一趟有 ' \+ failedList\.length \+ ' 条失败/.test(slice('runYtQueue')), ...)
```

变异：`if (failedList.length)` → **`if (false)`**

★ **字符串一个字都没少** → 断言照样绿 → 变异没被抓住。

★★ 也就是说那条断言**是假的**：它测的是"我写了这段话"，
  而不是"这段话**真的会打出来**"。

**它的适用边界**：

| 变异类型 | 字符串断言挡得住吗 |
|---|---|
| 删掉整段 | ✅ 挡得住 |
| 改 `if` 条件让它**永不执行** | ❌ **挡不住** |
| 把函数体掏空 | ❌ 挡不住 |
| 函数压根没被调用 | ❌ 挡不住（除非同时断言调用点） |

**修法：凡是"说出来的话"，都抽成函数，然后真的调一遍。**

```js
function reportFailures(list) { ... }        // 抽出来

// 测试里真跑：
const env = makeEnv(['reportFailures', 'log', 'LOG_LINES', 'logSink']);
env.reportFailures(['aaa.mp4', 'bbb.mp4']);
ok(/aaa\.mp4/.test(logs), '文件名要真的打出来');
ok(/可能已经传上去了/.test(logs), '要说清为什么需要人工看');
```

★ 顺带一定要有**反向断言**：`reportFailures([])` → **一条日志都不该打**。
  每批都刷"这一趟有 0 条失败"会把日志淹掉，
  而这类"汇总日志"的价值全在"**它出现 = 有事**"。

★★ 一句话：**"源码里有这句话"和"这句话会被说出来"是两件事。**
  前者靠 `slice + regex` 就能验，后者必须**真跑**。

### ★★★ 报错里的"我做了哪些尝试"必须有**代码保证**

同一个项目里出现过两次，值得并成一节：

- **3.2.46**：报错写着「三种打法都试过了」，而预算是 `3 × probeMs`
  正好吃满 → 第三级**根本没跑满**。而那句话是
  「问题在点击」这个结论的**唯一依据**。

- 同类：**"等了几秒"** 也必须是真等到的（`Date.now() - t0`），
  不是配置里那个数字。

★ 判据：**报错里只要出现"都做过 / 都试过 / 等够了"这类断言**，
  就要问一句：**它有代码保证吗？** 没有的话，那句结论是悬空的 ——
  而读的人会照着它去改方向。

### ★★★★★ 「归档」会顺手废掉**别的功能**的判据 —— 数据要按**作用域**分开

2026-09-20 晚。运营问：「你下次会不会把我这次上传的视频显示成没上传？」

★ 查了数据：**那一批不会**（21 条记录都在）。
★★★ 但顺着这个问题查下去，发现**另一条路上真会**：

```
「已上传」的判据原本读的是 VIDEOS
        ↓
归档会清空 VIDEOS（那是它的职责：让 Play 侧的列表变空）
        ↓
归档之后 → "已上传"标记全没
        ↓
下次扫目录，每个文件都显示"没传过"
        ↓
而「跳过已上传的」是**默认开**的 —— 它以为跳过了什么，实际一个都没跳
        ↓
整批重传（频道上多一份、额度不回收、还得专门去删）
```

★★ **全程一个错都不报**：归档成功、日志说"已归档 N 条"，一切正常。
   而运营手上有三个产品轮着来 → **每换一次产品就是一次归档** → 这个坑一定会踩到。

**判据：一份数据被"清空/归档/重置"的时候，要去查谁还在读它。**

问三个问题：

1. 这份数据回答的是**哪个问题**？
2. 清空它，是在回答"**这一批**有什么"，还是在回答"**历史上**有什么"？
3. 谁在读它？读的人想要的是前者还是后者？

★★ 如果两个问题混在一份数据里，就该**拆开**：

| 数据 | 回答的问题 | 生命周期 |
|---|---|---|
| `VIDEOS` | **这一批**传了什么（给下游当队列用） | 会被归档清掉 |
| `UPLOADED_EVER` | **历史上**传过什么（管"传没传过"） | **只增不减，归档不动** |

★ 落地时四个地方要一起改，少一个都不成立：
  ① 写入点（本项目放在 `saveVideos` 里，而不是各个调用点 ——
     调用点有好几个，漏一个要等到**归档之后**才暴露，中间隔着很久，联想不到）
  ② 读取点（索引要先铺永久名单、再叠当前记录）
  ③ **清空之前**要把这批并进永久名单（顺序：归档 → 并入 → 清空）
  ④ 日志里**把这件事说出来**（"标记不受归档影响"）——
     不说的话用户会以为"归档 = 这批当没传过"，然后去重传一遍

★★★ 还有一条更一般的：**"清空"这个动作的返回值要带上它的副作用**。
   本项目把 `clearVideoRecords` 的返回从裸数字改成了
   `{cleared, everTotal, everMissing}` —— 因为"这批进没进永久名单"
   现在也是这一步的**后果之一**，得有地方能说出来。

### ★★★★★ 本地记录会跟服务端**分叉** —— 要留一个"让人手动纠正"的口子

2026-09-22。运营问：「现在我的 YouTube 有 31 条视频，为什么我的谷歌才 20 个？」

★ 查出来的账：

```
传过的不同文件 50 · 其中视频还在 29 · 已被删 21
脚本认为"已建过 CSL"的（PLAY_DONE） 50
Play 上实际有的                       20        ← 差 30
```

★★ 根因不是脚本算错，是**账分叉了**：

```
他在 Play 后台手动删了 CSL
        ↓
Play 不知道脚本有一份"已建过"记录 → 删自己的
脚本也不知道 Play 被删了           → 留着记录
        ↓
重跑时这 30 条被当成"已经建过" → 跳过
        ↓
永远补不回来
```

**判据：只要"某个状态"存在服务端的副本，本地那份就一定会过期。
区别只在于"过期了会不会被发现"。**

★★ 想过自动修 —— 跑到 Play 页面把已有 CSL 名字读回来对账。
**放弃**，理由是这条老规矩：
**「没问到 ≠ 已失效」**。Play 列表是分页/懒加载的，
"我没读到"和"它不存在"**长得一模一样**；
一旦按"没读到 = 缺"来判，就会**重复建 → 白烧配额**（而配额不可逆）。

→ 所以做成**用户手动清**：脚本**不去猜**，只提供"清空已建记录"这个动作，
  外加**把账目算清楚给用户看**（`docs/CSL账目核对表.md` 那种对账表）。

★★★ 这类"手动纠正口子"的四条硬约束（本项目 3.2.58 全部落地）：

| # | 约束 | 为什么 |
|---|---|---|
| ① | **回读确认** | 不把存储读回来，"我以为清了"和"真清了"分不清 |
| ② | **必须警告"别全选"** | 清了记录后重跑，服务端已有的会被**重复建** |
| ③ | **任务在跑时不给清** | 否则正在跑的那批记不上账 → 制造新的幽灵 |
| ④ | **只清自己那一份，不许碰别的** | 本项目 `PLAY_DONE` 只管"要不要建 CSL"；碰了 `VIDEOS`/`UPLOADED_EVER` = 下次**重传视频**（不可逆） |

★★★★ 第 ④ 条是**作用域**那条规矩的复用：
"清空"要能回答"**清的是哪一份账**"。三份账各管各的：

| 存储 | 管什么 | 清了会怎样 |
|---|---|---|
| `VIDEOS` | 这一批传了什么 | 列表变空（正常） |
| `UPLOADED_EVER` | 历史上传过什么 | —— |
| `PLAY_DONE` | **要不要跳过建 CSL** | **已删的能重建（这是目的）** |

★★★ 验证方式（★ 这一版的重点）：这类"约束型"代码**最容易被假断言糊弄**
（"源码里有这句警告" ≠ "警告真会被说出来"）。
所以新加的 6 条测试**全用变异测试验过** —— 把源码故意改坏，看测试抓不抓得到：

```
playdone-clear-no-readback         ← 去掉回读
playdone-no-select-all-warning     ← 去掉"别全选"
playdone-clear-while-running       ← 允许运行中清
playdone-clear-ignores-cancel      ← 忽略取消
playdone-count-no-fallback         ← 计数兜底没了
playdone-clear-also-kills-videos   ← 顺手把 VIDEOS 也清了
```

**6 / 6 全被抓到** —— 约束才算真的存在。
→ 规矩：**给"不该做的事"写的约束，必须用变异测试证明它真的挡得住。**

### ★★★★★ 「对齐」比「清空」好：能对上账就别把账抹掉

2026-09-22 接着上面那条。「清空已建记录」上线后运营马上要的是下一步：
「你把已经创建的标记，然后没有在这 29 个的记录删了（除了我刚刚上传到 YouTube 的）」

★ 为什么"清空"只解决一半：清完之后面板**不再跳过任何条目**，
  而 Play 上已经建好的那些**还在**。他没有一份"Play 上到底有哪几个"的账
  → 要么不敢全选（漏掉该建的），要么全选（**重复建、烧配额**）。

**判据：能拿到"真实状态"的时候，要的是「对齐」，不是「清空」。**
清空是"我不知道，先全忘掉"，它把**正确的那部分**也一起忘了。

★★ 所以加了「按 Play 清单对齐」：把人给的名单对到记录上，三件事一起做 ——
  名单里的标成"已建" / 视频已删的废记录删掉 / 刚传的留着。

**名单必须人给。** 脚本看不到 Play 后台（没有 API），而"硬猜"会踩到另一件事：
**一个人故意只给部分视频建 CSL 是完全正常的用法**。
→ 拿到人给的东西之后，**第一件事是验它配不配得上**：
  **一条都配不上 = 大概率贴错表**（贴成别的产品、别的站、整份被改名），
  这时候下一步如果是"删掉不在名单里的"，就等于**把记录删光**。
  闸门要卡在**最前面**，不是等算完再检查。

★ 配对时两条踩过坑的规矩：
  · **允许"名字是前缀"** —— 真机上 Play 那边的 CSL 名会**少一截后缀**
    （人工建的时候改短了）。死按全等匹配 → 判成"Play 上没有" → **重复建**。
  · **但前缀必须唯一，而且全等优先于前缀** —— 一个名单项对上两个文件时
    谁也说不清是哪一个：挑错的那条会被当成"Play 上有"（**永远补不上**），
    没挑到的那条会被当成"没有"（**重复建**）。宁可报出来让人看。

★★★ 实测一条：9 个变异里有 **1 个第一次跑没被抓住** ——
  「`unknown` 当 `dead`」。原因是我只测了
  **`probeThumbAlive` 超时 → `unknown`**（直接调那个函数），
  却**没测**「调用方拿到 `unknown` 时怎么处置」——
  而变异改的正是调用方那一行，**那个测试根本走不到**。

  → 规矩：**测了"判据怎么产生"，还要测"判据被怎么用"。**
    三态判据（alive/dead/unknown）尤其容易漏 ——
    `unknown` 的**来源**不止一个（超时 / 根本没有值），
    而**处置**在另一段代码里。两边都要有用例。

### ★★★★★ 浏览器里问「还在吗」：`onerror` 分不清 404 和断网

★ 判据还是缩略图 `img.youtube.com/vi/<id>/default.jpg`（200 = 在 / 404 = 没了）。
  `tools/check-video-links.py` 用 urllib，**拿得到状态码**；
  但在**页面里**拿不到 —— 跨域（`no-cors` 是不透明响应，状态恒为 0）。

★★ `new Image()` 的 `onload/onerror` 不受 CORS 限制，**代价是丢掉了状态码**：
  `onerror` 既可能是 404、也可能是断网/超时，**两者在浏览器里长得一模一样**。

★★★ 后果是"整张表整齐地错"，而且**不报错**：
  一次 VPN 掉线 → 全部 `onerror` → 判成"视频全没了" → **记录被一口气删光**。

**规矩：判据的"可信度"本身也要有判据 —— 同屏放一个已知答案的对照组。**
先探一个**已知活着**的视频：
- 它 `onload` → 网络和判据都可用，可以往下
- 它失败 → 问题在网、不在视频，这次**全部判据不可信**
  → **整个停下，一条都不动**（不是"那就不删了吧"往下走 ——
   半做等于没说，用户看到一句"完成"就会按它理解数据）

★ 三态照旧，不许省：`alive` / `dead` / **`unknown`（超时、没有 videoId）**。
  `unknown` 一律**保留**并单独报出来。
  在这类功能里，"没问到"被当成"已失效" = **删掉用户的数据**。

★ 实现细节：`new Image()` 要**包一层**（本项目包成 `newThumbImage()`）——
  否则离线测试会**真的去请求 youtube.com**，用例结果就取决于
  "这台机器现在能不能上 YouTube"，那是最难查的一类红。

### ★★★★★ 删本地记录 ≠ 忘掉"传过它"

本项目里"删一条上传记录"很容易顺手写成"把这个文件名从所有地方去掉"。
**不能。** 两份数据管的是不同的事：

| 存储 | 管什么 | 删记录时 |
|---|---|---|
| `VIDEOS` | 这一批传了什么（Play 侧的视频列表靠它） | 可以删 |
| `UPLOADED_EVER` | 历史上传过什么（管"传没传过"） | **不许动** |

★ 名单一起没了 → 下次扫目录那个文件显示"没传过" →
  而「跳过已上传的」**默认开**，它以为自己跳过了什么、实际一个都没跳
  → **整批重传**（频道上多一份、额度不回收）。

★ 同理，"删"这种不可逆动作要跟"清空"用**同一套备份**（`pushVideoArchive` /
  `loadVideoBackup`），不要另开一套 —— 否则「恢复」按钮救不回这一步删的。

### ★★★★★ 后台标签页会把"慢"变成"失败" —— 而且**不留下任何证据**

同一个晚上，运营的另一问：
「是不是在自动化的时候不能把这个放在后台？我看报错都是我切了才有的」

★ **他的观察在机制上成立**，不是错觉：

| 标签页隐藏时长 | 定时器最小间隔 |
|---|---|
| < 10 秒 | 正常 |
| > 10 秒 | **1 秒** |
| > 5 分钟（intensive throttling） | **1 分钟** |
| 更久 | 可能被**冻结**（所有任务停止） |

★★ 而这类脚本的每一步都在 `waitFor` 里靠定时器轮询（`sleep(200)`）。
   所以后台的后果是：**页面早就准备好了，脚本还睡着** ——
   15 秒的窗口里可能一次都没轮到 → 报"等不到"。

★★★ 关键区分（**这两件事在日志里长得一模一样**）：

| | 前台 | 后台 |
|---|---|---|
| 上传本身 | 正常 | **也正常**（在服务端跑） |
| 脚本的判读 | 正常 | **可能误判成失败** |
| 修法 | 改选择器 / 页面结构 | 切回前台 |

**所以：切后台不会让上传失败，但会让脚本以为失败了。**

── 落地：防护 + **观测**，后者更重要 ──

★★★★ 查代码时发现最要紧的一件事：**这个信息原先根本没被记下来**。
  那条失败日志里，看不出当时标签页在不在前台 ——
  **所以事后无法判定**是不是后台造成的（写代码的人当时也判不了）。
  观测缺了，结论就只能靠猜。

所以要做四件：

1. `pageHiddenNow()` —— 能不能读到当前可见性
2. **报错里带上它**（`hiddenNote()`）—— 后台时说"先切回前台再重跑"
   ★ 前台时**返回空串**：把"你是不是切走了"挂在所有失败上，
     只会把每一次失败都往错方向引，还得怀疑这个提示本身准不准
3. **切走/切回当场记一行**（`visibilitychange`）
   ★ 不是等失败了才回头看 —— 那时标签页可能已经切回来了，**读到的状态是错的**
   ★ 只在任务**运行中**出声；平时切走切回不记（那是用户的事，记了只会稀释日志）
4. `waitFor` 后台时把等待窗口放宽（本项目放到 90 秒，够覆盖一次 1 分钟级的轮询）
   ★★★ **只放宽后台**。无条件放宽的话，所有真失败的反馈都被拖到 90 秒 ——
     而"失败了还要等"是日常最痛的地方。**放宽阈值这类改动，
     一定要问一句"它只对目标场景生效吗"。**

### ★★★ 给**公共函数**加依赖 = 给**所有组**加依赖

2026-09-20 实测的代价：`waitFor` 是测试 deps 里被最多组依赖的东西
（几十个组都切它）。给它加一个 `pageHiddenNow` 依赖 →

```
通过 1052  →  通过 345
报错：「异步用例抛异常：pageHiddenNow is not defined」
```

★ 组 9 一崩，后面几十组全不跑，而报错完全看不出跟可见性有关。

**处理方式：把这一族的兜底桩放进 `deps`，而不是去逐个组补名单。**

```js
// deps 里放兜底（默认值 = 改动前的行为，老断言语义一字不变）
pageHiddenNow: function () { return false; },
hiddenNote: function () { return ''; },
installVisibilityWatch: function () {},
// 非函数的东西（let/const）装不进 names，也只能在这儿兜底
hiddenWarned: false, visWatchInstalled: false, ARCHIVE_MAX: 5,
```

★ 要测真实行为的组把名字**切进** names 即可（`cut` 会跳过 deps 的 var 生成）。
★ 兜底值取"**改动前的行为**"很重要 —— 这样几十个老组的断言不用动。

★★★ 补充三条同一族的坑（本轮全撞了）：
  · **非函数常量**（`ARCHIVE_MAX` / `uploadIdxCache` / `uploadIdxAt`）
    切不进 names（`slice('ARCHIVE_MAX')` 找不到函数），只能进 deps
  · **返回值形状变了要连同锚点一起改**：`clearVideoRecords` 从返回数字
    改成返回对象 → 4 条旧变异预检失败。★ 改的是**锚点**，变异内容一字没变
  · **报错里对"我做了什么"的描述必须有代码保证**：本项目又一次抓到
    "报错写等了 30 秒、实际等了 45 秒"（`CONFIG.wait_timeout * 2`
    vs `wait_timeout + max(wait_timeout, 30000)`）

### ★★★★★ 文案串台的哨兵：判据要**常驻**，不能只在测试里

2026-09-21 实测。背景：这个脚本的 YouTube 标题/描述是**按产品写死的**，
运营手上三个产品（SLOT-01 / SLOT-02 / SLOT-04）
轮着用，所以要**来回切**。

**两天内切了一次（3.2.48 换 SLOT-01 → 3.2.54 换回 prod-b），踩到两个坑：**

| 坑 | 症状 |
|---|---|
| 哨兵写死成「不许出现 SLOT-02」 | 换回来时**哨兵自己变成错的** —— 它红，而读的人以为"改坏了" |
| 哨兵只在测试里 | 运营**不跑测试**，他改完文案就点开始了 |

**两条规矩：**

**① 禁忌名单要"算出来"，不要写死。**

```js
// CONFIG 里只配"当前是谁"+"我们做过哪些产品"
product_name: 'SLOT-02',
known_products: ['SLOT-02', 'SLOT-01',
                 'SLOT-04', 'SLOT-03'],

// 禁忌名单 = 全集 − 当前（算出来的）
const FORBIDDEN = known_products.filter(n => n !== product_name);
```

★ 这样换产品时只改 `product_name` 一行，哨兵自动跟着变。
★★ 通理：**凡是"跟当前状态相反"的名单，都不要写死** ——
   "另一个产品是谁"取决于"当前产品是谁"，写死任何一边都会在下次切换时失效。

**② 判据抽成源码函数，并接在**会被执行的路径**上。**

```js
function scanCopyProduct() { ... }    // 判据本体（纯函数，好测）
function logCopyProduct() { ... }     // 说出来（抽出来才能真跑）

// 开工时调一次（运营每天都会走到这里）
logCopyProduct();
```

★ 为什么不能只在测试里：**测试里的判据自己没人管**。
  本项目就撞过："描述必须含当前产品名"这条断言，
  对 SLOT-01 成立、对 prod-b **不成立**（prod-b 的描述里一个产品名都没有）——
  红的是产品文案，而不是判据。
★★ 这跟"报告函数要抽出来真跑"是同一族：
  **"源码里有这句话"和"这句话会被说出来"是两件事**。
  而且更进一步 —— **"功能写完了"和"功能被用上了"也是两件事**：
  抽了函数但忘了接调用点，删掉那一行是**静默**的（没有用例会红）。
  → 所以测试里还要有一条钉**调用点存在**的断言。

★★★ 输出的措辞也有讲究（`UNKNOWN ≠ SUCCESS` 的老规矩）：

| 情况 | 该说什么 |
|---|---|
| 对得上 | `· 这一批的标题/文案属于：**XXX**` |
| 串台 | `★★ 文案里出现的是「AAA」，而当前产品是「BBB」` —— **两边都要点出来** |
| 没配产品名 | `★ 没配 product_name —— **没法检查**`（不是"通过"）|
| 文案里没有任何已知产品名 | `★ 没有出现任何已知产品名` → "没法确认"≠"确认没问题" |
| 正常 | **什么都不许额外打**（否则这句提示会变成噪音）|

### ★★★★★ 从**频道侧**核验：三个通道，和一条"别用页面 HTML 计数"的坑

|---|---|---|
| 视频**还活着吗** | `youtube.com/oembed?url=…/watch?v=<ID>&format=json` | 200 在 / 404 没了 / 401·403 受限 |
| 频道**最近 15 条** | `youtube.com/feeds/videos.xml?channel_id=<UC…>` | videoId + 标题 + **逐字描述** |
| 频道 ID | 抓任一视频页，找 `"channelId":"UC…"` | —— |

★★★ **坑：别拿 watch 页面的 HTML 去数"某段文字出现了几次"。**
  同一段描述在页面里会出现 **3~4 份**（`<meta name="description">`、
  `og:description`、`ytInitialPlayerResponse` 的 JSON…），
  所以"`grep -o` 数到 2 次"**不能**推断"描述写了两遍"。

  **只有 RSS 的 `<media:description>` 是逐字原文**，量长短才作数
  （一个 `<entry>` 里就一个 `media:description`）。

★ 另：**网络可达性会变**。同一个工具 9/20 报"全问不到"、9/21 全正常 ——
  别把当时的网络状况写成结论（"没问到 ≠ 已失效"）。

### ★★★★★ 真实事故：**描述被写了两遍**（1517 字符 = 758 × 2）

2026-09-21 用上面那个 RSS 通道核出来的。

频道上最近 15 条**标题完全一样**（都是文案模板），但描述分成三种：

| 视频 | 描述长度 | 内容 | 判定 |
|---|---|---|---|
| 9/17 那批 6 条 | 1517 | prod-b × **2** | ★ 发出去时就这样 |
| 9/20 那批 9 条 | 1656 | **prod-b + SLOT-01** | ★ 手动加新文案时**没删旧的** |
| 9/20 早上补传那条 | 1517 | prod-b × 2 | ★ 同上 |

★★ **标题一样不代表内容一样** —— 那批视频从标题上看"全都对"，
   而描述里藏着两份文案。**这就是为什么核验要去量描述本身。**

★★★ 两个可迁移的教训：

1. **"回读对不上"必须带上方向。** 原来代码只报
   「填了 758 字，读回来 1517 字，但描述是选填的，继续」——
   读的人第一反应是**"没填上"**，而真相是**多了一份**。
   两种情况的处置**完全相反**：少了重填就行，多了得**先清空**（否则越填越多）。
   → 判据要有三个分支：变长 / 变短 / 同长但内容不同，
     而且**每种要说清"这意味着什么"**（变长 → 视频描述里会有两份文案）。

2. **手动编辑线上元数据，比重新上传更容易出事。**
   "在 Studio 里改一下"看起来最省事，但它是**没有判据的**
   （脚本至少还有回读核对）。要改就得连着**清空**一起做 ——
   而人复制粘贴时最容易只想着"贴上新的"。

### ★★★ 核对"某批文件传过没有"：只能靠**数量对账**，不能靠搜索

★★ 因为这类批量上传的**标题是模板**（所有视频标题一样），
  **描述里也不含文件名** —— 所以：
  · YouTube 站内搜索**搜不到**"这个文件传过没有"
  · 标题列表里也**分不出**哪个是哪个

**唯一可行的办法是三条互相印证：**

1. 本地记录里"活着"的有几条（体检）
2. 频道上**总共**有几条（人在 Studio 里数，或 RSS 给的最近 15 条）
3. RSS 里出现的那几条 videoId **能不能全部对上**本地记录

→ 三条对得上，才能说"没有来源不明的视频"。
★ 说结论时也要把这条推理链摆出来 —— 它**不是直接证据**，
  但它是"能拿到的最好的证据"，而读的人有权知道它是怎么来的。

### ★★★★★ 给"要照着复现的人（或 AI）"写技术文档：**先难点，再机制，最后流程**

2026-09-21 写《方法论》第 4 节时的返工。第一版按**操作顺序**写（第 0 步选目录、
第 1 步筛选、第 2 步上传……），被要求"技术流一点，带上代码，
目标是**他们的 AI 可以复现**"。

**两种写法的差别：**

| | 按操作顺序写 | 按"机制"写 |
|---|---|---|
| 读者得到 | "要做什么" | "**为什么必须这么做**" |
| 换一个页面 | 照抄步骤，**撞进同一个坑** | 能自己判断"我这边是不是同一个问题" |
| 对 AI 读者 | 会生成一份**看起来对、跑起来到处失败**的实现 | 能自己判断该不该用这套机制 |

★★★ **推荐的骨架：**

```
N.0  先摆清这一段要对付的 K 个难点
     ┌ 难点 ┃ 常规做法为什么不行 ┃ 本方案的做法 ┐     ← 一张表
N.1  环境与前置
N.2  ★ 底层机制（核心，每个机制：一段代码 + 它解决什么问题 + 踩过的坑）
     N.2.1 …  N.2.2 …  N.2.3 …
N.3  主流程（表里加一列"用到 N.2 的哪个机制"）
N.4  边界与批次控制
N.5  数据/记账
```

★ 那张"难点表"是**整篇里性价比最高的部分**：它让读者在动手之前就知道
**这条路为什么只能这么走**。缺了它，读者会用自己的直觉实现，
然后在那些坑里一个一个撞回来。

★★ 每个机制都要写清**"不这么做会怎样"**（具体的失效现象），而不只是"这么做"。
例：`collectRoots` 里那个 `el.isConnected` —— 不写它的后果是
"选得中但没反应、**不报错**、一路卡到超时"。这种细节写出来，
读者才知道**这行不能省**。

### ★★★★★ 文档里的代码是**交付物**，但没有东西会报错 —— 必须单独检查

同一个返工里意识到的：

```

★★ 为什么必须有：这份文档**是给 AI 读的，而 AI 会直接复制里面的代码**。

| | 产品代码 | 文档里的代码 |
|---|---|---|
| 会不会被 import | 会 | **不会** |
| 会不会被跑 | 会 | **不会** |
| 有没有用例覆盖 | 有 | **没有** |
| 改坏了会怎样 | 红 | **什么都不发生** |

### ★★★★★ 「失败了会天然被补上」≠「用户知道有东西要补」

2026-09-21。运营问：「我今天上传了 11 个视频为什么就生成 10 个 csl」+
「**记得把舍弃的那个上传**」。

★ 查完数据后发现：**功能上它本来就会被补上** ——
  失败的那条不记账，所以它不在任何成功记录里，
  「跳过已上传的」不会拦它，下次勾上就会被传。
  **但用户不知道这些**：他手里只剩"好像有一条没传"这种印象。

★★ 而这条印象的代价是**整批重跑一遍** —— 那才是真的浪费。

**通理：一个"沉默地做对了"的机制，跟"没做"在使用者眼里是一样的。**

具体做法（这套形状可以照搬到别的地方）：

| 要素 | 做法 |
|---|---|
| **持久化待办** | 失败时写一份**名单**（不能只在内存里/日志里） |
| **面板上常驻显示** | 一直挂着「待补 N 条（文件名…）」—— 不是弹一次就没了 |
| **一键带上** | 「只勾待补的」：把名单跟当前队列按**文件名**配对，一次勾好 |
| **说清为什么不会漏** | 日志里写"它们没记账，所以「跳过已上传」拦不住" —— 这是**依据**，不是安慰 |
| **补完要划掉** | 否则用户会一遍遍重传同一批（而这是他最怕的事） |

★★★ 还有一条容易漏的：**要把"当时的状态"一起存下来。**
本项目存了 `hidden`（失败时标签页在不在后台）——
它是判断"这次失败是误判还是真失败"的**唯一依据**，
而**事后采不到**（那时标签页早切回来了）。
→ 规矩：**凡是"事后无法复现的现场信息"，必须在事件发生的那一刻存下来。**

### ★★★★★ 桩没接上的时候，测试**可能照样全绿**

同一个晚上抓到的，值得单独一节。

**现象**：`selectPendingOnly` 的 6 条断言全红，原因是被测函数读到的
`ytState.entries` 是**空的**（源码真身），而不是我塞进 `deps` 的那个桩。

**机制**（`makeEnv` 的实现决定的）：

```js
const setup = Object.keys(deps).filter(k => !cut[k])
    .map(k => 'var ' + k + ' = deps[' + JSON.stringify(k) + '];').join('\n');
```

→ `cut` 就是"切进 names 的那些"。
  **切进 names 的名字不会生成 `var X = deps.X`**，
  于是那些名字用的是 `slice()` 拉出来的**源码真身** —— 桩等于没写。

★★★ **最阴的地方：桩没生效时，测试不一定红。**

本项目的实证：组 28 里有一条

```js
const ytStateStub = { running: false };
deps.ytState = ytStateStub;
const env = makeEnv([..., 'ytState', ...]);   // ← 切了，桩失效
```

而它**一直是绿的** —— 因为真身的 `ytState.running` 默认也是 `false`，
跟桩值**恰好一样**。也就是说：

| | 桩生效 | 桩没生效 |
|---|---|---|
| 桩值 ≠ 真身默认值 | 测到的是桩 ✓ | **红**（能发现） |
| 桩值 = 真身默认值 | 测到的是桩 ✓ | **绿**（发现不了，也**没测到东西**） |

→ **第三列是最坏的**：它不但没测到，还给出了一个"通过"的假象。

**两条规矩：**

1. **能用 deps 桩的，就别把它切进 names。**
2. 桩的取值**故意取一个跟真身默认值不一样的值** ——
   这样"桩没接上"会**当场红**，而不是伪装成通过。
   （例：真身 `running` 默认 false，桩就取 true。）

★★ 这一条跟"给公共函数加依赖 = 给所有组加依赖"是同一族问题的两端：
  前者是**缺依赖**（红得莫名其妙），后者是**桩没生效**（绿得莫名其妙）。
  **后者更难查** —— 红至少会有人看。

2026-09-21。3.2.56 把"后台把等待窗口放宽到 90 秒"换成了

### ★★★ 两个"兜底型改动"必须配真实时长上限

同一个改动的另一面。`waitFor` 那条：

+ hidden_grace_ms 真实时长兜底  ← 防的是"永远在后台 + 页面真坏了 → 永远等下去"
```

★★ **两条必须一起做**：只有前者 → 那种情况会**永远等下去**，

★★ 更一般：**凡是"要等很久才发生"的兜底，都要能在测试里按掉**，

### ★★ 造假时钟的桩必须**能当构造函数用**

2026-09-21 踩的。为了精确验证"后台时间不计入预算"，把 `Date` 换成了桩：

→ 走到任何打日志的路径就报：

```

```

★ 因为 `log()` 里是 `new Date()`。
★ 而这个报错**看起来像"源码写错了"**，跟"我换了个假时钟"完全联系不上。

### ★★★★★ 「**不该做**的那件事没做」——验不了返回值，只能**数次数**

2026-09-21 实测漏网的一条变异。

**被守的代码：**

```js
function removePending(fileNames) {
    const cur = loadPending();
    const out = cur.filter(x => !names[x.fileName]);
    const removed = cur.length - out.length;
    if (removed > 0) storeSet(STORE.PENDING, out);   // ★ 没命中就不写
    return removed;
}
```

**变异：** 去掉那个 `if`，改成无条件 `storeSet(STORE.PENDING, out)`。

**而用例是这样断言的：**

```js
eq(env29.removePending(['zzz.mp4']), 0,
    '★★★★ 没命中时返回 0 而且**不写存储** —— …');
```

→ **返回值一样是 0** → 断言照样绿 → **变异没被抓住**。

★★★ 问题在于：这条断言的**文案**说了两件事
（"返回 0" + "不写存储"），而**代码只验了第一件**。
第二件（"不该做的事没做"）**根本不体现在返回值上**。

**修法：数次数。**

```js
let writeCount = 0;
deps.GM_setValue = function (k, v) { writeCount += 1; store[k] = v; };

let w0 = writeCount;
eq(env.removePending(['a.mp4']), 1, '划掉 1 条');
eq(writeCount - w0, 1, '★ 真划掉了 → **写一次**（该写的必须写）');

w0 = writeCount;
eq(env.removePending(['zzz.mp4']), 0, '没命中 → 返回 0');
eq(writeCount - w0, 0, '★★★★★ 而且**一次存储都不许写**');
```

**这类"不该做的事"有一整族**（本项目里出现过的）：

| 守卫 | 返回值看得出来吗 | 要数什么 |
|---|---|---|
| 没命中就不写存储 | ❌ 看不出来 | 写入次数 |
| 空清单不打日志 | ❌ 看不出来 | 日志条数 |
| 前台不追加"你是不是切走了" | ❌ 看不出来 | 日志/字符串 |
| 后台提醒只打一次 | ⚠️ 打两次也不报错 | 匹配条数 |
| 同一个文件不重复记 | ⚠️ 读回来可能一样长 | 条目数 |
| 不重复挂监听器 | ❌ 看不出来 | 监听器个数 |

★★ 通理：**断言里写了几件事，就要验几件事。**
  写了"而且不写存储"却只验返回值 —— 那句文案是**装饰**，
  而它会给人"这条已经守住了"的错觉（比没写还糟）。

★★★ 顺带一条更一般的自查：
  **变异没被抓住时，第一反应不该是"再加一条用例"，而是先问
  "我原来那条断言，文案里承诺的东西都真的验了吗"。**
  本条就是这么发现的 —— 用例一直在那儿，一直绿，一直没在防它。

### ★★★★★ 「成功了一半」怎么记账：**「发出去了」比「有没有链接」更重要**

2026-09-21 咬到人的一个真洞（同一段代码的注释**自己预言过**它）。

**现场**：某条视频**标题描述了都填对了、也发布成功了**
（频道 RSS 里能看到它，描述长度正好等于模板），
但脚本在"取视频链接"这一步读不到 id → `throw` → 整条判失败 → **不记账**。

**三条后果**：

1. 面板不显示"已上传"
2. 下游（Play 侧）不给它建页面 —— 用户看到的是"11 个视频只建了 10 个"
3. ★★★ **下次跑会把它再传一份** —— 频道上多一条几乎一样的，**不可逆**

**而那段代码上面就写着**：

> 拿不到 id 不等于失败：视频其实已经传上去了…
> 记成 failed 会造成两件坏事：用户以为视频丢了；
> **下次跑的时候会把这条当成"没传过"而重复上传，白扣一遍配额。**

★ 也就是说：**注释早就写对了，代码做反了。**

**判据（可迁移）**：当一个动作**部分成功**时（发出去了、但没拿到回执），
要按"**哪一半更不可逆**"来选：

| 选择 | 后果 | 可逆吗 |
|---|---|---|
| 记一条不完整的账（链接为空） | 下游拿不到链接，会跳过它并**明说** | ✅ 补一下就好 |
| **不记账** | 下次跑**重传一份** | ❌ **不可逆** |

→ **记一条不完整的账**。

★★ 配套的两件事，少一件这个决定就站不住：

1. **下游必须能识别"不完整的记录"**并明确跳过 + 报出来。
   本项目 Play 侧从 3.2.44 起就有这道过滤（`src` 里要求 `r.videoId`），
   而且会把它们列进"**勾了、但没有视频链接**"那一条里说清楚。
   ★ 没有这个，改完就是把坏数据灌给下游。
2. **日志要说清"它已经发出去了"**，否则用户看到"没拿到链接"会以为"那就是没传成"。

★★★ 还有一条更一般的：**这类"注释说对了但代码做反了"的地方，
   往往是"后来有人加了条件分支"改出来的** ——
   改动时只想着新分支要什么，没回头看上面那段话还成不成立。
   → 改条件分支时，**回头读一遍那段注释**，问一句"它还成立吗"。

### ★★★★ 白名单式过滤：新加的字段会被**静默丢掉**

2026-09-21 被用例当场抓到的。

```js
function saveVideos(list) {
    const clean = (list || []).map(function (r) {
        return {                                   // ← 白名单：只留列出来的
            relPath: r.relPath, fileName: r.fileName, size: r.size,
            title: r.title, videoId: r.videoId || null, url: r.url || null,
            state: r.state, at: r.at,
        };
    });
    storeSet(STORE.VIDEOS, clean);
}
```

新加了一个字段（`manual: true`，标记"这条是手动补录的"）→
**没有报错、没有警告，读回来是 `undefined`**。

★★ 这个形状（`saveVideos` 这种"进存储前先洗一遍"）**本身是对的**
（它挡的是 `File` 对象那种不能序列化的东西 —— 放进去会静默变成 `{}`），
但它的代价是：**新字段必须被显式加进白名单**，漏了就无声消失。

**判据**：往这种"白名单收口"的地方加字段时，
**必须有一条用例真的读回来验那个字段**。
★ 只有"写进去了"是不够的 —— 本项目这条用例恰好验了 `rec[0].manual === true`，
  才抓到它。如果当时只验"记录条数 +1"，就漏过去了。

### ★★ 输入框什么时候该清：**成功才清，失败留着**

小但很影响手感的一条（2026-09-21）。

```
补录：  [ 文件名 ]  [ 链接 ]  [补录]
```

- **成功** → 清空两个框（方便接着补下一条）
- **失败** → **留着**（他要改一个字重试 —— 清掉的话那条长链接得重新复制一遍）

★★ 判据：**"用户下一步要做什么"决定清不清。**
  成功了下一步是"再补一条"（清空有用）；
  失败了下一步是"改一下重来"（清空有害）。

★ 同类的地方（本项目还有）：`标题/描述` 的输入、批量清单的多行框 ——
  都是"填错一个字符要重来"的场景。

### ★★★★★ 删功能：**连数据键、配置项、选择器一起删**，而且断言要**反过来写**

2026-09-22。运营一句「受众网址这个功能可以删除了」，删掉的是整个
「受众 = 网址」分支。记下来的是**删的过程**比删的代码更容易出错。

**为什么留着那条路不是中立的**（这是"该删"的理由，不是"顺手清理"）：

```
面板下拉选的值存在内存里（不持久化）
        ↓
每次刷新页面都按配置重新初始化 → 下拉可能自己跳回「网址」
        ↓
而网址框是空的
        ↓
if (!task.audienceUrl) throw StepError('…受众网址是空的…')
        ↓
一次都不点就整条失败 —— 错误信息还把人指向一个"根本不打算填"的框
```

★ 判据：**一条路如果只会通向一个坏状态，它就不该留在界面上。**
  不是"留着以后可能有用" —— 留着的代价是它会**主动**制造那个坏状态。

★★ **删的清单**（少删一样就等于没删干净）：

| 类别 | 例子 |
|---|---|
| 面板控件 | 下拉、输入框、它们的容器块 |
| 内存字段 | 面板选值用的那两三个 |
| 选择器配置 | 那条路专用的（通常配成 `null`） |
| 普通配置 | 那条路的清单（如 `xxx_urls: []`） |
| **存储键** | 那条路的历史数据（**不主动清**，见下） |
| 纯函数 | 只服务那条路的工具函数（清单解析 / 队列 / 分配） |
| 分支代码 | 主流程里的 `if (mode === ...)` |

★ **旧存储键不要去主动清**：它已经没有读者，去清要写一次存储、
  还得处理"写失败"。留着的代价只是几十字节。

★★★ **测试这边有两个坑，都很难自查**：

1. **假绿**。代码删了、用例还在测它，而用例读到的全是 `undefined`，
   于是**照样通过**。→ 删用例时**留一段注释说明删了什么、为什么**，
   不要让它凭空消失（下一个来看的人会找不到）。
2. **该反过来写的断言**。原来写"默认值必须是 A 或 B"的，
   现在要写"默认值必须是 A"；原来写"这个键要在"的，
   现在要写"这个键**不许**在"。**方向不翻，等于没测。**

★★★★ **必须有源码级的守护**（只读配置的断言看不见"控件被加回来"）：

```
eq(CONFIG.play.audience, 'ads')                       ← 只剩一条路
ok(!/audienceSel/.test(SRC))                          ← 面板控件不许回来
ok(!/…play_url_used/.test(storeSrc))                  ← 存储键不许回来
ok(!/function\s+(a|b|c)\s*\(/.test(SRC))              ← 工具函数不许回来
```

★★★★★ **变异要连锚点一起删**。守那条路的变异，`find` 锚点在源码里
已经不存在了 —— 留着的话工具会**报错退出**（"替换目标找不到"）。
那不是 bug，是刻意的：**宁可就地炸，不许静默变成"什么都没改"**。
（本项目这次删了 5 条变异，每条都确认过锚点确实没了才删。）
★ 但**别把所有相关变异都删掉**：有一条（"把默认路改回去"）改改描述
  就能继续守新判据 —— 检查一遍再决定。
