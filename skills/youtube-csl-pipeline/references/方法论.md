# YouTube 批量上传 + Google Play 自定义商店页（CSL）自动化 · 方法论

---

## 0. 一句话结论

**这条流水线不用任何官方 API，而是用一个浏览器脚本，替人在 YouTube Studio 和  
Play Console 的页面上操作。**

绕开的不是技术难度，是**两个平台的规则**：

| 环节        | 官方 API 的情况                       |
| --------- | -------------------------------- |
| 建 CSL     | **根本没有 API** —— 只能操作 Console 页面  |
| 传 YouTube | 有 API，但**未过审的项目传上去只能是"私享"**，等于白传 |

---

## 1. 要解决的问题

日常要重复做两件手工活：

1. **把上百条视频素材传到 YouTube** —— 每条要填同一个标题、同一份长描述、  
   选缩略图、设受众、设可见性、发布。**单条几十秒，上百条就是两个多小时**，  
   而且**手滑一次就是"发了条标题错的视频"**（收不回来）。
2. **在 Play Console 里为这些视频逐条建 CSL** —— 四步向导、每步都要选下拉、  
   填链接、勾选项。每条**烧一份不可回收的配额**。

目标：两段都变成"点一次开始，然后看着它跑"。

---

## 2. ★ 为什么不用 API

### 2.1 Play 侧：**CSL 压根没有 API**

**Google Play Developer API（`androidpublisher` v3）不包含 CSL 资源。**

- `edits.listings` 只有**语言维度** —— 它管的是**默认商店页**，  
  不是"按国家 / 广告系列 / 安装状态定向"的那些替代页
- fastlane 官方（2026-06 核对）明确答复：Developer API 不暴露 CSL 和商店页实验，  
  `supply` 只能更新默认页
- 2026-07 的 API 变更清单里没有 CSL 相关方法

> **也就是说：无论用什么技术，"用接口批量建 CSL"这件事做不到。**  
> 任何声称能全自动的服务商，实际都绕不开 Play Console 后台。

**所以 Play 这一段，从第一天起就只剩"操作页面"一条路。**

★ 附带一条流程事实：CSL 提交后**要过平台审核**（通常 1–3 天）才生效 ——  
这是平台侧的，不因为自动化而改变。

### 2.2 YouTube 侧：**API 能传，但传上去发不出去**

这一段最容易被误解 —— YouTube Data API **确实有上传接口**（`videos.insert`）。  
真正的障碍是这条**官方政策**（2026-09 核对原文）：

> *"All videos uploaded using the `videos.insert` endpoint from unverified API  
> projects created after 28 July 2020 will be restricted to **private** viewing  
> mode. To lift this restriction, each API project must undergo an  
> **audit** to verify compliance with the Terms of Service."*

**翻译成业务语言：**

- 用 API 传，视频会**强制变成"私享"**
- **不是"传完再改成公开"就行** —— 未过审项目下，**API 改不了、Studio 里也改不了**
- 要解除，得让这个 API 项目**通过 YouTube API Compliance Audit**

**★ 这直接判了死刑**：CSL 需要一个**能公开访问的预览视频**，  
一条私享视频放进去毫无意义 —— 而这条流水线的**全部产出就是"一堆能用的视频链接"**。

### 2.3 而且审核是**两道**，不是一道

| 审查                               | 管什么           | 谁需要                                         |
| -------------------------------- | ------------- | ------------------------------------------- |
| **OAuth 验证**                     | 同意屏幕、能有多少用户授权 | `youtube.upload` 是 **Restricted scope**，必须过 |
| **YouTube API Compliance Audit** | 上传的视频能不能不是私享  | 所有 2020-07-28 后创建的项目                        |

★ 这两道**互相独立、都要过**，而人们常把它们混为一谈。  
★ 官方**没有公布审核周期** —— 按"以周计"准备比较现实。

**对一个内部运营工具来说，为了批量传视频去走平台的两道开发者审核，  
投入产出完全不成比例** —— 而且还不保证过。

### 2.4 顺带说清两个容易被旧资料误导的点

**① "API 配额不够"这个理由，现在已经不成立了。**

| 时间         | 变化                                           |
| ---------- | -------------------------------------------- |
| 2025-12-04 | `videos.insert` 从约 **1600 单位**降到约 **100 单位** |
| 2026-06-01 | 上传进入**独立 bucket：每天 100 次**                   |

→ 一次传几十个视频，**配额完全够**。  
网上大量文章仍写"每天只能传 6 个"（那是 2025-12 之前的数字）。  
**别拿配额当理由** —— 真正的理由是 2.2 那条"强制私享"。

**② API 还有两个"能力缺口"，即使过了审也补不上：**

| 要做的事                   | 脚本（操作页面）         | API                                          |
| ---------------------- | ---------------- | -------------------------------------------- |
| **缩略图：从平台自动生成的截图里挑一张** | ✅ 能              | ❌ 缩略图接口只能**上传一张自定义图**，**没有"从自动生成的那几张里选"的方法** |
| **判断这条会不会被判成 Short**   | ✅ 能从对话框里的链接形态看出来 | ❌ 由平台自动判定，上传前拿不到                             |

**③ 运维成本也不一样：**

|    | API                           | 脚本                   |
| -- | ----------------------------- | -------------------- |
| 前置 | 建云项目、开 API、配 OAuth 同意屏幕、走两道审核 | 装个脚本                 |
| 凭据 | 管 refresh token、过期续期          | **用浏览器里已有的登录态，没有凭据** |
| 网络 | 要给服务器配出口                      | 用你本机的网络              |
| 排查 | 看 HTTP 状态码和配额仪表盘              | **看它自己打的日志（有现场）**    |

### 2.5 为什么连 Playwright 也不用

同一类问题的另一面（2026-09 实测定论）。

两条理由，任一条都足以定案：

1. **登录。** 脚本跑在**用户已登录的页面**里 —— 登录这个问题根本不存在。  
   Playwright 要另起浏览器会话，实测**四条登录路线全部失败**。
2. **读本地素材目录。** `window.showDirectoryPicker()` **只有页面上下文能调用**；  
   Playwright 调它会弹出操作系统原生对话框，程序点不了。  
   而"批量上传素材"必须先拿到本地文件。

### 2.6 一句话概括整个选型

> **API 自动化** = 以"**第三方应用**"的身份去操作 → 要过平台的开发者审核。  
> **脚本自动化** = 替"**用户本人**"操作 → 就是用户自己在点，**没有第三方**。

后者天然不在那些规则的范围里。这不是钻空子 —— 用户本来就有权在  
自己已登录的页面上做这些操作，脚本只是**替他更快、更准地做**。

## 3. 方案总览

### 3.1 两个面板，一份共享数据

脚本挂在两个站点，各自一个面板：

| 站点             | 面板      | 干什么                    |
| -------------- | ------- | ---------------------- |
| YouTube Studio | 右上角（可拖） | 选目录 → 批量上传 → 填元数据 → 发布 |
| Play Console   | 右上角（可拖） | 读记录 → 批量走 CSL 四步向导     |

**两侧靠浏览器存储里一份"素材 → 链接"的对照表通信** —— 它是两段流水线之间唯一的桥：

```
上传侧                                建页侧
──────────                            ──────────
传完一条 → 写一条记录                   读这份记录 →
  { 文件名, 视频 id,                     · 用**文件名**配对（建页时的「参考名称」就是它）
    链接, 状态, 时间 }                    · 用**链接**填「视频链接」那一栏
        ↓                                      ↓
   存进共享存储  ─────────────────────→   给每条建一个 CSL
```

★★ **为什么配对键是"文件名"**：

- 标题是**模板**（所有视频一个样），配不了
- 相对路径会随"这次选了哪一层目录"变化
- **文件名跨批次稳定**，而且建页侧的「参考名称」本来就用它

### 3.2 存储键一览

| 键        | 作用                         |
| -------- | -------------------------- |
| `<视频记录>` | **上传记录**（文件名 → 链接）—— 两侧的桥  |
| `<永久名单>` | **历史上传过的文件名**（只增不减，归档也不清）  |
| `<归档栈>`  | 归档备份（留最近 5 份）              |
| `<已建记录>` | 建页侧自己的一份"这版建过没有"（按**文件名**） |
| `<表单记忆>` | 可见性、受众等选项的记忆               |
| `<面板位置>` | 面板被拖到哪儿了（两个站点各一份）          |

★ 早先还有一份「已用过的受众网址」（建页侧一度支持"依次填不同的网址"）。
**那条路后来被整个删掉了** —— 受众固定走「广告流量」，于是那份键、
配套的两个选择器和整个网址池（清单解析 / 队列 / 分配）一起没了。

★★ **这次删除留下的一条规矩**：删一个功能时，要**连它的数据键和配置项
一起删**。留一个没有读者的键**不会报错**，只会让下一个人以为"还能切回去"，
然后去补一个已经删掉的输入框 —— 而那个输入框一旦回来，
就会带回一条"选错一项、一次都不点就整条失败"的路。
测试里那条断言也**反过来写**了（`ok(!/…play_url_used/.test(storeSrc))`）：
"删干净"才是这一步的要求。

★ **「视频记录」和「已建记录」为什么要分开**：前者存的是上传侧的  
**视频标题**（"这批传了什么"），后者要存**素材文件名**（"这版建没建过"）。  
这两样在真实数据里就是不一样的 —— 标题可以改、文件名不会。  
混用会出现"标题一样但文件不同"被误跳过。

## 4. 第一段：批量上传（详细 · 可复现）

> **这一节的定位**：面向"要照着做一个同样的东西"的人（或 AI）。
> 代码是从实际在跑的脚本里摘出来的，去掉了业务相关的部分，**保留了机制本身**。
> ★ 文中出现的 `<...>` 一律是占位符（不写具体产品名 / 文件名），不是漏写。

### 4.0 先摆清：这一段要对付的 7 个技术难点

| # | 难点 | 常规做法为什么不行 | 本方案的做法 |
|---|------|------------------|-------------|
| 1 | 目标元素在 **shadow DOM** 里 | `querySelector` **不跨 shadow 边界** —— 选择器怎么写都选不中（这是规范，不是写法问题） | 自己实现穿透查询：先收集全部可达的 shadow root，再逐层查；跨边界用 `>>>` **显式**表达 |
| 2 | **没有"选文件"的 API** | 浏览器安全模型不允许脚本打开系统文件框 | 用 `DataTransfer` 构造 `FileList`，**直接赋给 `input.files`**，再补发 `change` |
| 3 | 标题/描述框是 **contenteditable 的 `div`**，不是 `<input>` | 对它调 `HTMLInputElement` 的 value setter 会**当场抛 TypeError**（原生 setter 检查接收者的内部槽） | 三路分支：`input` / `textarea` / `contenteditable` 各走各的 |
| 4 | 框架（React / Polymer）有**内部状态** | `el.value = x` 绕过框架的 setter → **界面看得见、提交上去是空的** | 调**原生 prototype 上的 value setter**，再补发 `input` / `change` |
| 5 | 同一条流程，**第 1 条能跑通、第 2 条跑不通** | —— | 四级事件序列依次试 + 用"**浮层容器在不在文档里**"当分水岭 |
| 6 | 页面状态是**异步**的 | 点完立刻查必然查不到 | 统一走 200ms 轮询；判据只要**正面证据**，不要"没读到反证" |
| 7 | 全流程**不可回退**（上传配额扣了不返还） | 出错才发现就晚了 | 每个写操作后面跟一次**回读核对** |

第 1、2、4 条是**这个方案能成立的前提** —— 缺任何一条，整条路都走不通。  
第 5、6、7 条决定了它**稳不稳**。

### 4.1 环境与前置

| 项 | 要求 | 为什么 |
|---|------|-------|
| 浏览器 | Chrome / Edge（要有 `showDirectoryPicker`） | 拿目录句柄，才能递归扫 + 拿到 `File` 对象 |
| 运行形式 | 用户脚本（油猴类）注入到平台的已登录页面 | 复用用户自己的登录态（见第 2 节：这正是绕开 API 审核的原因） |
| 登录 | 已在目标的创作后台登录对应账号 | —— |
| 素材 | 本地目录，**可以带子目录**（会递归扫） | —— |
| 标签页 | ★ **跑的时候留在前台** | 后台会被浏览器**节流定时器** → 轮询睡着 → 把"慢"误报成"失败"。详见 4.2.5 |

### 4.2 六个底层机制（★ 复现的核心）

下面六个函数是整条流水线的地基。**把它们先跑通，剩下的都是编排。**

#### 4.2.1 选目录 + 递归扫描

```js
async function pickVideoDirectory() {
    const win = typeof unsafeWindow !== 'undefined' ? unsafeWindow : window;
    if (typeof win.showDirectoryPicker !== 'function') {
        throw new Error('这个浏览器不支持 showDirectoryPicker，请用 Chrome 或 Edge');
    }
    return await win.showDirectoryPicker();
}
```

```js
/**
 * 递归扫描目录，返回 [{ relPath, fileName, file, size }]
 * ★ file 是浏览器 File 对象，只在当前页面会话里活着。
 */
async function scanDirectory(dirHandle, cfg) {
    const out = [];

    async function walk(handle, prefix, depth) {
        const names = [];

        for await (const [name, child] of handle.entries()) {
            if (child.kind === 'directory') {
                // ★ 深度封顶：防目录环（软链接指回上层）
                if (cfg.recursive && depth < 6) names.push({ name: name, dir: true });
                continue;
            }
            if (!isVideoFile(name, cfg.video_ext)) continue;
            names.push({ name: name, dir: false });
        }

        // ★ 自然序：01 / 02 / 10 —— 不加 numeric 的话 10 会排在 2 前面
        names.sort(function (a, b) {
            return String(a.name).localeCompare(String(b.name), undefined,
                { numeric: true, sensitivity: 'base' });
        });

        for (const item of names) {
            if (item.dir) {
                let child;
                try { child = await handle.getDirectoryHandle(item.name); }
                catch (e) { continue; }          // 权限/损坏目录：跳过，不炸整趟
                await walk(child, prefix + item.name + '/', depth + 1);
                continue;
            }

            let file;
            try {
                const fh = await handle.getFileHandle(item.name);
                file = await fh.getFile();
            } catch (e) { continue; }

            out.push({
                relPath: prefix + item.name,   // 含子目录 —— 筛选按它匹配
                fileName: item.name,           // ★ 配对键
                file: file,                    // ★ 原样搬运，绝不重建
                size: file.size,
            });
        }
    }

    await walk(dirHandle, '', 0);
    return out;
}
```

**★ 三条必须记住的：**

1. **`file` 对象不能丢、不能重建。** 曾经有个版本在"建队列"时只挑了 `relPath / fileName / title / skip` 四个字段重新构造对象 ——  
   **`File` 就在那一步被吃掉了**，后面投文件时收到的是 `undefined`。  
   报错出现在几百行之外，像是"页面不接受注入"，实际是**自己把数据搞丢了**。  
   → 队列是纯内存的（从不持久化），**带 `File` 是安全的**。

2. **选完目录后不要刷新页面。** 句柄只活在当前页面会话；刷新之后 `getFile()` 会失败。  
   （表现为：列表还在，但每个文件旁边标着 `File ✗`。）

3. **`relPath` 要带子目录。** 素材通常按主题分子目录，而主题词常常**只在目录名里、不在文件名里**。  
   只按文件名筛选，那些词一个都筛不出来。

#### 4.2.2 穿透 shadow DOM 的查询

```js
/** 收集一个 root 及其内部所有可达的 shadow root */
function collectRoots(root) {
    const r = root || document;
    const out = [r];
    const seen = new Set();

    (function walk(node) {
        let all;
        try { all = node.querySelectorAll('*'); } catch (e) { return; }
        for (const el of all) {
            let sr = null;
            try { sr = el.shadowRoot; } catch (e) { continue; }
            // ★ isConnected 是必须的 —— 见下面
            if (sr && el.isConnected && !seen.has(sr)) {
                seen.add(sr);
                out.push(sr);
                walk(sr);          // 递归：shadow root 里还能再有 shadow root
            }
        }
    })(r);

    return out;
}
```

★★ **`el.isConnected` 这一条不能省。**  
脱离文档的 shadow root 照样能 `querySelector` 出元素 —— 但那些是**死节点**：  
对它们 `click()`、赋值、派事件**全部毫无反应**。  
这种"**选得中但没反应**"是最难查的一类故障：**不报错**，就是一路卡到超时。

```js
let rootsCacheAt = 0;
let rootsCacheVal = null;

/** 遍历全文档找 shadow root 是有成本的，而轮询是 200ms 一轮 */
function cachedRoots() {
    const now = Date.now();
    if (rootsCacheVal && now - rootsCacheAt < 300) return rootsCacheVal;
    rootsCacheVal = collectRoots(document);
    rootsCacheAt = now;
    return rootsCacheVal;
}

/**
 * 穿透 shadow DOM 的 querySelectorAll。
 * 跨边界语法：`a >>> b` = 先在整页找 a，再进它的 shadowRoot 找 b。
 */
function deepQueryAll(selector, scope) {
    const out = [];
    const parts = String(selector || '').trim().split(/\s*>>>\s*/);
    if (!parts[0]) return out;

    // 第一段：在每个根里查
    let current = [];
    for (const r of (scope ? collectRoots(scope) : cachedRoots())) {
        let hits = null;
        try { hits = r.querySelectorAll(parts[0]); } catch (e) { continue; }
        for (const n of hits) current.push(n);
    }

    // 后续段：只在上一段命中的元素的 shadowRoot 里查
    for (let i = 1; i < parts.length; i += 1) {
        const next = [];
        for (const host of current) {
            const sr = host.shadowRoot;
            if (!sr) continue;
            let hits = null;
            try { hits = sr.querySelectorAll(parts[i]); } catch (e) { continue; }
            for (const n of hits) next.push(n);
        }
        current = next;
    }

    for (const n of current) out.push(n);
    return out;
}

function safeDeepAll(selector) {
    try { return deepQueryAll(selector); } catch (e) { return []; }
}
```

★★★ **为什么必须自己写这两个函数：**

- **CSS 选择器不跨 shadow 边界。** 一条普通选择器无论怎么写都选不中 shadow root 里的元素。  
  所以"跨边界"必须**显式表达**（`>>>`，和 Chrome DevTools 控制台里同一个意思），  
  让查找**分两段走**。
- **同一个选择器可能命中多个根里的多个元素。**  
  所以查完之后要**打分选优**，而不是"取第一个"。
  打分维度至少要有：**可见性 / 是否在文档里 / 有没有尺寸 / 是不是自己插进去的**。  
  ★ 最后那条容易被忽略 —— **脚本自己的面板也是页面的一部分**，  
  如果面板里恰好有个同名元素，它会被选进来（而点它毫无反应）。

#### 4.2.3 一个按钮，四种打法

**背景**：有些组件的"打开"行为不是绑在 `click` 上，而是绑在 `pointerdown` / `mousedown` 上；  
还有些组件"按下时打开、又被同一串里那记冒泡的 `click` 关掉"（"点到外面就关"那种监听器）。

所以准备**四套事件序列**，从"最像真人"到"最不打扰"：

```js
const MOUSE_SEQ = {
    // ① 整条链（默认，最接近真实用户）
    full: ['pointerover', 'pointerenter', 'mouseover', 'mouseenter', 'pointermove',
        'mousemove', 'pointerdown', 'mousedown', 'FOCUS', 'pointerup', 'mouseup', 'click'],

    // ② 只按下：**不补 up / click** —— 给"按下时打开、又被后面那记 click 关掉"的组件
    downOnly: ['pointerover', 'pointerenter', 'mouseover', 'mouseenter', 'pointermove',
        'mousemove', 'pointerdown', 'mousedown'],

    // ③ 只派一次 click：给只认 click 的组件兜底
    clickOnly: ['click'],

    // ④ 诊断级：同样是"按下 → 抬起 → click"，但**一个都不冒泡**
    //    （bubbles:false / composed:false）
    noBubble: ['pointerdown', 'mousedown', 'pointerup', 'mouseup', 'click'],
};
```

★ **第 ④ 级的用途**：它把"**开出即关**"这种可能**单独排除掉**。  
不冒泡的事件照样能触发**挂在元素自己身上**的监听器（框架的模板绑定就挂在元素自己上），  
但**到不了 `document`** —— 也就碰不到那个"点到外面就关"的监听器。  
**如果它在第 4 级成功了**，说明前三级的失败原因是"开出即关"，而不是"没点到"。

```js
function fireMouseSeq(el, mode) {
    if (!el) return;
    const seq = MOUSE_SEQ[mode] || MOUSE_SEQ.full;
    const noBubble = (mode === 'noBubble');
    const common = { bubbles: !noBubble, cancelable: true, composed: !noBubble };

    // ★ 用**页面世界**的事件构造函数（unsafeWindow），不是脚本沙箱里的。
    //   沙箱的 MouseEvent 和页面的不是同一个构造函数 ——
    //   页面里若有 `e instanceof MouseEvent` 这类判断会**静默判否**，
    //   现象正是"点了、不报错、没反应"。
    const PAGE = (typeof unsafeWindow !== 'undefined' && unsafeWindow) || null;
    const pick = function (name) {
        try { if (PAGE && typeof PAGE[name] === 'function') return PAGE[name]; }
        catch (e) { /* 跨 realm 读属性有时会被拒 */ }
        try {
            if (typeof window !== 'undefined' && typeof window[name] === 'function') {
                return window[name];
            }
        } catch (e) { /* 同上 */ }
        return null;
    };
    const PtrEv = pick('PointerEvent');
    const MouEv = pick('MouseEvent');
    const view = PAGE || (typeof window !== 'undefined' ? window : null);

    const fire = function (type, usePointer) {
        let ev;
        try {
            if (usePointer && PtrEv) {
                ev = new PtrEv(type, Object.assign({}, common, {
                    view: view, button: 0, buttons: 1,
                    pointerId: 1, pointerType: 'mouse', isPrimary: true,
                    detail: type === 'click' ? 1 : 0,
                }));
            } else if (MouEv) {
                ev = new MouEv(type, Object.assign({}, common, {
                    view: view, button: 0, buttons: 1,
                    // ★ detail: 真实点击是 1。有些实现拿它区分
                    //   "用户点的"和"代码补的" —— 补上更接近真点击。
                    detail: type === 'click' ? 1 : 0,
                }));
            } else {
                ev = Object.assign({ type: type }, common);
            }
        } catch (e) {
            ev = Object.assign({ type: type }, common);
        }
        try { el.dispatchEvent(ev); } catch (e) { /* 派不出去还有别的级 */ }
    };

    for (let i = 0; i < seq.length; i += 1) {
        const step = seq[i];
        if (step === 'FOCUS') {
            try { if (typeof el.focus === 'function') el.focus(); } catch (e) {}
            continue;
        }
        fire(step, step.indexOf('pointer') === 0);
    }
}
```

#### 4.2.4 填值：三种元素，三套写法

```js
/**
 * 往输入框里写值。要对付三种完全不同的东西：
 *   <input>          → HTMLInputElement.prototype 上的 value setter
 *   <textarea>       → HTMLTextAreaElement.prototype 上的 value setter
 *   contenteditable  → textContent + InputEvent
 */
function setValue(el, value) {
    if (!el) throw new Error('setValue 收到空元素');

    const text = value === null || value === undefined ? '' : String(value);
    if (el.focus) el.focus();

    // ── ① contenteditable ──
    //    isContentEditable 把"属性在祖先上"也算进去了，
    //    比自己读 getAttribute('contenteditable') 可靠。
    if (el.isContentEditable) {
        el.textContent = text;

        // 优先发 InputEvent（带 inputType / data，框架靠它判断"用户输入了什么"）。
        // 构造失败就退回普通 Event —— 特殊环境里 InputEvent 可能不可用。
        let sent = false;
        try {
            el.dispatchEvent(new InputEvent('input', {
                bubbles: true, inputType: 'insertText', data: text,
            }));
            sent = true;
        } catch (e) { sent = false; }
        if (!sent) el.dispatchEvent(new Event('input', { bubbles: true }));

        el.dispatchEvent(new Event('change', { bubbles: true }));
        if (el.blur) el.blur();
        return;
    }

    // ── ② input / textarea ──
    let proto = null;
    if (typeof HTMLTextAreaElement !== 'undefined' && el instanceof HTMLTextAreaElement) {
        proto = HTMLTextAreaElement.prototype;
    } else if (typeof HTMLInputElement !== 'undefined' && el instanceof HTMLInputElement) {
        proto = HTMLInputElement.prototype;
    }

    if (proto) {
        const d = Object.getOwnPropertyDescriptor(proto, 'value');
        if (d && typeof d.set === 'function') d.set.call(el, text);
        else el.value = text;                       // 退化
    } else {
        el.textContent = text;                      // 既不是输入框也不是 contenteditable
    }

    el.dispatchEvent(new Event('input', { bubbles: true }));
    el.dispatchEvent(new Event('change', { bubbles: true }));
    el.dispatchEvent(new Event('blur', { bubbles: true }));
    if (el.blur) el.blur();
}
```

★★★ **两个不能省的点：**

**① `contenteditable` 必须单独处理。**  
目标平台的标题框和描述框**就是 `contenteditable` 的 `div`**，不是 `<input>`。  
对普通 `div` 调 `HTMLInputElement` 的原生 value setter 会**直接抛 `TypeError`**（原生 setter 检查接收者的内部槽，`div` 没有 input 的槽）。  
**不是"设不上值"，是当场炸** —— 而且炸在"填标题"那一步，也就是**文件刚投进去、配额已经扣了之后**。

**② 不能图省事写 `el.value = text`。**  
那是直接写 JS 属性，**绕过了框架的 value setter** → React / Polymer 的内部状态不更新 →  
**界面上看得见值，提交上去是空的**。所以原生 setter 这条路必须保留。

**读回来（每个写操作后面都要）：**

```js
function readValue(el) {
    if (!el) return '';
    if (el.isContentEditable) return String(el.textContent || '');
    if (typeof el.value === 'string') return el.value;
    return String(el.textContent || '');
}
```

```js
// 用起来就三行
setValue(titleBox, item.title);
await sleep(CONFIG.step_pause);
if (readValue(titleBox).trim() !== item.title.trim()) {
    throw new Error('标题回读对不上 —— 不能就这么发出去');
}
```

★ **为什么标题必须核对**：**标题留空，平台会拿文件名兜底**。  
不核对的话，发出去就是一条**标题等于素材文件名**的视频（而文件名通常带着内部编号）。

#### 4.2.5 等待与判据

```js
/**
 * 轮询等一个条件成立。成立返回它的返回值，超时返回 null。
 * 条件自己抛异常时当作"还没好" —— 页面切换过程中元素暂时取不到是正常的。
 */
async function waitFor(fn, timeout) {
    const limit = (timeout === undefined || timeout === null) ? CONFIG.wait_timeout : timeout;

    // ★ 参数是坏的时候必须**立刻抛**，不能进循环：
    //   退出条件 `Date.now() - t0 >= limit` 在 limit 是 NaN 时**恒为假**，
    //   于是循环永不退出 —— 脚本卡在那儿，既不报错也不结束。
    if (!(typeof limit === 'number' && isFinite(limit) && limit >= 0)) {
        throw new Error('waitFor 收到非法超时：' + JSON.stringify(limit));
    }

    const t0 = Date.now();
    for (;;) {
        let v = null;
        try { v = fn(); } catch (e) { v = null; }
        if (v) return v;
        if (Date.now() - t0 >= limit) return null;
        await sleep(200);
    }
}
```

★★★ **这里有一条贯穿全文的判据原则 —— 三态，不是两态：**

| 状态 | 判据 |
|-----|------|
| **成功** | 读到了**正面证据**（"出现了 X"） |
| **失败** | 读到了**反面证据**（"X 明确不在了 / 报错了"） |
| **未知** | 什么都没有（等超时了） |

**「未知」不等于「失败」，更不等于「成功」。**  
把它汇总进"失败"，会诱发一整轮**白重做**；  
把它当成"成功"，会让下游拿到一份**看起来完整、实际是空的**结果。  
→ 报错时必须允许说出"**我不知道**"，并且说清"**我不知道的是哪一件事**"。

**各步骤的判据（这几条是踩出来的）：**

| 步骤 | 判据（正面证据） | 反面教训 |
|-----|----------------|---------|
| 投文件被接受 | **出现上传对话框**（而不是"没报错"） | "文件对象还在"只说明本地没问题，**不代表平台收了** |
| 翻页 | 步骤标记真的变了 | 点完就往下走 → 后面所有元素都找不到，报错像"选择器配错了" |
| 发布被受理 | **出现「处理中」对话框** = 服务端回执 | 曾把它当"忙"→ 死等 30 秒 → 误报失败 → **用户重跑 → 重复投稿** |
| "保存/发布生效" | ★ **自证**：点击**之前**扫一遍页面，点击**之后**再扫，只有"**之前没有、之后才有**"的才算数 | 拿"页面上存在 X"当判据 → 那个 X 可能本来就有 |

★★ **最后那条（自证）值得展开**，因为它是这一整套里最容易搞错的一条：

```js
// 点击之前：先记基线
const baseline = scanNotePresence();

await clickFinalSave();

// 点击之后：只有"基线里没有、现在有了"的才算信号
const hit = await waitFor(function () {
    const now = scanNotePresence();
    const fresh = now.filter(w => baseline.indexOf(w) < 0);
    return fresh.length ? fresh[0] : null;
}, CONFIG.wait_timeout);

if (!hit) {
    // ★ 不许说"失败"，只能说"不知道"
    throw new Error('点了保存，但**没有任何一条判据成立** —— '
        + '所以**不知道**这次到底存上没有。去页面上确认一眼再跑下一条。');
}
```

**为什么**：如果只用"页面上有没有「保存成功」这几个字"，  
那它在**点击之前可能就已经存在**（上一次留下的、或者页面上别处的同名文字）。  
**"保存前没有、保存后有"才是唯一能自证的判据。**

**后台标签页（★ 必须知道）**

浏览器对**隐藏的标签页**会节流定时器：

| 标签页隐藏时长 | 定时器最小间隔 |
|--------------|--------------|
| < 10 秒 | 正常 |
| > 10 秒 | **1 秒** |
| > 5 分钟（intensive throttling） | **1 分钟** |
| 更久 | 可能被**冻结**（所有任务停止） |

★ 而本方案的每一步都在 `waitFor` 里靠定时器轮询（`sleep(200)`）。  
所以后台的后果是：**页面早就准备好了，脚本还睡着** → 15 秒的窗口里可能一次都没轮到 → 报"等不到"。

★★★ **关键区分（这两件事在日志里长得一模一样）：**

|  | 前台 | 后台 |
|---|-----|------|
| 上传本身 | 正常 | **也正常**（在服务端跑） |
| 脚本的判读 | 正常 | **可能误判成失败** |
| 修法 | 改选择器 / 页面结构 | **切回前台** |

**→ 切后台不会让上传失败，但会让脚本以为失败了。**

配套要做两件事（**观测比防护更重要**）：

```js
function pageHiddenNow() {
    try { return !!(typeof document !== 'undefined' && document.hidden); }
    catch (e) { return false; }
}

// ① 失败信息里带上"当时在不在前台"（前台时返回空串）
function hiddenNote() {
    if (!pageHiddenNow()) return '';      // ★ 前台时**什么都不说**
    return '★ 这个标签页现在是**后台**的 —— 先切回前台再重跑。';
}

// ② 切走 / 切回**当场**记一行日志
//    ★ 不是等失败了才回头看 —— 那时标签页可能已经切回来了，**读到的状态是错的**
function installVisibilityWatch() {
    document.addEventListener('visibilitychange', function () {
        if (!running()) return;           // 平时切走切回不记（那是用户的事）
        log(pageHiddenNow() ? '★ 标签页切到**后台**了 —— 定时器会被节流'
                            : '· 标签页回到前台');
    });
}

// ③ waitFor 在后台时把窗口放宽（只放宽后台）
const limit = pageHiddenNow() ? Math.max(base, 90000) : base;
```

★★ **只放宽后台** —— 无条件放宽的话，**所有真失败的反馈都被拖到 90 秒**，  
而"失败了还要等"是日常最痛的地方。

#### 4.2.6 按"字符"截断（emoji 陷阱）

```js
/**
 * 按 **code point** 截断，不是按 JS 的 .length。
 * ★ emoji 占 2 个 UTF-16 code unit，用 slice() 会把它劈成半个孤立代理字符。
 */
function truncateChars(s, max) {
    const chars = Array.from(String(s === null || s === undefined ? '' : s));
    if (chars.length <= max) return chars.join('');
    return chars.slice(0, max).join('');
}
```

★ **为什么这条值得单列**：标题是有长度上限的。  
用 `str.slice(0, 100)` 截断时，如果第 100 位正好落在某个 emoji 的中间，  
会留下一个**孤立的高位代理字符** —— 然后"回读核对"立刻对不上，那一步抛错停下，  
**而配额已经扣了**。  
→ 凡是**对长度有上限、又可能含 emoji** 的字段，截断都必须按 code point 算。

### 4.3 主流程：11 个子步骤

单条约 **25–45 秒**。每一条都走完下面 11 步；**任何一步失败就抛错**，  
由批次层决定"跳过去继续"还是"停下"（见 4.4）。

| # | 做什么 | 判据（怎么知道成了） | 失败怎么办 | 用到 4.2 的哪个机制 |
|---|-------|-------------------|-----------|------------------|
| 1 | **找文件输入框** | 深层查到 `input[type=file]` | 找不到就先点「上传视频」，等对话框起来再找一轮 | 4.2.2 |
| 2 | **文件闸门** | 那个 `File` 对象还在（不是 `undefined`） | 抛错 —— 说明选目录后刷新过页面，要重选 | 4.2.1 |
| 3 | **投文件** | `input.files.length === 1` 且 `change` 已发 | 抛错（这是 File API 层的问题，跟页面无关） | 4.2.4 前半 |
| 4 | **平台接不接受** | 出现上传对话框 / 进度 —— ★ **这是分界线** | 抛错并说明"页面不接受程序化注入" | 4.2.5 |
| 4b | **顺手记视频 id** | 从对话框里的链接锚点读出来 | 允许读不到（链接随进度出现），后面还有一次 | —— |
| 5 | **填标题** | **回读核对**：读回来必须等于填进去的 | 分两轮等（15s + 30s）还是等不到 → 抛错，**报错里带文件名** | 4.2.3 / 4.2.4 / 4.2.6 |
| 5b | **填描述**（配了模板才填） | 回读核对，**而且比长短** | 描述是选填 → 只警告不抛；★ 要报清"变长还是变短" | 4.2.4 |
| 5c | **选缩略图** | 从平台**自动生成的截图里点第 1 张** | 选填 → 找不到就跳过，不抛 | —— |
| 6 | **受众声明** | 勾上「不是给小朋友看的」 | 同上，尽力而为 | 4.2.3 |
| 7 | **一路「下一步」** | 连点 3 次，每次确认真的翻页了 | 抛错；★ 离开这步**之前再记一次视频 id** | 4.2.5 |
| 8 | **设可见性** | 命中「公开」控件 + 回读 | 抛错 | 4.2.3 |
| 9 | **发布** | ★ 出现「处理中」对话框 = **已受理** | 抛错 | 4.2.5 |
| 10 | **取视频链接** | 从对话框 / 地址栏 / 之前记的 id 拼 | 允许失败（停在草稿），记录里链接为空 | —— |
| 11 | **关掉对话框** | 页面回到干净状态 | 警告（下一条开工时会先关残留对话框） | —— |

**三个值得单独说的设计：**

**① 标题必须回读核对**（代码见 4.2.4）。  
**标题空着，平台会拿文件名兜底** —— 不核对的话，发出去就是一条标题等于素材文件名的视频。

**② 描述回读要"比长短"。** 对不上有**两个方向**，处置**完全相反**：

| 方向 | 含义 | 怎么办 |
|-----|------|-------|
| 读回来**更短** | 被截断（超长） | 重填 |
| 读回来**更长** | ★ 框里**原本就有内容**，我们那份被填在了后面 | 得**先清空**再填，否则越填越多 |
| 一样长但内容不同 | 被页面改写过 | 人工看 |

★★ 这个判据不是想出来的，是从**线上实际数据**量出来的两条历史事故：

- 有一批的描述长度**约等于模板的 2 倍** → 模板被写了**两遍**
- 另一批的长度**约等于两个模板长度之和** → **两个产品的文案拼在一起**  
  （手动加新文案时没删旧的）

而当时的警告只说"对不上"，读的人第一反应是"**没填上**"—— **方向反了**，  
处置也就反了（该清空的去重填 → 越填越多）。

```js
function describeDescMismatch(fillLen, gotLen) {
    if (gotLen > fillLen) {
        return '**读回来比填进去长 ' + (gotLen - fillLen) + ' 字** ——'
            + '\n      多半是**框里原本就有内容**，我们那份被填在了它后面。'
            + '\n      这一条发出去，视频描述里会有**两份文案**。';
    }
    if (gotLen < fillLen) {
        return '**读回来比填进去短 ' + (fillLen - gotLen) + ' 字** ——'
            + '\n      多半是被截断（超长），或者填的时候丢了一部分。';
    }
    return '（长度一样但内容不同 —— 被页面改写过。）';
}
```

**③ 「发布已受理」不等于「发布会成功」**  
判据是**出现「处理中」对话框** —— 这是"服务端收下了"的**正面证据**。  
它在服务端继续跑，**脚本不用等**（等的话每条要多花几十秒）：

```js
// 判据从宽到严，命中哪个算哪个：
//   ① 对话框没了 / 不可见        → 成功（发完它自己关掉）
//   ② 对话内容变了（步骤标记变了） → 成功
//   ③ 完成按钮不在了              → 成功
//   ④ 出现「处理中」对话框         → **成功（已受理）**  ← 必须在"判失败"之前
//   ⑤ 有忙碌特征                  → 继续等，不算失败
//   ⑥ 等满预算还没动静            → **才**判失败
```

★★ **为什么 ④ 必须在 ⑥ 之前**：  
曾经把它当"忙"→ 死等 30 秒 → 误报失败 → 用户重跑 → **重复投稿**。  
★ 代价不对称，所以**偏向"认成功"**：

| 误判方向 | 后果 |
|---------|------|
| 误认成功（其实没发成） | 留个草稿，手动点一下 —— **不亏** |
| 误报失败（其实发成了） | **重复投稿，不可逆** |

---

### 4.4 批次控制

| 机制 | 现在的值 | 说明 |
|-----|---------|------|
| 单批上限 | **0 = 不限** | ★ 曾经的上限一直在帮倒忙：一百多条每次都被拦，逼人手动筛 —— 而**筛选本身就是手滑的来源** |
| **连败就停** | **3 条** | 偶发失败（页面被拖慢）跳过去继续；系统性问题（选择器变了）连撞 3 次就停 |
| 成功清零 | 是 | 否则"中间隔了 50 条成功、偶尔失败 3 次"会被误判成"连着失败" |
| 中止按钮 | **做完当前这条才停** | 半路停会留下半个对话框，而且**已经点下去的发布可能已经生效** |
| 失败清单 | 批次结束**汇总** | 那几条会被后面上百条成功的日志淹没，翻上去找没人会翻 |

**★ 顺序是承重的（这点很容易写反）：**

```
① 跳过以前传过的        ← 必须在前面
② 超过上限就报错        ← 必须在后面
```

反过来的后果：这一批 189 个、上限 20 ——  
"勾了 189 个、其中 20 个传过了"会**先**被 ② 拦下、整批一条都不传，  
而真正要传的只有 169 个。**报出来的数字是错的。**

★ 这类错在 diff 里**完全看不出来**（两段代码都在、都对，只是先后换了位置），  
所以判据必须钉**相对位置**：

```js
const pSkip  = src.indexOf('uploadedInEntries(');
const pLimit = src.indexOf('CONFIG.yt.max_per_run');
assert(pSkip >= 0 && pSkip < pLimit, '跳过必须在超上限检查之前 —— 顺序是承重的');
```

**连败计数（成功一条必须清零）：**

```js
let failStreak = 0;
for (const item of todo) {
    if (stop) { log('已手动停止。'); break; }
    try {
        await uploadOne(item);
        failStreak = 0;                       // ★ 成功清零
    } catch (e) {
        failStreak += 1;
        failed.push(item.fileName);           // ★ 收集，批次结束汇总
        if (failStreak >= CONFIG.yt.max_fail_streak) {
            log('连续 ' + failStreak + ' 条失败 —— 看着像系统性问题，停下。');
            break;
        }
    }
}
reportFailures(failed);                        // ★ 抽成函数，才能真的调一遍
```

★ **`reportFailures` 为什么必须抽成函数**：  
内联在循环里的话，测试只能靠"查源码里有没有这段字符串"来验，  
而把 `if (list.length)` 改成 `if (false)` 那种坏法**一个字都不会少**。  
抽出来才能**真的调用一遍**（并且加一条反向断言：**空清单时一条日志都不许打**）。

**开工时会打的几行（格式）：**

```
★ 这一趟要传 **<N> 个**（不限量）。
   一条一条来，中途随时可以按「中止」
· 这一批的标题/文案属于：**<当前产品>**          ← ★ 文案哨兵
[<i>/<N>] <相对路径>
  · 页面形状：<页面形状>
  描述已填：<N> 字（回读一致）
  ✓ 完成：<视频链接>
```

★★ 那一行「**文案属于 `<当前产品>`**」是专门防串台的：  
文案串台**完全静默**（不报错、照传、照扣配额），而换产品时最容易忘的就是它。  
所以每次开工都**主动报一次** —— 而且这个判据要**常驻在代码里**，不能只写在测试里  
（**做业务的人不跑测试**，他改完文案就点开始了）。

```js
function scanCopyProduct() {
    const expect = CONFIG.yt.product_name;          // 当前产品
    const known  = CONFIG.yt.known_products || [];  // 做过的全部产品
    const hay = CONFIG.yt.title_template + '\n' + CONFIG.yt.description_template;
    const found = known.filter(n => hay.indexOf(n) >= 0);
    return { expect, found, ok: !!(expect && found.length === 1 && found[0] === expect) };
}
```

★ 注意这里的两个设计：  
- **禁忌名单是算出来的**（全集 − 当前），不是写死的。  
  产品会**来回切**，"另一个产品是谁"取决于"当前产品是谁" —— 写死任何一边都会在下次切换时失效。
- **没配当前产品时 `ok = false`**（不是 `true`）。  
  "**没检查**"和"**检查通过**"必须分开，跟 4.2.5 那个三态是同一个道理。

### 4.5 记账

每传完一条，往对照表里写：

```json
{
  "relPath": "<相对路径>",
  "fileName": "<文件名>",
  "size": <字节数>,
  "title": "<这条视频实际用的标题>",
  "videoId": "<视频 id，可能为空>",
  "url": "https://www.youtube.com/watch?v=<视频 id>",
  "state": "published",
  "at": "<UTC 时间戳>"
}
```

★ **`fileName` 是配对键。**  
下游（第二段建页面）靠它把"这条素材"和"这个链接"对起来。

★★★ **`videoId` 为空 ≠ 没上传** —— 只说明"没拿到链接"（停在草稿、或取链接那一步失败了）。  
拿它当"没传过"，重跑会**再传一份**，而配额不回收。

**这条判据的方向要往"宽"的那边站：**

| 判据写法 | 判错了会怎样 |
|---------|------------|
| 判**窄**（要求 `videoId` 非空才算传过） | → **重传**：频道上多一份、配额不回收、还得专门去删 |
| 判**宽**（只要有记录就算传过） | → **漏传**：人工看一眼就能补，再跑一次就行 |

★ 所以：**宁可漏传，不可重传。**  
而"判窄"这个错特别容易犯，因为它**看起来更严谨** ——  
"没拿到链接 = 没成功 = 应该重传"，这个推理听起来很顺；  
它漏掉的是：**视频很可能已经传上去了**。

★ **时间存的是 UTC** —— 给人看的时候必须转本地时区，  
差几小时会让人以为"我凌晨在传视频"。

**另外要有一份"历史上传过"的名单，跟"这一批"分开：**

| 数据 | 回答的问题 | 生命周期 |
|-----|-----------|---------|
| **当前记录** | **这一批**传了什么（给下游当队列用） | 会被"归档"清掉 |
| **永久名单** | **历史上**传过什么（管"传没传过"） | **只增不减，归档不动** |

★★ 不分开会出事：**"归档"会清空当前记录**，而"已上传"的判据如果读的是它 ——  
归档之后每个文件都显示"没传过" → 而"跳过已上传"默认是开的 →  
**它以为跳过了什么，实际一个都没跳** → 整批重传。  
★ 而且**全程一个错都不报**（归档成功、日志说"已归档 N 条"，一切正常）。

**通理：一份数据被"清空 / 归档 / 重置"的时候，要去查谁还在读它。**

## 5. 第二段：Play Console 批量建 CSL（详细）

### 5.0 前置条件

| 项       | 要求                                                |
| ------- | ------------------------------------------------- |
| 登录      | 已在 Play Console 登录，且**进到目标 app**                  |
| 上传记录    | **必须在第一段跑完之后**（这一段读的就是那份记录）                       |
| 当前页     | 停在 **CSL 列表页**（脚本要在这里点「创建」）                       |
| 手头没有半成品 | ★ **页面上不能有停在半路的创建向导** —— 有的话脚本会拦下来说"已经在向导里了"（故意的） |

### 5.1 这一批要建哪几个

```
读上传记录 → 取有视频 id 的
      ↓
减掉「已建记录」里已经建过的（按**文件名**）
      ↓
再减掉这次没勾的
      ↓
= 这一批要建 N 条
```

然后会打印：

```
这一批要建 <N> 条：　（脚本 v<版本>）
   1. <文件名（去扩展名）>
   2. <文件名（去扩展名）>
   ...
   ✓ Play 预检查通过：这一趟要用的选择器都配齐了
```

★★ **预检查是"点之前"的最后一道门** —— 选择器缺一个就当场停，  
不等到点了「创建」才发现（那时如果碰巧点进去了，会留下半个向导）。

### 5.2 四步向导（★ 逐步展开）

#### ① 设置

```
点「创建自定义商店页」
   ↓ ★ 入口是个**同名按钮可能有两个**的坑：先试第 1 个候选，看向导起没起来；
      没起来就换第 2 个（不能"点了就算"）
等向导起来 → 回读判据：
   · 页面形状变成「创建 / 复制向导」
   · 且 **步骤条里"当前步"的标记落在第 1 步**
   ↓
选「复制现有商品详情」（单选框，★ 按**选项文字**定位 ——
                         它的 id 是渲染时生成的，不能当选择器用）
   ↓
打开下拉 → 选模版那一项
   ↓
点「下一步」→ **确认真的翻页了**（步骤标记到第 2 步）
```

★ **下拉是这个流程里最难点的一个**。实测的失败模式是"点了但菜单没被创建出来"  
（页面压根没渲染浮层），所以脚本准备了**四级打法**，  
并且失败时会把"**浮层容器在不在文档里**"作为**分水岭**报出来 ——  
在 → 问题在点击；不在 → 页面状态坏了，刷新页面就行。

★ 顺带一条排障经验：如果**手动也打不开**这个下拉，那就是页面坏了，跟脚本无关。

#### ② 需求

```
填「参考名称」= 素材文件名（去掉扩展名）
   ↓
「发布比例」下拉 → 选 100%
   ↓ ★ 选完会弹一个确认框（是 / 否）→ 点「是」
   ↓
「受众」下拉 → 按配置选（广告流量 / 指定网址）
   ↓ ★ 走「广告流量」就**不填网址**；走「网址」才需要（且要求不重复）
   ↓
点「下一步」→ 确认翻页
```

★ **受众有两种模式**，决定了要不要填网址：

| 模式       | 下拉选什么 | 网址                            |
| -------- | ----- | ----------------------------- |
| 广告流量（默认） | 广告流量  | **不填**                        |
| 指定网址     | 对应那一项 | 要填，且**同一批里不能重复**（脚本记住用过的，防重复） |

#### ③ 资源

```
填「视频链接」= 第一段记录里的链接
   ↓
其余保持默认（截图 / 图形素材都不动）
   ↓
点「下一步」→ 确认翻页
```

★ 这一步是**两段流水线的接缝**：链接从第一段的记录里来。  
所以**记录没了 = 这一步没法做** —— 这也是为什么归档前要先导出存档。

#### ④ 评价

```
「AI 资源声明」→ 按配置**不动**
   ↓
「不为资源添加标签」→ 勾上
   ↓ ★ 这一项**可能还没渲染出来**，要点着等（最多 8 秒）
   ↓ ★ 它的勾选框**没有文字**（真正的 `input` 藏在深层结构里），
     只能先找到那行文字、再顺着找到它的框
```

★ **这一步最容易"以为自己点上了"** —— 实测里"已勾"和"没勾"从外观上差别很小，  
而**每一条 CSL 都烧一份不可回收的配额**。所以勾完必须回读。

#### 收尾：保存

```
点「保存」
   ↓ ★★★ 判据必须**自证**：
      保存**之前**先扫一遍页面（基线），保存**之后**再扫，
      **只有"之前没有、之后才有"的才算数**
   ↓ 命中收尾按钮出现 = 保存已受理 ✓
   ↓
点那个收尾按钮
   ↓
等页面回到 **CSL 列表页**（下一条要从这里重新开始）
```

★★★ **为什么要"自证"**：一开始的判据是"页面上有没有某个按钮"——  
但那可能**本来就在**（比如上一条留下的）。用"保存前没有、保存后有"才算数，  
才是**这一条保存造成的证据**。

★★ **为什么必须收尾**：不收尾的话，**这一条的账会记在下一条头上** ——  
下一条一开工撞上"已经在向导里了"那道闸，报出来的错长得像"选择器配错了"，  
去查选择器是白查。

★ **为什么等回到列表页**：下一条要从列表页点「创建」，  
留在别的页面下一条就找不到入口。

### 5.3 三态判据：这个流程的核心

每一步的结果**只有三种**，而且**必须分开**：

| 状态     | 含义                 | 能不能往下走               |
| ------ | ------------------ | -------------------- |
| **成功** | 有**正面证据**（不是"没报错"） | 能                    |
| **失败** | 有负面证据（明确报错、明确不对）   | 不能                   |
| **未知** | **判不出来**           | ★ **当失败处理 —— 绝不当成功** |

★★★ **「未知」不等于「成功」**：写错一次的后果是"那条永远补不上"  
（记成成功 → 下次跳过它 → 而它其实没建出来）。  
所以判不出来时，脚本宁可停下，并在报错里说清"我不知道"。

### 5.4 记账

```
每条建完 → 往「已建记录」写一条（按**文件名**）
         并打印：✓ 完成 <N> 条（这一批）
```

★ 下一次跑的时候，这批会被自动跳过（"这版建过没有"是它的职责）。

## 7. 关键设计决策（为什么这么做）

| 决策                     | 理由                                     |
| ---------------------- | -------------------------------------- |
| **每步都回读**              | 页面上"看起来点了"和"真的生效了"是两件事；而这里点错的代价是配额     |
| **判据要"自证"**            | 成功不能用"页面上有没有那个东西"判 —— 必须"操作前没有、操作后有"   |
| **「未知」不等于「成功」**        | 判不出来就说"不知道"，**不许**当成通过                 |
| **"没问到" ≠ "已失效"**      | 网络不通和链接失效是两件事，混在一起会诱发一轮白重传             |
| **宁可漏传，不可重传**          | 两种错代价不对称：重传 = 频道上多一份 + 额度不回收；漏传 = 再跑一次 |
| **失败就跳过、连败才停**         | 偶发失败（页面变慢）跳过去；系统性问题连撞几次就停，不把上百条一条条试完   |
| **按文件名配对**             | 跨批次稳定；且跟建页侧的「参考名称」一致                   |
| **文案里不许出现别的产品名**       | 串台**完全静默**：不报错、照传、照扣配额                 |
| **配额类操作先"说清要做什么"再问确认** | 人得知道自己在对什么点头；只说"确定吗"是没用的               |

## 8. 异常与恢复

| 现象            | 真实原因                        | 怎么办                                   |
| ------------- | --------------------------- | ------------------------------------- |
| 标题框等很久没出来     | 连着传多条后页面被拖慢 / **标签页在后台被节流** | 切回前台再跑；报错里会带文件名，去 Studio 搜一下它在不在      |
| 「已经有向导了，先处理掉」 | 上一次留下了半个创建向导                | 手动关掉它（或保存 / 舍弃），回到 CSL 列表页            |
| 下拉点了没反应       | 浮层容器不在文档里 = 页面状态坏了          | **手动试一次**：手动也打不开 → 刷新页面；手动能开 → 才是脚本的事 |
| 描述回读对不上       | 框里原本就有内容 / 被截断              | 看报的方向（变长 / 变短）再处置                     |
| 有的视频没拿到链接     | 停在草稿了                       | 记录里链接为空 **≠ 没上传**；下次跑会自动跳过            |
| 面板上「已上传」标记全没了 | 记录被归档了                      | 从归档栈取回；★ 用导出的存档对一下                    |
| 传完发现标题是别家的    | **文案串台**（换产品忘了改）            | 下次开工会打一行"文案属于 <当前产品>"预警；已发的只能重传或手动改   |
| 描述里出现两份文案     | 手动在页面上改时**没删旧的**            | 用描述核验工具扫一遍（见第 9 节）                    |

## 9. 运维与核验

流水线跑起来之后，真正花时间的是**核验**（确认发出去的东西是对的）。  
这一套工具都对着"**从平台侧拿实据**"这个原则：

| 工具   | 解决的问题                       | 判据来源                |
| ---- | --------------------------- | ------------------- |
| 链接体检 | 记录里的链接**还活着吗**              | 平台的 oembed 接口 / 缩略图 |
| 描述核验 | 视频的**描述写对了吗**（长度、有没有混进别的产品） | **频道 RSS 里的逐字描述**   |
| 记录导出 | 把记录导出成存档（防"存储被清"）           | 本地存储                |
| 代码指纹 | 重构时**代码有没有被改到**             | 剥掉注释后逐行哈希           |

★ **核验的铁律：能拿到"平台侧原文"就别看自己这边的记录。**  
核出过的两个真事故，都是靠平台侧原文：

- **描述被写了两遍** / **描述里混着上一个产品的文案**  
  → 只有把**描述本身**量出来才看得见（看长度就够了）——  
  **光看标题列表一切正常**（因为标题是模板，全一样）
- **链接失效** → 本地存储里只有一个字符串，看不出死活

★★ **"线上元数据被手动改过"是最难发现的**：脚本写的东西至少有回读核对，  
**手在页面上改是没有判据的** —— 要么别手改，要么改完用描述核验工具跑一遍。

## 10. 已知限制（先说清，免得踩）

1. **CSL 必须人工确认提交范围** —— 每建一条烧一份配额，脚本不替你判断"该不该建"
2. **选择器是"实测值"不是"推导值"** —— Play Console 的 class 名是构建产物，改版就变。  
   改版后第一件事是**重新采样**（面板有「诊断对话框（复制结构）」能一键复制页面结构）
3. **上传素材会进 Asset Library** —— 那是 app 级共享资产库，影响面大于单个 CSL
4. **平台的限额是平台行为** —— 真到限额它会拒绝 / 排队，脚本不替它拦
5. **本地素材的文件句柄只在"刚选完目录、没刷新页面"时有效** —— 刷新后要重选目录
6. **浏览器切到后台会拖慢脚本**（定时器被节流）—— 跑的时候把标签页留在前台
7. **政策与配额会变** —— 第 2 节那些数字请在使用前重新核对
